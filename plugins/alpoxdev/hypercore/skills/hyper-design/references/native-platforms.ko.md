# 네이티브 플랫폼

iOS나 Android 화면, 즉 SwiftUI, UIKit, Jetpack Compose, 플랫폼 뷰 작업이면 읽는다. 웹 페이지가 아니다. 플랫폼이 이 패키지의 웹 규칙을 대신한다. 시스템 타이포와 Dynamic Type은 CSS 타이포 토큰을, 안전 영역은 뷰포트 패딩을, 탐색 스택과 탭은 페이지 라우팅을, 플랫폼 색상은 hex 토큰을 대신한다. 브리프, 토큰, 납품 게이트는 바뀌지 않는다. 표면만 바뀐다.

## 1. 타이포와 크기 키움

| 징후 | 이유 | 고치기 |
|---|---|---|
| 한 기기에 맞춰 조정한 고정 텍스트 크기 | 사용자가 텍스트 크기를 키우거나 줄인다. 고정 값은 다른 설정에서 넘치거나 비좁아진다 | 플랫폼 텍스트 스타일에서 시작하고 시스템이 키우게 둔다. 납품 전에 가장 작은 크기와 가장 큰 크기를 확인한다 |
| CSS 규모(16/20/24/32px)를 그대로 옮긴 크기 목록 | 앱이 전화기 안에 눌러 담은 웹 페이지처럼 읽힌다 | 각 역할에 가장 가까운 시스템 스타일을 대응시킨 뒤 동점은 토큰 계획으로 가른다 |
| 가장 큰 크기에서 잘리는 텍스트 | 레이아웃에 자랄 자리가 없다 | 컨테이너가 늘어나거나 줄바꿈하게 둔다. 텍스트 행은 고정 높이 상자 안에 넣지 않는다 |

## 2. 안전 영역과 인셋

| 징후 | 이유 | 고치기 |
|---|---|---|
| 화면 가장자리에 고정된 내용 | 노치, 상태 막대, 홈 인디케이터, 제스처 영역이 가린다 | 안전 영역 안으로 넣는다. 플랫폼 레이아웃 기본 요소가 기본으로 해 주므로 인셋을 무시하지 않는다 |
| 상태 막대와 홈 인디케이터를 무시하는 고정 머리말 | 텍스트와 컨트롤이 시스템 크롬 아래에 깔린다 | 플랫폼이 자기 크롬을 배치하게 두고, 직접 만든 막대는 그 아래에 둔다 |
| 폰, 태블릿, 접히는 기기, 분할 화면에 레이아웃 하나 | 늘어난 폰 레이아웃은 실수처럼 보인다 | 컴팩트 폭과 레귤러 폭을 다른 레이아웃으로 다룬다. `responsive-reflow.md`가 폰과 데스크톱을 다른 레이아웃으로 다루는 것과 같다 |

## 3. 탐색과 구조

| 징후 | 이유 | 고치기 |
|---|---|---|
| 앱 안에 그려 넣은 웹식 상단 메뉴 | 사용자가 사이트를 다시 배워야 한다 | 플랫폼 컨테이너를 쓴다. 파고여 들어가면 탐색 스택, 주요 목적지 몇 개는 탭, 짧은 작업은 시트로 둔다 |
| 아무 데도 가지 않는 뒤로 가기 | 스택을 모델링하지 않았다 | 스택 맨 위는 목록이다. 밀어 넣은 화면은 모두 부모로 돌아올 수 있다 |
| 모든 화면이 모달 | 시트는 짧은 작업과 분명한 빠져나옴을 약속한다 | 계층은 푸시로 두고, 시트는 범위 있는 작업에만 쓴다 |

## 4. 터치와 컨트롤

| 징후 | 이유 | 고치기 |
|---|---|---|
| 터치 최소값보다 작은 컨트롤 | 손가락은 커서가 아니다 | iOS 44pt, Android 48dp를 최소로 둔다. 보이는 크기가 작으면 패딩이나 더 큰 히트 영역을 쓴다. 근거와 이유는 `responsive-reflow.md` §5에 있다 |
| 하나처럼 읽히는 붙어 있는 타깃 둘 | 엄지가 잘못된 쪽에 닿는다 | 하나의 누름 영역이 다음을 덮지 않게 간격을 둔다 |
| hover에서만 존재하는 것 | 터치스크린에는 hover가 없다 | 모든 hover 상호작용에 탭 대응을 두고 눌림 피드백을 보이게 한다 |
| 보이는 대안 없는 제스처 | 제스처를 못 하는 사람도 있다 | 같은 동작을 버튼이나 메뉴 경로로도 둔다 |

## 5. 색과 외관

| 징후 | 이유 | 고치기 |
|---|---|---|
| 곳곳에 박힌 hex 색 | 다크 모드, 강제 색상, 고대비 설정에서 화면이 깨진다 | 의미 플랫폼 색(label, secondary label, background, separators와 Android 대응값)을 쓴다. 밝기·어둡기와 접근성 설정을 함께 들고 간다 |
| 외관을 바꿀 때마다 손으로 다시 맞춘 값 | 값이 역할에서 어긋났다 | 역할 이름을 한 번 정한 뒤 외관마다 풀리게 둔다 |
| "테크처럼 보여서" 다크 모드 | 유행이지 제품 결정이 아니다 | 브리프가 하나를 못 박지 않는 한 두 외관 모두 작동하게 둔다. 납품 전에 둘 다 확인한다 |

## 6. 네이티브 화면의 증거

CSS 토큰, Lighthouse 보고서, 브라우저 스크린샷은 앱에 대해 아무것도 증명하지 못한다. 네이티브 화면의 증거는 다음 중 하나다.

- 확인한 크기 클래스에서의 시뮬레이터나 기기 캡처. 텍스트 크기 설정을 함께 쓴다.
- 해당 화면의 접근성 검사기 출력. 라벨, 역할, 상태가 드러나야 하며 빌더의 인상은 아니다.
- 프로젝트가 이미 돌리는 플랫폼 미리 보기·스크린샷 테스트 출력. 이름을 함께 쓴다.

시뮬레이터나 기기가 없으면 렌더 항목을 `static_only`나 `unavailable`로 표시하고 이유를 적는다. 웹 경로에서 브라우저가 없을 때 보고하는 것과 같다. 소스만으로 시각이나 접근성 통과를 보고하지 않는다.

## 7. 원칙으로만 옮겨지는 웹 규칙

대비, 목적 테스트, 정직한 자리 표시, 납품 게이트는 그대로 옮겨진다. 제품에 관한 것이지 매체에 관한 것이 아니기 때문이다. 옮겨지지 않는 것은 CSS 토큰, 중단점 이름, hover와 커서 동작, 브라우저 크롬, Lighthouse 수치, 뷰포트 주장이다. 웹 규칙과 플랫폼 규칙이 어긋나면 앱에서는 플랫폼 규칙이 이기고, 어긋난 점을 브리프에 적는다.
