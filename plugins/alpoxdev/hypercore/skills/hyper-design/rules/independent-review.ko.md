# 독립 검토

`design`, `restyle`, `mockup`, `audit`, `verify`의 검토 단계 전에 읽는다. 이 파일은 누가 검토하는지, 검토자가 무엇을 받는지, 발견 사항이 무엇을 인용해야 하는지, 발견 사항에 어떻게 답하는지를 소유한다.

## 1. 만든 쪽이 혼자 채점하지 않는 이유

자기 산출물을 판단하는 모델은 자기가 만들었을 법한 텍스트와 이미지를 선호한다. 그것이 바로 이 스킬이 피하려는 중간값이다. 모델의 비구조적 스크린샷 비평도 사람 검토자에 못 미치고, 각 지적을 화면 영역에 연결하면 나아진다. 그래서 검토는 만들기와 분리하고, 만든 쪽의 추론을 주지 않고, 증거에 묶는다.

## 2. 검토자

| 가능한 것 | 검토 모드 | 보고 값 |
|---|---|---|
| subagent나 두 번째 세션을 띄울 수 있다 | §3의 입력만 받은 새 검토자 | `subagent` |
| subagent 기능이 없다 | 같은 에이전트가 빌드를 마친 뒤 새 pass로 §3의 입력만 읽고, 자기 노트를 보기 전에 §4의 질문에 모두 답한다 | `self (degraded)` |
| 사용자가 검토한다 | 사용자의 지적은 발견 사항이다. 그대로 기록한다 | `user` |

검토자에게 만든 쪽의 근거, `brief.md`의 추론 섹션, 만든 쪽이 좋다고 믿는 목록을 절대 주지 않는다.

## 3. 검토자 입력

- 한 문장 브리프, 방문 모드, 다이얼이 붙은 디자인 읽기(Design Read) 줄(`brief.md`의 나머지는 제외)
- 검사한 너비와 상태의 렌더 캡처, 렌더링이 없으면 바뀐 소스 경로
- `rules/craft-floor.md` §9와 아래 §5의 "보이는 것 / 할 일" 표
- mockup이면 `references/mockup-craft.md` §2의 실패 모드

## 4. 질문, 순서대로

1. 이것이 그 분류의 어느 제품이든 될 수 있는가? 이 제품에 고유한 것을 대거나, 아무것도 없다고 보고한다.
2. 시선이 처음, 두 번째, 세 번째로 어디에 닿고, 그것이 작업이 요구하는 순서인가?
3. 역할이 없는 요소는 무엇인가. 장식, 컨테이너, 라벨, 모션.
4. 시스템을 깨는 값은 무엇인가. 한 번만 쓴 색, 크기, 간격, 반경, 시간.
5. 빠졌거나 미완으로 보이는 상태는 무엇인가?
6. 실패한 정석 수치 항목은 무엇이고 측정값은 얼마인가?
7. 결과가 선언한 다이얼(ENERGY, RHYTHM, MOTION)과 맞고, 초점 하나와 강조 하나, 정체성 모티프 하나가 있는가?
8. 로고와 제품 이름을 바꿔도 이 제품의 것으로 남는 것이 있는가?

가장 크게 보이는 실패를 먼저 고치고, 그다음 처음부터 다시 확인한다.

## 5. 보이는 것 / 할 일

| 보이는 것 | 할 일 |
|---|---|
| 모든 섹션이 같은 카드 그리드다 | 섹션마다 역할을 주고 그 역할이 요구하는 레이아웃을 준다 |
| 모든 제목 위에 eyebrow 라벨이 있다 | 상태나 순서를 전달하는 라벨은 남기고 나머지는 없앤다 |
| 읽기 어려운 회색 텍스트 | 대비를 정석 수치까지 올리고 위계는 크기와 굵기로 표현한다 |
| 모든 곳의 무게가 같다 | 화면마다 하나를 주역으로 만든다 |
| 역할 없는 그라디언트, 글로우, orb | 제거하거나 브랜드나 상태에 묶는다 |
| 모든 요소에 모션이 있다 | 피드백 모션과 의도해 만든 순간 하나를 남기고 나머지는 없앤다 |
| 정상 경로만 있다 | loading, empty, error를 디자인한다 |
| 근거를 흉내 낸 것(로고, 지표, 후기) | 제거하거나 placeholder로 표시한다 |
| 창을 카드에 축소해 사방 여백을 준 형태(mockup) | 잘라서 모서리 밖으로 흘러나가게 한다 |

## 6. 발견 사항 형식

검토 발견 사항은 다음을 인용한다.

- 영역(캡처 파일과 구역, 또는 파일과 줄)
- `references/anti-pattern-catalog.md`의 rule ID 또는 `rules/craft-floor.md`의 정석 수치 항목
- 측정하거나 관찰한 값
- `rules/evidence-and-severity.md`의 심각도

영역과 규칙이 없는 발견 사항은 발견 사항이 아니라 논평이다. 기록하되 조치하지 않는다. 비평 발견 사항은 보고서에 `| Before | After | Why |` 표로 낸다.

## 7. 발견 사항에 답하기

- `high`(P0/P1) 발견 사항은 수정 예산 안에서 고치거나, 사용자가 확인할 수 있는 이유로 답한다.
- 브리프나 문서화된 브랜드 결정과 충돌하는 발견 사항은 그 증거로 답한다. 따르지 않는다.
- 검토자 답변은 증거다. "좋아 보이니 그대로 내보내자"는 통과가 아니다. 체크리스트와 인용된 발견 사항만 결정한다.
- 기능을 지워서 만족시키는 규칙(모든 모션 제거, 모든 상태 제거, 실제 배지 제거)은 퇴화한 수정이다. 의미를 지탱하던 것을 되살린다.

### Evidence grade

편향 결과는 텍스트에서 측정된 것이지 인터페이스에서 측정된 것이 아니다. 이를 UI 검토에 적용하는 것은 추론이다. 검토자 프로토콜은 이 패키지의 설계다.
