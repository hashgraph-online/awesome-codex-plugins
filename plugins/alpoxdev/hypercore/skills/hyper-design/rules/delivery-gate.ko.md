# 납품 게이트

`design`, `restyle`, `mockup`, `clean`의 결과를 넘기기 전과 `audit`, `verify`의 발견 사항을 쓰기 전에 읽는다. 이 파일은 최종 통과·실패 목록, 각 줄에 필요한 증거, 줄이 실패했을 때 일어나는 일을 소유한다.

## 1. 원칙

이 문서의 모든 항목은 두 질문으로 결정한다.

- **목적:** 이 기법은 무엇을 위해 쓰는가. 그라디언트, 글로우, 카드 그리드, 배지, 모션은 위계, 정체성, 가독성, 상태에 기여하고 그 이유가 `brief.md`에 적혀 있으면 허용된다. "최신처럼 보인다"와 "기본값이다"는 이유가 아니다.
- **생동감:** 일반적인 패턴을 걷어내면 빈자리가 남고 모델은 그 빈자리를 가장 일반적인 출력으로 채운다. 깨끗하지만 생기 없는 화면도 실패다. 생동감은 의도해 더한다(§6).

완료는 세 가지를 동시에 뜻한다. 모든 기법에 목적이 적혀 있고 화면이 자기 정체성을 가지며 실제로 동작한다.

## 2. 게이트 실행 방법

- 게이트를 보고서의 `## 검증` 절에 표로 쓴다. 항목, `PASS | FAIL | n/a | not run`, 증거.
- 증거 없는 `PASS`는 통과가 아니다. 증거는 파일과 줄, 명령과 그 출력, 뷰포트와 상태를 밝힌 캡처, 클릭 확인 기록이다("회원가입 -> /signup, 콘솔 오류 없음"; "빈 폼 -> 검증 메시지"; "모바일 메뉴 -> 열리고 Escape로 닫힘").
- 결과물을 실행할 수 없으면(정적 연출 화면, 소스만 있는 경우) 그렇다고 밝히고 코드를 읽어 컨트롤마다 확인한다. 렌더링이 필요한 항목은 `static_only`로 표시한다.
- `FAIL`이 하나라도 있으면 납품을 막는다. 모드의 수정 예산(`rules/workflow.md` §4) 안에서 고치고 게이트를 다시 실행한다. 예산을 다 쓰면 납품 대신 열린 줄을 보고한다.
- `audit`에서는 실패한 줄마다 번호가 붙은 발견 사항이 된다. `clean`에서는 블록 1과 편집이 건드린 줄만 실행한다.
- 세션을 이끄는 다른 워크플로가 이 게이트를 대체하지 않는다. 그쪽 요약은 게이트로 치지 않는다.

## 3. 블록 1: 정직성과 기능 (절대)

모든 답은 **아니오**여야 한다. 이 줄은 브리프가 다르게 요구해도 유지된다. 충돌은 소유자에게 제기하며 조용히 해소하지 않는다.

| # | 질문 | 규칙 |
|---|---|---|
| H1 | 실제 출처 없이 숫자, 통계, 변화량, 후기, 고객 로고, 인물, 보안이나 규정 준수 주장, 성능 수치를 보여 주는가? | `copy.unsupported-metric`, `copy.unsupported-proof`, `copy.fabricated-claim` |
| H2 | 실제 내용이나 자리 표시로 분명히 밝힌 내용(`[REAL DATA]`, "Coming soon") 대신 사실처럼 보이는 내용(기능, 팀, 활동 피드 항목, 표 행, `John Doe` 같은 폼 값)을 지어냈는가? | `copy.placeholder-person`, `structure.filler-feed` |
| H3 | 소유자 확인 없이 로고, 아바타, 제품 표식, 인물 일러스트를 최종본처럼 만들었는가? | `copy.assumed-asset` |
| H4 | 버튼, 링크, 드롭다운, 폼이 아무것도 하지 않거나, 이동 항목이 없는 페이지나 구역을 가리키는가? 자리 표시에는 보이는 "Coming soon" 표시가 필요하다. | `quality.dead-control`, `quality.dead-anchor` |
| H5 | 데이터 화면에 빈, 로딩, 오류 상태가 없거나, 그 상태가 원인과 다음 행동을 말하지 않는가? | `quality.missing-states` |
| H6 | FAQ에 이 제품 사용자의 실제 질문이 아닌 템플릿 질문이 있는가? | `structure.template-faq` |
| H7 | 출시하는 테마(라이트 또는 다크)가 색, 대비, 글꼴, 레이아웃을 깨뜨리는가? | `quality.theme-broken` |
| H8 | 소스에 쓰지 않고 문자열 치환으로 소스나 CSS를 다시 쓰는 스크립트로 기능을 추가했는가? | `quality.patch-script` |
| H9 | 사용자가 요청하지 않은 유명 제품의 겉모습을 그대로 베꼈는가? | `structure.product-clone` |
| H10 | 빌드하거나 실행하지 않고, 콘솔을 확인하지 않고, 모든 상호작용 요소의 클릭 확인 기록 없이 결과를 넘겼는가? | `rules/validation-and-reporting.md` |
| H11 | 이번 실행에서 측정하지 않은 Lighthouse 점수나 Core Web Vitals 수치를 보고했는가? | `rules/craft-floor.md` §8 |

## 4. 블록 2: 정석 수치 기준 (절대)

`rules/craft-floor.md` §9의 모든 항목이 이유와 함께 `pass`, `n/a`, `static_only` 중 하나다. 가장 자주 빠지는 항목은 다음과 같다.

- `references/contrast-check.md`로 계산한 모든 텍스트 쌍. 이미지와 그라디언트 위 텍스트를 포함하며 최악 지점에서 확인한다.
- 키보드로 도달 가능하고 포커스 표시가 보이는 모든 컨트롤. 대체 없이 `outline: none`을 쓰지 않는다.
- 켜진 모든 컨트롤이 `cursor: pointer`를 보이고 네이티브 요소이며 접근 가능한 이름이 있고 서로 다른 hover, active, disabled 상태를 가진다(`references/accessible-interaction.md`).
- 가로 넘침이 없고 잘린 것이 없으며 가장 좁은 폭에서 타깃이 최소 24×24 CSS px(터치 표면은 44 px)이고 서로 간격이 있다(`references/responsive-reflow.md`).
- 모든 미디어 요소에 크기가 있고 히어로 이미지가 지연 로드가 아니며 렌더링을 막는 서드파티 스크립트가 없다.
- 차트 기하(`rules/rendered-evidence.md`의 chart geometry checks)를 측정했거나, 렌더링 측정값이 없으면 `unverified`로 보고한다(`references/chart-artifact.md`).
- `assets/report-template.md`(`## Processing summary`)의 WCAG 2.2 표: 나열된 모든 기준이 이유와 브라우저 증거를 갖춘 `PASS`, `FAIL`, `N/A` 중 하나다. 누락된 기준이나 증거 없는 `PASS`는 실패다

## 5. 블록 3: 목적과 사용량 (기법은 허용, 이유는 필수)

각 줄은 그 기법이 `brief.md`에 이유 없이 기본값으로 나타나거나 사용량 상한을 넘을 때만 실패한다.

| # | 기법 | 통과 조건 |
|---|---|---|
| P1 | 그라디언트, 글로우 배경, 방사형 오브, 보라나 네온 팔레트 | 브랜드 정체성이거나 한 위계 단계를 다른 단계와 분리하며 이유가 적혀 있다 |
| P2 | 아이콘 | 각 아이콘이 내용과 관련 있고 세트가 라이브러리 기본값이 아니라 결정이며 "AI"를 뜻하는 반짝임, 요술봉, 별, 로봇, 오브가 없다 |
| P3 | 서체 | 모델 기본값이라서가 아니라 브랜드나 참조에서 이유를 적어 고른 서체다 |
| P4 | 배경 텍스처, 그리드, 점, 청사진 패턴 | 제품 정체성이나 실제 캔버스를 뒷받침한다 |
| P5 | 버튼의 화살표 | 방향 단서가 필요한 동작에만 있다 |
| P6 | 배지, 필, 상태 점 | 각각 실제 상태나 레이블을 표시한다; 필, 얇은 테두리, 글로우, 점, 대문자를 함께 쓰지 않는다 |
| P7 | 글래스나 배경 흐림 | 요소가 최대 하나나 둘; 내비게이션 바, 카드, 모달, 사이드바에 함께 쓰지 않는다 |
| P8 | 그림자 | 떠오르는 몇몇 요소의 고도를 표시한다; 대부분의 표면은 평평하게 둔다 |
| P9 | 글로우 | 초점 요소가 최대 하나나 둘; 카드, 버튼, 배지, 아이콘, 테두리, 배경에 함께 쓰지 않는다 |
| P10 | 카드 그리드 | 카드 크기와 처리가 내용 무게를 따른다; 모든 항목이 카드는 아니다 |
| P11 | 모션 | 각 모션이 적힌 목적을 갖고 MOTION 다이얼과 맞는다; 실제 상태 없는 끝없는 반복이 없다 |
| P12 | 일러스트 | 각각이 제품과 연결된다; 아니면 실제 스크린샷을 쓰거나 넣지 않는다 |
| P13 | 팔레트 | 핵심 색 최대 두세 개에 강조색 하나, 중성색은 세지 않는다. 문서화된 시스템이 다르게 말할 때는 예외다 |

## 6. 블록 4: 생동감 (있어야 함)

모든 답은 **예**여야 한다.

| # | 질문 |
|---|---|
| L1 | 만들기 전에 디자인 읽기(Design Read)를 밝히고 세 다이얼(ENERGY, RHYTHM, MOTION)을 `brief.md`에 정했는가? |
| L2 | 결과가 다이얼과 맞는가? RHYTHM 3에서 섹션이 모두 같으면 실패이고 MOTION 1에서 스크롤 연출을 넣으면 실패다. |
| L3 | 화면마다 분명한 초점이 정확히 하나인가? |
| L4 | 여백을 남은 공간이 아니라 구조(묶음과 리듬)로 쓰는가? |
| L5 | 의도한 강조가 하나 있는가? 없어도 안 되고 모든 곳에 있어도 안 된다. |
| L6 | 정체성 모티프가 하나 있는가? 구체적이고 반복되는 패턴, 제스처, 타이포그래피 목소리다. |
| L7 | 로고와 제품 이름을 바꿔 끼우면 디자인이 여전히 이 제품으로 느껴지고 다른 제품으로는 느껴지지 않는가? |

방향 없이, 물어볼 기회도 없이 만든 디자인은 "방향 없는 초안"으로 표시하고 정직한 다이얼 ENERGY 1 / RHYTHM 1 / MOTION 1을 쓰며 납품물로 제시하지 않는다(`rules/design-direction.md` §10).

## 7. 브리프와의 충돌

`DESIGN.md`나 브랜드 가이드, 사용자의 예시가 블록 1의 줄이 금지하는 것을 요구하거나, 이유를 밝히지 않은 블록 3의 패턴을 요구하면 조용히 따르지도 조용히 뒤집지도 않는다. 요소를 짚고 걸리는 줄을 짚고 한 번 묻고 답을 `brief.md`에 기록한다. 대담한 팔레트나 특이한 서체는 정체성이지 충돌이 아니다.
