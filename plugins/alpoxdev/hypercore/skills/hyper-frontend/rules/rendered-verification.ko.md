# 렌더링 검증

프런트엔드 작업을 전달했다고 말하기 전에, 그리고 `verify` 모드 전체에서 이 규칙을 읽습니다. 소스가 맞아 보인다는 것은 페이지가 맞다는 증거가 아닙니다. 실제 브라우저에서 무엇을 확인하는지, 어떻게 읽는지, 브라우저가 없으면 어떻게 보고하는지를 정합니다.

## 1. 증거 라벨

보고서의 모든 주장에 세 라벨 중 하나를 붙이고, 표현으로 라벨을 올리지 않습니다.

- `static`: 소스, 빌드, 타입 검사 결과에서 읽은 것.
- `rendered`: 실제 브라우저에서 밝힌 뷰포트, 테마, 상태로 관찰한 것.
- `not verified`: 관찰할 수 없었던 것. 이유를 적습니다.

## 2. 캡처 매트릭스

변경을 덮는 가장 작은 매트릭스를 고르고 보고서에 적습니다.

| 축 | 값 |
|---|---|
| 너비 | 320(리플로 하한), 390(폰), 1440(데스크톱). 둘 사이에서 레이아웃이 바뀌면 768을 더합니다 |
| 테마 | 프로젝트가 둘 다 제공하면 라이트와 다크 |
| 상태 | 변경이 건드리는 상태 매트릭스의 모든 행([layout-and-states.ko.md](layout-and-states.ko.md) §6) |
| 콘텐츠 | 실제 또는 현실적인 것: 비어 있음, 긴 라벨, 끊기지 않는 문자열, 많은 항목 |
| 입력 | 포인터, 그다음 키보드만(Tab, Shift+Tab, Enter, Space, Escape) |
| 환경설정 | `prefers-reduced-motion: reduce`, 필요하면 forced colors |

컴포넌트 하나를 작게 고쳤다면 제품 전체가 아니라 그 컴포넌트가 닿을 수 있는 상태와 너비면 충분합니다.

## 3. 읽을 것

- 크기, 간격, 대비, 줄 길이는 소스가 아니라 계산된 값(`getComputedStyle`, 레이아웃 사각형)으로 읽습니다.
- 한 컨트롤의 치수를 상태별로 비교합니다. 모두 같아야 합니다([layout-and-states.ko.md](layout-and-states.ko.md) §5).
- 콘솔을 읽습니다. 페이지가 멀쩡해 보여도 오류나 실패한 요청은 발견 사항입니다.
- 캡처한 각 상태의 스크린샷을 눈으로 봅니다. 측정은 통과해도 그림은 틀릴 수 있습니다.
- 키보드 확인: 모든 동작에 닿고, 순서가 읽기 순서와 같고, 포커스가 항상 보이며 sticky 요소 뒤에 가려지지 않고, 갇히지 않아야 합니다.

## 4. 구현 단계 접근성 확인

구현이 결정하는 확인 항목입니다. 디자인 시스템 산출물 전체의 적합성 표는 다른 작업입니다.

| 항목 | 통과 조건 |
|---|---|
| 리플로(1.4.10) | 320 CSS px에서 주요 콘텐츠가 가로로 스크롤되지 않음 |
| 대비(1.4.3, 1.4.11) | 텍스트 4.5:1(큰 텍스트 3:1), 컨트롤 테두리·아이콘 3:1, 두 테마 모두, 플레이스홀더 포함 |
| 대상 크기(2.5.8) | 포인터 대상이 24×24 CSS px 이상 |
| 포커스(2.4.7, 2.4.11) | 모든 표면에서 포커스 링이 보이고 sticky·오버레이에 완전히 가려지지 않음 |
| 키보드(2.1.1, 2.1.2) | 모든 동작에 닿고 키보드 트랩이 없음 |
| 이름 | 모든 컨트롤에 접근 가능한 이름이 있고 이미지에는 의미 있는 대체 텍스트가 있거나 장식으로 표시됨 |

각 항목을 통과, 실패, 해당 없음으로 보고하고 근거가 된 관찰을 붙입니다.

## 5. 성능 확인

요청이나 프로젝트가 성능을 요구하거나 변경이 회귀일 가능성이 있을 때(큰 이미지, 새 의존성, 긴 목록)만 실행합니다.

- 좋은 사용자 경험의 75번째 백분위 목표: LCP 2.5초 이내, INP 200 밀리초 이하, CLS 0.1 이하.
- 프로덕션 빌드가 있으면 그것을 실제 브라우저에서 측정합니다. 개발 서버를 썼다면 그렇게 밝힙니다.
- 측정하지 않은 점수나 시간은 `not verified`입니다. 숫자를 지어내지 않고, 점수를 올리려고 동작·콘텐츠·모션을 포기하지 않습니다.

## 6. 브라우저가 없을 때

페이지를 열 브라우저 기능이 없으면 정적 확인을 모두 실행하고, 각 주장에 `static`을 붙이고, 없었던 기능을 정확히 밝히며 `delivered_unverified`로 끝냅니다. 확인을 돌리려고 브라우저, 드라이버, 테스트 의존성을 설치하지 않습니다. 소스만 보고 시각 결과가 확인되었다고 쓰지 않습니다.

## 7. fix 모드

보고된 결함은 다음 순서로 다룹니다.

1. 보고가 밝힌 뷰포트, 테마, 상태에서 먼저 재현하고 증거를 남깁니다. 사용자의 관찰은 사실입니다. 보고를 의심하려고 재현하는 것이 아니라 원인을 찾으려고 재현합니다.
2. 깨진 관계를 한 문장으로 말합니다. 어떤 제약, 상태, 소유권이 틀렸는지입니다.
3. 그 관계를 바로잡는 가장 작은 변경을 프로젝트 자체 스타일로 합니다.
4. 같은 캡처를 다시 하고 이어서 인접 상태와 너비를 확인한 뒤 전후를 기록합니다.
5. 수리 시도가 두 번 실패하면 멈추고 증거와 함께 `blocked`로 보고합니다.
