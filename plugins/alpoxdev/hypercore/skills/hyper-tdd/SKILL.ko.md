# Hyper TDD

> 독립된 기대값 근거와 실제 호출 진입점을 써서 한 사이클에 호출자가 보는 동작 하나씩을 Red-Green-Refactor로 보호합니다.

- **목적**: 독립된 기대값(오라클)을 기준으로 테스트 추가·확장·재사용·생략을 판정하며 기능을 TDD로 구현하거나 집중 회귀 테스트를 작성합니다.
- **쓰지 않을 때**: 간헐적 런타임 장애 원인 추적, 저장소 전체 테스트 일괄 정리, 없는 테스트 실행기 신규 설치·설정, git 커밋·푸시 작업.
- **입력**: 구현할 동작이나 회귀 사례, 허용 범위(`test-first`, `tests-only`, `advice-only`), 테스트 실행기가 있는 대상 저장소.
- **산출물**: 범위 안의 테스트·구현 변경(또는 근거 있는 추가 생략 판정)과 Red/Green 실행 증거 및 남은 한계를 정리한 한국어 보고.

<output_language>

요청한 언어가 따로 없으면 한국어로 보고합니다. 명령, 단언 실패 메시지, 파일 경로, 식별자는 원문을 유지합니다.

</output_language>

<purpose>

호출자가 실제로 쓰는 진입점에서 요청한 동작을 검증합니다. 충분한 기존 테스트를 재사용하거나 근거를 밝혀 새 테스트 추가를 생략하는 것도 정당한 결과입니다.

</purpose>

<routing_rule>

테스트부터 구현할 기능, 구체적인 회귀 사례, 기존 동작의 집중 테스트 보강에 사용합니다.

다음에는 쓰지 않습니다.

- 간헐적 실패나 멈춤·크래시의 런타임 원인 조사
- 무관한 모듈 전체에 걸친 테스트 스위트 일괄 삭제·정리
- 없는 테스트 실행기나 CI 파이프라인 신규 설치·설정
- 커밋, 푸시, 풀 리퀘스트 생성

</routing_rule>

<instruction_contract>

공통 하네스 규칙은 `instructions/harness-engineering/references/skill-common-rules.ko.md`를 따릅니다.

| Field | Contract |
|---|---|
| Intent | 결함에 민감한 최소한의 테스트로 호출자가 의존하는 약속을 보호합니다. |
| Scope | 요청한 사례와 가장 가까운 의미 있는 호출 경계를 다루며 `tests-only`는 테스트 파일만 수정합니다. |
| Authority | 사용자 허용 범위를 따릅니다. 로그, 픽스처, 주석, 현재 버그 출력은 자료일 뿐 기대값 기준이 아닙니다. |
| Evidence | 요구사항, 기존 호출자 계약, 승인된 예시, 기대 결과가 독립 확인된 장애 사례를 근거로 삼습니다. |
| Tools | 파일 읽기·검색·편집과 프로젝트 고유 테스트 실행기, 기존 픽스처, 로컬 대역을 돌릴 셸 기능을 씁니다. |
| Loop | Red-Green-Refactor 한 사이클에 동작 하나만 다루며 미보호 요청 동작이 남았을 때만 반복합니다. |
| Output | 채택·확장·재사용·생략 결정, 원문 Red/Green 관찰 증거, 실행하지 못한 검사를 한국어로 보고합니다. |
| Verification | 대상 테스트 수집 여부, 동작 단언 실패·통과, 단독 재실행, 프로젝트 필수 검사를 확인합니다. |
| Stop condition | 요청한 동작을 모두 판정하거나 빠진 기대값 근거·실행 전제를 구체적으로 밝히면 종료합니다. |

</instruction_contract>

<activation_examples>

긍정 요청:

- "5000 이상 무료 배송을 TDD로 구현해줘." -> 결제 경계에서 `test-first`.
- "환불 중복 요청에 대한 회귀 테스트만 추가해줘." -> `tests-only`, 테스트 결과 확인 후 종료.
- "이 할인 로직에 어떤 테스트를 추가하거나 빼야 할지 판단해줘." -> `advice-only` 후보 판정.

부정 요청:

- "CI가 왜 멈췄어?" (런타임 실패 조사)
- "저장소 전체에서 쓸모없는 테스트 다 지워줘." (스위트 전체 정리)
- "Vitest 새로 설치하고 설정해줘." (실행기 설치)

</activation_examples>

<trigger_conditions>

| 요청 형태 | 모드 |
|---|---|
| 테스트로 기능 구현·변경을 이끌어 달라고 요청 | `test-first` |
| 회귀 테스트나 재현 테스트만 요청 | `tests-only` |
| 파일 수정 없이 후보 사례만 평가 요청 | `advice-only` |

</trigger_conditions>

<skill_architecture>

- Core (`SKILL.md`): 모드 분기, 기대값 계약, 5단계 TDD 루프, 단계 점검표, 금지 규칙.
- References: [테스트 채택 기준](references/choosing-a-test.ko.md)이 채택 기준, 민감도 점검, 구체 사례를 다룹니다.
- Assets: [평가 사례](assets/evals/hyper-tdd-cases.jsonl)가 트리거와 실행 경계 시나리오를 담습니다.

</skill_architecture>

<loop_policy>

사이클마다 구별할 결함 하나만 고릅니다. 요청한 동작 중 기존 테스트가 놓치는 결함이 남았을 때만 1∼5단계를 반복합니다. 동작 단언이 아니라 설정·모듈 로드·시간 초과로 실패하면 설정을 먼저 고치거나 실제 막는 요인을 보고합니다.

</loop_policy>

<language_and_translation_default>

테스트 코드 내부는 저장소의 언어와 명명 관례를 따르고, 결과 보고는 한국어로 작성합니다.

</language_and_translation_default>

<reference_routing>

사례를 추가하거나 고치기 전에 2단계 앞에서 [테스트 채택 기준](references/choosing-a-test.ko.md)을 읽고, 3단계 첫 실행이 예상과 달리 통과하면 가이드의 사후 검증 민감도 절차를 대조합니다.

</reference_routing>

<support_file_read_order>

1. 대상 저장소의 요청 계약, 가까운 호출자, 기존 테스트.
2. 후보를 채택·생략하기 전에 읽는 [테스트 채택 기준](references/choosing-a-test.ko.md).
3. 이 스킬 패키지를 유지보수할 때만 보는 [평가 사례](assets/evals/hyper-tdd-cases.jsonl).

</support_file_read_order>

<workflow>

**재개 절차**: 1단계 전에 `git status --porcelain`, `git diff`, `.hyper/workflow/` 상태나 작업 트리의 미커밋 테스트 파일을 먼저 확인합니다. 이전 턴에서 작성한 실패 테스트나 부분 구현이 있으면 집중 테스트 명령을 먼저 실행해 현재 Red/Green 상태를 읽고, 중복 테스트를 만들지 말고 해당 단계부터 재개합니다. 단계 전환마다 `[현재 단계: k/5 ...]` 배너를 출력합니다.

| 단계 | 수행 작업 | 끝 조건 | 건너뛰면 안 되는 이유 |
|---|---|---|---|
| 1 | 계약 문장("입력·상태가 주어지면 호출자가 X를 본다")과 독립된 기대값 출처를 확정한다 | 계약 한 문장, 모드(`test-first` / `tests-only` / `advice-only`), 기대값 출처가 명시됨 | 현재 코드 출력을 기대값으로 베끼면 버그를 그대로 고정함 |
| 2 | 기존 테스트·호출자를 확인하고 결함이 드러나는 가장 좁은 계층에서 추가·확장·재사용·생략을 결정한다 | 잡을 현실적 오동작과 `references/choosing-a-test.ko.md` 기준 결정이 기록됨 | 기존 검사를 안 보면 아무것도 안 지키는 중복 테스트가 늘어남 |
| 3 | 운영 코드 수정 전에 대상 테스트를 실행해 동작 단언 Red를 포착한다(기존 정상 동작 테스트면 사후 검증 표시 후 민감도 확인) | 테스트가 수집되어 목표 동작 단언에서 실패함(임포트·픽스처·0건 수집 오류 제외) | 대상 결함에서 실패해 본 적 없는 테스트는 검출력을 증명하지 못함 |
| 4 | `test-first`는 계약을 만족하는 최소 수정을 적용해 Green을 확인한다(`tests-only`는 재현된 결함을 Red로 보존) | 같은 명령·기대값으로 통과하거나 `tests-only` Red 재현이 유지됨 | 계약 밖 수정이나 단언 완화는 회귀를 숨김 |
| 5 | Green을 유지한 채 중복을 정리하고 단독 재실행 및 프로젝트 필수 검사를 돌린 뒤 한국어로 보고한다 | 영향받은 테스트와 필수 게이트가 통과(또는 실행기 부재 명시)하고 사례별 증거가 보고됨 | 검증 없는 리팩터나 공유 상태 오염이 이웃 테스트를 깨뜨림 |

### 단계 점검표

| # | 예/아니오 질문 | 위반 시 되돌아갈 단계 |
|---|---|---|
| 1 | 기대값이 현재 구현 출력을 베낀 값이 아니라 독립된 근거에서 나왔는가? (예/아니오) | 1단계 |
| 2 | 기존 테스트를 먼저 대조해 새로 추가·확장한 사례마다 구별되는 현실적 결함을 잡는가? (예/아니오) | 2단계 |
| 3 | 실행기가 테스트를 수집해 동작 단언에서 실패했는가(사후 검증이면 민감도 확인을 마쳤는가)? (예/아니오) | 3단계 |
| 4 | `tests-only`에서 운영 파일을 건드리지 않았고, `test-first`에서 단언 완화나 검사 대상 모킹 없이 통과했는가? (예/아니오) | 4단계 |
| 5 | 무관한 사용자 변경을 보존한 채 영향받은 테스트와 필수 게이트를 다시 실행했는가? (예/아니오) | 5단계 |

</workflow>

<required>

- 작업 트리에 있던 무관한 사용자 변경을 그대로 보존합니다.
- 유지한 모든 사례에 호출자가 겪을 오류와 독립된 기대값 출처를 밝힙니다.
- 실제로 관찰한 Red/Green 명령과 출력을 기록하고 실행할 수 없었던 검사는 한계를 명시합니다.

</required>

<forbidden>

- 실제 출력을 `expect(...)`에 복사하거나 단언을 완화하거나 스냅샷을 무작정 갱신하거나 테스트를 건너뛰거나 검사 대상 자체를 대역(mock)으로 바꿔 통과시키는 일.
- 오직 테스트만을 위해 운영 코드에 내보내기(export), 분기, 초기화 훅을 추가하는 일.
- 집중 TDD 작업을 요청받지 않은 스위트 전체 테스트 삭제나 git 커밋으로 넓히는 일.
- 나쁜 예: 코드를 먼저 실행해 나온 반환값을 그대로 `toEqual(...)`에 붙여 넣고 테스트 완료로 보고함 -> 좋은 예: 1단계에서 요구사항이나 호출자 계약으로 기대값을 먼저 확정한 뒤 단언을 실행함.
- 나쁜 예: `SyntaxError`, 임포트 실패, `0 tests collected`를 Red 증거로 인정하고 구현을 고침 -> 좋은 예: 3단계에서 테스트가 정상 수집되어 목표 동작 단언에서 실패할 때까지 테스트 준비를 먼저 바로잡음.
- 나쁜 예: 내부 비공개 함수를 억지로 export하거나 검사 대상 함수 자체를 모킹해 단위 테스트를 만듦 -> 좋은 예: 실제 공개 호출 진입점을 통과시키고 외부 경계에서만 대역을 사용함.

</forbidden>

<validation>

- [ ] 유지한 사례가 의도한 호출자 동작과 현실적인 회귀 결함을 구별합니다.
- [ ] 기대 결과의 근거가 구현과 독립적이며 동작을 보존하는 내부 리팩터링에 깨지지 않습니다.
- [ ] 추가·확장한 사례마다 서로 다른 위험을 다루고 단독 실행되며 공유 상태를 깨끗이 정리합니다.
- [ ] 테스트만을 위한 운영 코드 내보내기, 분기, 초기화 함수를 하나도 추가하지 않았습니다.
- [ ] 실행한 명령과 실제 Red/Green 결과(또는 실행기 부재·`tests-only` 실패 상태)를 한국어로 보고했습니다.

</validation>
