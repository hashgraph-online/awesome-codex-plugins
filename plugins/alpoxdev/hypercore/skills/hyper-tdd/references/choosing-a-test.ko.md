# 테스트 채택 기준

## 작성 전 판단

| 후보 | 판단 |
|---|---|
| 이름을 바꾼 파일이 옛 경로에 없는지 검사합니다. | 생략합니다. 예전 클라이언트에 특정 응답을 보장한다면 그 호환 동작을 검사합니다. |
| 버튼이 클릭 이벤트를 내거나 타입이 문자열이거나 대역이 설정값을 반환하는지 검사합니다. | 생략합니다. 저장 버튼이라면 기록을 다시 열어 값을 확인합니다. 외부에서 받은 JSON이라면 실제 파서가 약속대로 잘못된 값을 거부하는지 확인합니다. |
| 비공개 도우미 호출, 내부 상태, 콜백 호출 순서를 검사합니다. | 관찰 가능한 결과로 고칩니다. 외부 알림을 정확히 한 번만 보내는 것이 계약이라면 발송 경계에서 전달 건수를 셉니다. |
| 예외가 없었다는 사실만 확인합니다. | 약속한 결과나 효과를 단언합니다. 특정 입력을 거부해야 한다면 문서에 명시된 실패와 그때 일어나지 말아야 할 부수 효과를 확인합니다. |
| 같은 경계에서 같은 결함을 잡는 기존 검사가 있습니다. | 재사용합니다. 같은 줄을 실행해도 잡는 오류는 다를 수 있습니다. 다시 열었을 때 저장값이 사라지는 경우처럼 다른 위험이 있을 때만 별도 계층에서 검사합니다. |
| 커버리지를 올리거나 살아남은 변이를 잡는 것만이 작성 이유입니다. | 사용자가 차이를 볼 수 있는 입력을 찾습니다. 허용된 입력에서 결과가 같다면 생략합니다. |

수정 범위의 기존 테스트가 제품 계약과 구현 세부를 함께 검사한다면 계약을 유지하고 구현에 묶인 단언을 뺍니다. 구현 수정도 허용됐고 마지막 사용처를 없앨 때만 테스트 전용 운영 코드까지 정리합니다. 테스트만 요청했다면 남은 전용 코드는 보고합니다.

## 입력과 기대값

**결함을 드러낼 입력**과 **정답 판정 기준**을 따로 정합니다. 문서의 예, 직접 검산한 결과, 도메인 규칙에서 기대값을 구합니다. 입력이 결함 조건에 도달하는지와 단언이 오동작을 구별하는지 모두 확인합니다. 모델의 추측, 현재 출력으로 다시 만든 스냅샷, 검사 대상을 다시 호출해 얻은 값은 정답의 근거가 될 수 없습니다.

입력이 많다면 잘못된 구현에서 깨질 수 있는 속성을 고릅니다. 정렬 결과는 순서가 맞고 입력 원소와 각 원소의 개수도 보존해야 합니다. 순서만 검사하면 빈 목록만 돌려주는 구현도 통과합니다. 입력 생성 조건이 단언을 저절로 참으로 만들지 않는지 확인합니다. 실행기가 지원하면 재현할 수 있는 반례를 남깁니다.

## 경계값 사례

예시 계약에서는 소계가 5000 이상이면 배송료를 면제하고 나머지 주문에는 300을 더합니다. 계약과 같은 금액 단위로 결제 총액을 검사합니다.

| 소계 | 기대 총액 | 잡아내는 오류 |
|---:|---:|---|
| 5000 | 5000 | 초과 조건을 쓰면 5300을 청구합니다. |
| 4999 | 5299 | 모두 무료로 처리하면 4999를 청구합니다. |

입력값별 결제 테스트에 두 번째 행이 있다면 첫 번째 행만 추가합니다. 초과 조건을 사용한 구현에서 기대값 5000과 실제값 5300의 차이를 관찰합니다. 구현 수정이 허용되면 비교 조건을 고쳐 두 행을 다시 실행합니다. 이후 배송료 계산을 다른 함수로 분리해도 두 기대값은 유지됩니다.

이미 올바른 코드에서 첫 실행이 통과하면 추가 증거가 필요할 때 폐기 가능한 사본에서 알려진 결함 버전이나 되돌릴 수 있는 현실적인 오류 하나를 사용합니다. 같은 단언이 실패하는지 확인하고 사본을 폐기한 뒤 원래 코드에서 통과를 확인합니다. 테스트만 요청했다면 원래 운영 코드는 그대로 둡니다. 안전하게 비교할 수 없다면 처음부터 통과했고 결함 검출력은 확인하지 못했다고 밝힙니다. 관찰하지 않은 실패를 기록하지 않습니다.

## 격리와 실패 원인 판별

확인하려는 동작을 보존하면서 빠르고 결과가 일정하면 실제 협력 객체를 사용합니다. 외부 경계는 로컬 대역, 제어할 수 있는 시계, 격리된 저장소나 발송 기록을 사용합니다. 데이터베이스 자체의 동작을 확인하려면 프로젝트가 지원하는 테스트 데이터베이스를 사용합니다. 실결제, 운영 서비스, 테스트 간 실행 순서, 고정 시간 대기, 재현할 수 없는 난수에 의존하지 않습니다. 완료 신호나 제한 시간이 있는 조건을 기다리고 실패하더라도 자원을 정리합니다.

AI가 작성한 테스트가 실패하면 대상 수집, 초기 설정, 결함을 드러낼 입력, 기대값, 실제 구현 순서로 확인합니다. 오류 메시지는 잘못된 픽스처나 누락된 모듈을 알려줄 수 있습니다. 제품 규칙 변경의 근거로 쓰지는 않습니다. Meta는 빌드·안정적 통과·커버리지 증가로 후보를 추렸고 TestPilot은 커버리지를 측정했습니다. TOGA 재평가는 생성한 단언에서 오탐을 확인했습니다. 각 연구가 측정한 성질이 다르므로 개별 테스트는 제품 계약에 비춰 판단합니다.
