# Hypotheses And Escalation

첫 가설 묶음을 쓰기 전에, 그리고 라운드가 두 번 실패했을 때 다시 이 파일을 읽는다.

## 1. One Hypothesis Is A Hunch

가설이 하나면 모든 관찰이 확증이 된다. 조사자는 이미 믿는 것을 코드에서 찾고, 모순되는 증거는 깎아내리고, 그럴듯한 첫 스택 프레임에서 멈춘다.

가설이 둘이면 결정이 강제된다. 다음 probe를 하나를 지지하는 쪽이 아니라 둘을 가르는 쪽으로 고르게 되기 때문이다. 세 번째가 정말 다른 축이면 셋이 낫다. 표현만 바꾼 가설로 수를 채우는 것은 진짜 둘보다 나쁘다.

## 2. Orthogonal Axes

같은 축에서 뽑은 가설은 하나의 짐작을 변주한 것이다. 축을 가로질러 흩어 놓아야 한쪽 probe가 다른 쪽도 함께 움직이지 않는다.

| Axis | Framing |
|---|---|
| 사용자 코드 로직 | 있어서는 안 되는 분기가 실행된다. 이른 반환, off-by-one, 잘못된 상수, 뒤집힌 조건 |
| 라이브러리·의존성 동작 | 클라이언트가 오류를 삼키고, 내부에서 재시도하고, 기본값을 돌려주고, 낡은 값을 캐시한다 |
| 환경과 설정 | 변수를 채우기 전에 읽고, 설정 파일이 실제 로드되는 파일이 아니고, 쓰는 지점에서 비밀이 비어 있다 |
| 비동기와 타이밍 | 응답을 보낸 뒤에 rejection이 도착하고, 콜백이 두 번 돌고, 프로세스가 끝나면서 작업이 버려진다 |
| 공유 상태 | 앞 단계가 바꾼 상태를 지금 단계가 물려받는다. 싱글턴, 캐시, 전역이 실행 사이에 초기화되지 않는다 |
| 관측 공백 | 오류가 올라오지만 로그 전에 억제된다. 실패가 무시된 반환값으로만 존재한다 |
| 빌드와 런타임 | 읽는 코드가 도는 코드가 아니다. 낡은 빌드 산출물, 다른 진입점, 심볼릭 링크된 바이너리, 캐시된 wheel |
| 데이터 모양 | 도착한 입력이 코드가 가정한 입력이 아니다. null과 없는 키, 문자열과 숫자, 빈 배열과 없는 필드 |

묶음마다 최소 두 축을 고르고, 가설마다 축을 적는다.

## 3. What Each Hypothesis Must State

가설마다 네 줄을 모두 일지에 쓴다.

1. **주장** — "Y 때문에 X가 일어난다" 형태의 한 문장.
2. **구분 관찰** — 확정하거나 반박할 정확한 값, 상태, 출력과 그것을 읽을 위치(`path:line`, 명령, 로그 출처, 포트).
3. **예측** — 주장이 참일 때 그 관찰이 어떻게 보이고, 거짓일 때 어떻게 보이는지. 참과 거짓의 예측이 같은 가설은 시험할 수 없다.
4. **참이면 수정은** — 두세 단어. 추적을 시작하기 전에 수정 비용을 눈앞에 두게 한다.

## 4. The Collapse Rule

- 두 가설이 같은 관찰에 같은 결과로 갈린다면, 그것은 옷만 바꾼 하나의 가설이다. 합치고 정말 다른 대안을 찾는다.
- 다른 관찰을 예측하는 두 번째 가설을 세우지 못한다면, 아직 시스템을 충분히 이해하지 못한 것이다. probe를 돌리기 전에 코드, 로그, 테스트를 더 읽는다. 첫 짐작만 확증하는 probe를 돌리지 않는다.
- 가진 접근으로는 반증할 수 없는 가설은 그렇다고 밝히고 버린다. 영구적인 "아마도"로 남기지 않는다.

## 5. A Round

라운드는 열린 가설 묶음에 대한 한 번의 통과다.

1. 한 번에 가장 많은 가설을 가르는 probe를 고른다.
2. 실패가 아직 보이는 가장 작은 준비에서 한 번 실행한다.
3. 값을 출처와 함께 그대로 기록한다.
4. 가설마다 확정, 반박, 여전히 열림 중 하나로 표시한다.

열린 가설이 모두 증거를 얻었거나, 쓸 수 있는 증거 출처가 바닥났을 때 라운드가 끝난다. 바닥난 라운드는 카운터에 실패한 라운드다.

같은 질문에 답하는 probe를 두 번 돌리지 않는다. 반복한 probe는 새 라운드도 아니고 증거도 아니다.

## 6. Three-Way Reframe After Two Failed Rounds

실패한 라운드가 두 번 연속되면 실제 원인은 지금 틀 안에 없는 범주에 있을 가능성이 크다. 같은 정신 모델 안에서 시간을 더 쓰는 것은 낭비다. 문제를 세 방향으로 재구성하고 셋 다 일지에 기록한다.

| Framing | 답할 질문 |
|---|---|
| 보이는데 놓친 것 | 모든 관찰과 양립하는, 민망할 만큼 단순한 원인은 무엇인가. 잘못된 import, 잘못된 상수, 낡은 캐시, 잘못된 파일, harness와 앱, 소스와 빌드 산출물 |
| 시스템 경계 | 어느 컴포넌트 사이의 경계가 깨졌는가. SDK 동작, 미들웨어, 게이트웨이 재작성, 빌드 시점과 런타임 환경, 모듈 로드 순서, 버전 불일치, 전송 |
| 짊어진 가정 | 지금 모든 가설이 의존하는 가정은 무엇이고, 그것을 반증할 가장 작은 질의는 무엇인가 |

그다음:

- 두 방향 이상에서 나온 후보를 적는다. 직교하는 틀에서 독립적으로 겹치면 쓸 수 있는 가장 강한 신호다.
- 각 불일치를 다음 라운드의 probe로 바꾼다.
- 세 번째 틀의 반증 질의를 적힌 그대로 다음 라운드로 가져온다.
- 합의와 불일치 양쪽에서 뽑아 최소 두 개의 새 가설 묶음을 만든다.
- 실패 라운드 카운터를 0으로 되돌린다.

예산은 재구성 한 번이다. 그 뒤 두 라운드가 더 실패하면 최선 가설, 그 `Assumption:` 줄, 판정에 필요한 정확한 점검을 붙여 `unconfirmed`로 끝낸다. 루프를 빠져나오려고 수정을 짐작하지 않는다.

## 7. Escalate Only For Access

라운드 횟수는 문제를 되돌려줄 이유가 아니다. 다음 단계에 세션이 줄 수 없는 것이 필요할 때만 올린다. credential, 장치, production 로그, 사용자만 일으킬 수 있는 재현이다. 구체적인 질문 하나를 하고 실행을 `awaiting_input`으로 표시하며, 일지에 이미 있는 나머지는 그대로 둔다.
