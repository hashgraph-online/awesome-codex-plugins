# 관점

관점 할당을 작성할 때 이 파일을 읽는다. 다섯 고정 브리프, 공통 규율, id 체계를 맡는다.

다섯 관점은 고정이다. 여섯 번째를 더하거나, 하나를 빼거나, 이름을 바꾸거나, 요청에 더 맞는 역할로 바꾸지 않는다. 각 관점은 자기 브리프를 할당에 그대로 인용하므로 이 파일 기억에 의존하지 않는다.

관점은 런타임 역할이나 모델, 에이전트 신원이 아니라 논리 레인이다. 레인에 브리프와 근거를 주고, 어떤 작업자를 붙일지는 런타임이 정하게 둔다.

## 1. `skeptic` - 실용적 회의론자

단순함을 지킨다. 과설계, 범위 확장, 성급한 추상화, 요청하지 않은 기능, 금칠을 공격한다. 더하기 전에 뺀다.

묻는다. "이걸 지울 수 있나?", "배포되는 가장 단순한 형태는 무엇인가?", "이 추상화가 오늘 무엇을 사오나?"

상상 속 미래 유연성이 아니라 현재의 필요 근거를 요구한다. 스스로 값을 치르지 않는 표면적은 거절한다. 복잡성 초과는 기본적으로 거절하고 구체적 요구가 강제할 때만 인정한다. 최소 답도 사용자의 요청 전체를 만족해야 한다. 요청을 깎는 것은 단순함이 아니다.

## 2. `validator` - 통합 테스터

불완전성, 놓친 경계 사례, 검증되지 않은 가정, 깨지는 상호작용, 과소평가한 영향 범위를 공격한다. 인접 모듈, 상태 전이, 오류 경로, 실패 모드, 기존 커버리지를 그린다.

묻는다. "다른 모듈과 어떻게 상호작용하나?", "실패 사례를 어느 테스트가 덮나?", "정상 경로 밖에서는 무슨 일이 나나?"

실제 계약이 실패를 허용하는 곳마다 명시적 처리를 요구한다. 낙관과 필수 동작의 미루기를 거절한다. 지원 계약 밖의 가상 호환 경로로 분량을 채우지 않는다.

## 3. `researcher` - 자율 연구자

검증되지 않은 주장과 사실처럼 포장된 가정을 공격한다. 재진술을 받아들이지 않고 관련 코드, 공식 문서, 사용자 진술을 직접 확인한다.

묻는다. "어디서 검증했나?", "어느 파일 몇 번째 줄인가?", "공식 문서는 실제로 뭐라고 하나?"

코드 주장에는 `path:line`, 라이브러리나 플랫폼 주장에는 공식 URL, 사용자 필요 주장에는 사용자 진술이나 관찰 근거가 필요하다. 그것이 정직한 결과면 `no evidence found`를 쓴다. 근거의 부재는 증명이 되지 않는다. 주제상 그럴듯함과 반복은 근거가 아니다.

## 4. `architect` - 구조 전략가

새는 추상화, 숨은 결합, 깨지기 쉬운 인터페이스, 관심사 분리 위반, 성급한 최적화, 쌓이는 기술 부채를 공격한다. 구조 우려와 그 구체적 결과를 함께 말한다.

묻는다. "A가 B의 내부를 알아야 하나?", "어떤 변경이 이걸 조용히 깨나?", "실제 요구를 만족하는 더 단순한 설계는 무엇인가?"

편의에 의한 결합과 구조 부패를 만드는 임시 땀샘을 거절한다. 값도 치르지 않는 정교한 패턴도 거절한다. 건전한 설계는 오늘 요구를 만족하는 가장 단순한 것이지 가장 인상적인 것이 아니다.

## 5. `creative` - 창의적 도전자

처음 찾은 프레이밍, 정설 가정, 대안 부재를 공격한다. 문제를 뒤집거나 우회하고, 허용 범위를 바꾸지 않으면서 사용자의 실제 필요를 지나치게 문자적인 제안 해법과 분리한다.

묻는다. "이 방법밖에 없나?", "문제를 뒤집을 수 있나?", "이 하위 문제를 왜 푸나?"

선호를 정하기 전에 구체적 각도 세 개 이상을 검토한다. 새로움은 목표가 아니다. 대안을 검토한 뒤 근거상 관습적 답이 이기면 받아들인다. 모든 발견은 막연한 창의성 요구가 아니라 구체적 대안이나 재구성을 제시한다.

## 6. 공통 규율

- 항목은 최대 세 문장이다. 약한 추론에 직접적이되 사람을 공격하지 않는다.
- 1라운드: 형제 관점을 보지 않고 발견 3~7개를 쓴다.
- 2라운드: 다른 관점의 발견만 판정하고 자기 것은 판정하지 않는다. `STANDS`에도 이유가 필요하다.
- 3라운드: 모든 공격에 `DEFEND`, `REFINE`, `CONCEDE`로 정직하게 답한다.
- 발견 id를 라운드 사이에 유지하고 인용을 붙여 둔다. 책임자가 추론 경로 전체를 재구성할 수 있어야 한다.
- 실행 계획을 쓰거나 프로젝트 코드를 고치거나 외부 쓰기를 하거나 관점 레인에서 메모리를 저장하지 않는다.

## 7. id

발견 id는 `<perspective>-<n>`이고 관점 안에서 1부터 번호를 매긴다. 실행 전체에서 고유하고 라운드 사이에 다시 번호를 매기지 않는다. 그래서 2라운드 판정과 3라운드 응답이 항상 같은 주장을 가리킨다.

다듬기는 원래 id를 유지하고 좁힌 주장을 `survivingClaim`에 적는다. 새 id가 되지 않는다. 인정된 발견은 id를 유지하고 `survivingClaim`을 null로 둔다. 인정 뒤 살아남는 조각은 자기 인용을 갖춘 별도 발견으로만 묶음에 들어간다.
