# 라운드

1라운드를 보내기 전과 매 라운드 경계에서 이 파일을 읽는다. 웨이브 규율, 절차 수준의 세 라운드 계약, 순차 대체, 원장을 맡는다.

## 1. 1라운드 전 근거 수집

어떤 관점도 돌기 전에 요청을 원장에 다시 적는다.

- 사용자 요청 원문
- 사용자가 밝힌 범위와 제약
- 계획이 만들어야 하는 관찰 가능한 결과
- 이 스킬을 선택한 적대적 선택 문구
- slug와 영수증 디렉터리 `.hyper/debate/<slug>/`

그다음 읽기 전용으로 근거를 모은다. 근거를 받지 못한 관점은 근거를 지어내므로, 책임자가 가장 작은 유용한 근거 집합을 먼저 모은다. 요청이 지목한 파일, 그것을 제약하는 스키마나 설정, 사용자가 밝힌 제약이 대상이다. 모은 경로는 원장의 `grounding`에 적는다.

근거 수집은 계획이 아니다. 접근을 정하지 않고, 작업 순서를 잡지 않고, 계획의 할 일을 미리 쓰지 않는다.

## 2. 웨이브 규율

한 라운드는 관점 작업 다섯 개의 웨이브 하나다.

1. 런타임이 병렬 하위 에이전트를 지원하면 다섯 개를 한꺼번에 보낸다. 각 작업은 공유 요청, 근거, 자기 관점 브리프, 라운드 계약, 발견 id 접두사를 갖는다.
2. 반환된 모든 작업 식별자를 관점, 라운드, 시도 번호와 함께 처리 전에 원장에 적는다.
3. 웨이브의 대기 집합이 비고 다섯 영수증이 모두 유효할 때만 넘어간다. 미리보기, 일부 메시지, 아직 실행 중인 스냅숏은 완료된 영수증이 아니다.
4. 관점의 논리 이름은 전송 주소가 아니다. 실행 중인 작업은 런타임이 돌려준 식별자로만 지목한다.
5. 아직 실행 중인 작업의 대체를 시작하지 않는다. 침묵과 경과 시간은 실패가 아니다.
6. 레인은 작업이 무효로 끝나거나 실패한 뒤에만, 정확한 실패 문맥을 실어 한 번 대체한다. 같은 레인의 두 번째 실패는 실행을 `blocked`로 끝낸다.

책임자는 영수증 본문만 보고 판정하지 않는다. 형식, 커버리지, 인용, 식별자를 따로 검증한다.

## 3. 1라운드: 독립 발견

각 관점은 근거를 읽고 발견 3~7개를 낸다. 어떤 관점도 다른 관점의 발견을 보지 않는다.

발견은 다음을 갖는다.

- 실행 전체에서 고유한 안정적 id. 관점 접두사를 붙인다(`skeptic-1`, `validator-3`).
- 주장 하나. 최대 세 문장이다.
- 인용 하나 이상. `path:line`, 공식 URL, 사용자 진술, 또는 명시적 `no evidence found`다.

인용 없이 위험만 말하는 발견은 거절하고 같은 관점에 고쳐 보내게 한다. 인용 있는 발견 세 개를 만들 수 없는 관점은 근거를 대지 못한 항목에 `no evidence found`를 붙여 그보다 적게 보고하고, 책임자는 분량을 채우지 않고 부족을 기록한다.

1라운드는 종합, 계획, 순위를 만들지 않는다.

## 4. 2라운드: 교차 공격

1라운드 발견을 id, 관점, 인용과 함께 묶는다. 동일한 묶음을 다섯 관점 모두에 준다.

각 관점은 나머지 네 관점의 모든 발견을 판정하고 자기 것은 판정하지 않는다.

- `ATTACK` - 발견이 틀렸거나, 근거가 없거나, 범위를 넘거나, 결론이 따라오지 않는다. 이유에 결함과 그것을 보여주는 근거를 적는다.
- `STANDS` - 이 관점의 검토를 견딘다. 그래도 이유는 필요하다. 이유 없는 `STANDS`는 빈 판정이라 거절한다.

검증은 스키마 점검이 아니라 커버리지 점검이다. 다른 관점의 발견이 정확히 한 번씩 나오고, 알 수 없는 대상 id가 없고, 어떤 관점도 자기를 판정하지 않는다. 책임자는 공격을 약화하지 않고 넘기며 일찍 종합하지 않는다.

## 5. 순차 대체

런타임이 병렬 하위 에이전트 capability를 노출하지 않으면 다섯 관점을 책임자 문맥에서 하나씩 돌린다.

대체 경로도 세 라운드, 영수증 형식, id, 인용을 유지한다. 잃는 것은 독립성이다. 같은 문맥이 다섯 관점을 쓰므로, 책임자의 읽기에서 생긴 맹점이 다섯을 모두 통과할 수 있다. 보고에 정확히 그렇게 적는다.

대체 규칙:

- 다음 관점을 시작하기 전에 각 관점의 영수증을 별도 파일로 써서 분리가 감사 가능하게 남게 한다.
- 같은 발견 id 접두사와 같은 커버리지 요구를 유지한다.
- 2라운드에서 묶인 발견을 기억이 아니라 디스크에서 읽고, 다른 관점의 발견마다 판정 하나를 낸다.
- 원장에 `execution: sequential`과 `reduced: true`를 이유와 함께 적는다.
- 종료 상태는 `planned`가 아니라 `reduced-planned`가 된다.
- 다섯 독립 관점, 관점 간 발견, 완전한 병렬 토론을 했다고 주장하지 않는다.

대체는 범위 축소가 아니다. 모든 관점이 돌고, 모든 라운드가 끝나고, 승인 지점도 그대로다.

## 6. 3라운드: 방어, 다듬기, 인정

2라운드 판정을 대상 발견별로 묶는다. 각 관점에 자기 발견과 그에 대한 모든 판정만 주고, 공격자 신원을 붙인다.

각 관점은 자기 발견마다 응답 하나를 낸다.

- `DEFEND` - 모든 공격을 구체적 근거로 반박하고 주장을 유지한다. 근거는 필수다.
- `REFINE` - 살아남는 더 강하고 좁은 주장을 밝히고, 무엇이 바뀌었는지 적고, 좁힌 주장을 뒷받침하는 근거를 인용한다. 다듬은 주장은 새 주장이므로 자기 인용을 갖는다.
- `CONCEDE` - 주장이 틀렸거나 근거가 없다. 생존 주장이 없다.

관점은 발견에 대한 모든 공격을 다뤄야 하고, 쉬운 것만 다루면 안 된다. 답하지 않은 공격은 미해결로 기록하고 그 발견은 방어된 것으로 세지 않는다.

## 7. 책임자의 독립 판정

`DEFEND`는 이해관계자의 주장이지 증명이 아니다. 방어되거나 다듬어진 발견마다 책임자가 인용된 근거를 다시 읽고 정한다.

- 인용이 생존 주장을 실제로 뒷받침하면 유지한다.
- 인용이 주장보다 약하면 열린 질문으로 내린다.
- 인용이 주장을 전혀 뒷받침하지 않으면 버린다.

결정과 이유를 발견별로 원장에 적는다. 책임자는 관점이 자신 있게 말했다는 이유로 주장을 유지하지 않는다.

## 8. 원장

`.hyper/debate/<slug>/ledger.json`은 실행의 지속 기록이다. 다음을 담는다.

- `request` - 사용자 요청 원문과 인용한 선택 문구
- `slug`, `mode`, `execution`(`parallel` 또는 `sequential`), `reduced`(불리언), `reducedReason`
- `grounding` - 1라운드 전에 읽은 경로와 명령
- `waves` - 라운드별 관점 id, 작업 식별자, 시도 번호, 영수증 경로
- `findings` - 모든 발견의 id, 관점, 주장, 인용, 2라운드 판정, 3라운드 응답, 책임자의 유지/다듬기/버리기 결정
- `surviving`과 `dropped` - 관점별 수
- `openQuestions` - 근거가 해소하지 못한 모든 이견
- `approval` - 요청, 시각, 결정 원문
- `terminal` - `planned`, `awaiting-approval`, `reduced-planned`, `declined`, `blocked` 중 하나
- `notes` - capability 공백, 대체한 레인, 부족분

각 항목은 정해지는 즉시 적는다. 다음 턴이나 압축된 문맥은 기억이 아니라 이 파일에서 재개한다.
