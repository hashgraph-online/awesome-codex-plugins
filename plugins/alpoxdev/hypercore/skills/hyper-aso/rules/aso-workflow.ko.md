# ASO 워크플로

**목적**: App Store와 Google Play 최적화 실행의 단계별 수행 규칙.

## 1. 범위 단계

무엇이든 수집하기 전에 감사 대상을 확정한다.

- 앱 식별자: 표시 이름, Apple ID 또는 번들 ID, Android 패키지명, 공개 스토어 URL. 모든 URL이 같은 앱으로 연결되는지 확인한다. 다른 개발자의 동명 앱이 흔한 혼동 원인이다.
- 스토어: `app_store`, `google_play`, 또는 둘 다. `one_store`는 사용자가 이름을 대었을 때만 추가한다.
- 앱 상태: `pre-launch`(setup 모드), `live`, `relaunch`.
- 로캘과 스토어프런트: 앱이 제공하는 메타데이터 로캘과 사용자가 신경 쓰는 스토어프런트. 스토어별 주 언어를 기록한다.
- 초점: 전체 감사, 또는 표면 하나(키워드, 크리에이티브, 평점, 현지화).
- 경쟁사 집합: 비교를 요청받았을 때 스토어별로 이름이 지정된 앱 최대 5개. 선택 근거를 밝히지 않고 경쟁사 목록을 만들지 않는다.

출력: 이 필드를 담은 범위 블록. `report.md`에 쓰고, complex 모드에서는 `flow.json`의 `scope` 단계에 쓴다.

## 2. 측정 단계

점수화 전에 어떤 채널이 있는지 기록한다.

| 채널 | 증거 등급 | 전형적인 내용 |
|---|---|---|
| Apple·Google 공식 문서와 정책 | `official` | 필드 한도, 에셋 규격, 정책 문구, 지표 정의 |
| 브라우저에서 관측한 공개 스토어 페이지 | `live` | 현재 제목, 부제 또는 짧은 설명, 스크린샷, 평점, 리뷰 수, 카테고리 |
| 소유자의 App Store Connect나 Play Console 내보내기 | `console` | 노출 수, 제품 페이지 조회 수, 스토어 등록정보 방문자, 전환율 또는 클릭률(CTR), 유입원, 실험, 바이탈 |
| 서드파티 ASO 도구 | `tool` | 키워드 인기도나 검색량 추정치, 난이도, 순위 이력, 경쟁사 키워드 |
| AI 비서 프로브 | `synthetic` | 이름이 지정된 비서가 프롬프트 집합에 대해 앱을 언급하는지 |
| 실무자 안내나 패키지 판단 | `heuristic` | 문구 품질, 스크린샷 스토리텔링, 키워드 선택 |

- 스토어 페이지는 스토어프런트, 기기, 로그인 상태에 따라 달라질 수 있다. 모든 `live` 판독에 스토어프런트와 기기를 기록한다.
- 콘솔 지표는 정의가 바뀐다(`references/metrics.md` 참고). 정의가 바뀐 지점을 넘어 수치를 비교하지 않는다.
- 채널이 없으면 능력 한계와 대체 방법을 `results.json.measurement_methods`에 기록하고, 의존하는 카테고리를 `unknown`으로 표시한다.

## 3. 메타데이터와 키워드 단계

스토어와 로캘별로:

- 검색 대상이거나 노출되는 모든 텍스트 필드를 현재 값과 스토어 자체 단위의 길이(Apple 키워드 필드: 바이트, 그 밖의 필드: 글자)와 함께 읽는다. 한도는 `references/policy-limits.md`에서 읽는다.
- 스토어가 검색 입력으로 문서화한 필드를 매핑한다(`rules/apple.md` §1, `rules/google-play.md` §1). 검색 입력으로 문서화되지 않은 필드는 전환 관점에서만 판단하고 순위 입력으로 점수화하지 않는다.
- 키워드 집합을 `references/keyword-research.md`로 만들거나 검토한다. 관련성, 이름이 지정된 출처의 인기도와 난이도, 배치 순서로 판단한다.
- 필드 간 반복, 낭비된 글자, 서술어 없이 브랜드만 있는 제목, 정책 위험 단어를 점검한다(`rules/apple.md` §5, `rules/google-play.md` §5).
- 주 카테고리(그리고 Apple의 보조 카테고리)가 앱의 주 기능과 맞는지 점검한다.

## 4. 크리에이티브와 전환 단계

- `rules/listing-assets.md`로 아이콘, 스크린샷, 미리보기나 프로모션 영상, 피처 그래픽을 평가한다.
- 사용 중인 전환 도구를 조사한다. Apple 맞춤 제품 페이지, Product Page Optimization, In-App Events, 프로모션 인앱 구매, Google Play 맞춤 스토어 등록정보, Store Listing Experiments, 프로모션 콘텐츠, 사전 등록. 무엇이 있고 무엇이 라이브이며 그 결과를 읽을 수 있는지 기록한다.
- 진행 중이거나 끝난 실험은 스토어 자체 결과 상태만 읽는다. 스토어가 우승으로 표시할 때만 변형이 우승이다.

## 5. 평점, 리뷰, 품질 단계

- 스토어와 스토어프런트별로 노출되는 평균 평점과 평점 수를 읽는다. 둘 다 변하므로 날짜를 기록한다.
- 평점 요청 구현을 스토어 API 한도와 정책에 맞춰 점검한다(`rules/apple.md` §4, `rules/google-play.md` §4). 조건부 게이팅, 보상, 불만 사용자를 걸러내는 자체 사전 프롬프트가 없어야 한다.
- 리뷰 응답을 점검한다. 최근 비판적 리뷰에 대한 응답률, 어조, 앱이 하지 않는 일을 약속하는 답변 여부.
- Google Play: 소유자가 제공하면 Android vitals를 읽고 `references/policy-limits.md`의 나쁜 동작 임계값과 비교한다. Apple: 소유자 내보내기가 있으면 크래시와 크기 데이터를 읽는다. 데이터가 없으면 `unknown`이다.
- 앱 크기: 관측 가능하면 다운로드와 설치 크기를 기록한다. 크기 증가는 전환 위험이며 순위 규칙이 아니다.

## 6. 정책 위험과 웹 링크 단계

- 정책 위험: 스토어 메타데이터 정책과 충돌하는 메타데이터나 그래픽 요소를 정책 조항과 함께 모두 나열한다. 이는 발견 가능성과 거절 위험 플래그이며 규정 준수 판정이 아니다.
- 웹-앱 연결: Apple App Site Association 파일, Android `assetlinks.json`, Smart App Banner 태그, 스토어 배지 링크, 맞춤 페이지 딥링크를 `references/web-and-ai-surfaces.md`로 점검한다. 무엇을 가져왔고 HTTP 상태가 무엇인지 기록한다.
- AI 비서 표면: 요청받았을 때 `references/web-and-ai-surfaces.md` §3의 유한하고 날짜가 붙은 프롬프트 집합을 실행하고 `synthetic`으로 기록한다.

## 7. 점수, 리포트, 산출물

- 측정한 카테고리만 `SKILL.md` `<scoring>`의 가중치로 점수화하고, `unknown`과 `not-applicable`은 `score: null`로 기록한다.
- 기대 영향, 확신도, 노력, 새 앱 버전 필요 여부로 우선순위를 정한다. Apple의 이름, 부제, 키워드, 스크린샷, 아이콘은 보통 버전을 타고, 프로모션 텍스트는 타지 않으며, Google Play 등록정보 텍스트는 릴리스 없이 바뀐다. `references/policy-limits.md`를 참고한다.
- `results.json`을 쓰고 `assets/runtime/check-results.jq`를 실행하고 `results.js`를 만들고 대시보드를 복사한 뒤 `report.md`와 `sources.md`를 쓴다(`references/artifact-spec.md`).
- 제안 문구: 스토어, 로캘, 필드별로 블록 하나. 센 길이와 한도를 함께 적는다.

## 8. setup 모드(출시 전)

앱이 아직 라이브가 아니고 산출물이 점수가 아니라 세팅 계획일 때 쓴다. 다음 단계를 순서대로 따르고 모든 항목을 `done`, 소유자가 붙은 `planned`, `not-applicable`, 빠진 접근 권한을 밝힌 `unknown` 중 하나로 기록한다.

1. **포지셔닝과 키워드**: 핵심 용도, 대상 로캘과 스토어프런트, 출처가 붙은 시드 키워드 목록, 어떤 용어를 어느 필드에 넣을지.
2. **메타데이터 초안**: 이름, 부제 또는 짧은 설명, 키워드 필드, 설명, 프로모션 텍스트, What's New, 카테고리. 각각 센 길이를 붙인다.
3. **크리에이티브**: 아이콘, 필수 기기 클래스별 스크린샷 세트, 미리보기나 프로모션 영상, 피처 그래픽, 검색 결과용으로 계획한 첫인상 프레임.
4. **현지화**: 스토어프런트별 메타데이터 로캘, 추가 로캘 색인 계획(`rules/localization.md`).
5. **평점 계획**: 인앱 평점 요청이 뜨는 시점, 리뷰 응답 절차, 답변을 맡는 소유자.
6. **링크와 측정**: AASA와 `assetlinks.json`, Smart App Banner, 캠페인 파라미터가 붙은 스토어 배지 링크, App Analytics와 Play Console 접근, 첫 주에 기록할 기준선 지표.
7. **첫 30일**: 첫 실험(Product Page Optimization 또는 Store Listing Experiment), 첫 맞춤 페이지나 등록정보, 첫 이벤트나 프로모션 콘텐츠, 크래시와 ANR 데이터 검토.

콘솔 제출, 계정 설정, 라이브 등록정보 편집은 정확한 값으로 준비해 두고, 사용자가 콘솔에서 조작할 권한을 주지 않는 한 소유자에게 남긴다.

## 9. optimize 모드

사용자가 도달 가능한 최고의 등록정보나 반복 개선을 요청할 때 실행한다. 유한하게 한다.

1. **기준선과 예산 먼저**: 카테고리 점수, 전체 등급, critical 발견사항 수, 목표, 예산(기본 3회), 가드를 `decision: "baseline"`과 함께 `results.json.score_history[0]`에 기록한다.
2. **안정적인 평가자**: 스토어, 로캘, 비교 가능한 앱 집합, 루브릭 버전, 증거 채널을 그대로 유지한다. 변경이 있으면 `decision: "reset"`으로 기록하고 그 지점을 넘어 델타를 보고하지 않는다.
3. **반복당 변경 하나**: 필드 하나 다시 쓰기, 스크린샷 세트 하나 변경, 실험 계획 하나.
4. **증거로 인정되는 것**: 같은 표면의 재감사, 또는 스토어가 스스로 결론을 낸 스토어 실험. 미해결 실험을 기다리는 반복은 `report.md`에서 `pending`이며 `kept`로 `score_history`에 들어가지 않는다.
5. **가드와 폐기**: 비교 가능한 카테고리가 개선되고 어떤 카테고리도 회귀하지 않으며 정책 위험이 증가하지 않을 때만 반복을 유지하고, 그렇지 않으면 `discarded`로 기록한다. `best_run`은 유지된 반복이나 기준선 중 점수가 가장 높은 것이다.
6. **중단 게이트**: 목표 달성, 예산 소진, 정체, 가드 실패, 소유자 전용 단계(콘솔 접근, 제출, 사업 판단), 사용자 중단. 사유를 기록한다.

점수를 조작하지 않고, 순위·추천·설치 증가를 약속하지 않는다.

## 10. 모드 규칙

- **Create**: 범위에 잡힌 스토어와 로캘에 대해 모든 단계를 순서대로 수행한다.
- **Update**: 기존 `report.md`와 `results.json`을 먼저 읽고, 변경됐거나 새로 요청된 표면만 재평가하며, 날짜가 붙은 변경 기록을 덧붙이고, 대체되지 않은 이전 발견사항을 유지한다.
- **Setup**: §8을 따른다. 초안에 대한 점수화 감사도 요청받았을 때만 `results.json`과 대시보드를 추가한다.
- **Optimize**: create나 update 감사에서 시작해 §9를 수행한다.
