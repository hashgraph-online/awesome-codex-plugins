# Interpretation Gate

> 근거가 뒷받침하는 해석을 골라 바로 실행하고, 잘못 짐작했을 때 비용이 클 때만 묻고, 직접 수정으로 감당할 수 없는 것은 넘긴다.

## 1. Outcome and Reading

수정 전에 항목마다 두 줄을 쓴다.

- **원하는 결과**: 작성자가 자기 사용자에게 이루려는 것을 한 문장으로 쓴다. 제안된 해결책("버튼을 빨간색으로")은 작성자가 고집할 때만 제약으로 두고, 그렇지 않으면 결과("눈에 띄게")를 이루는 후보 중 하나로 본다.
- **수용 확인**: 변경 후 누구나 관찰할 수 있는 확인 하나. 렌더링된 문자열, 도달 가능한 컨트롤, 반환값, 변경 전에는 실패했을 테스트 같은 것이다.

해석은 아래 근거 사다리를 올라가며 고르고, 결정되는 첫 단계에서 멈춘다.

1. 요청 자체의 말과 작성자가 밝힌 제약.
2. 저장소에 이미 기록된 제품 결정: 명세, `DESIGN.md`, `AGENTS.md`, ADR, 코드에서 링크한 이슈 본문.
3. 저장소의 관례: 디자인 토큰, 문구 스타일, 컴포넌트 패턴, 이름 짓기.
4. 제품의 다른 곳에서 같은 종류의 문제를 푸는 가장 가까운 기존 패턴.
5. 결과를 이루는 가장 작고 되돌릴 수 있는 변경. 가정으로 표시한다.

항목마다 결정한 단계를 기록한다. 5단계에서 결정됐으면 보고서의 가정 목록에 올린다.

## 2. When to Ask

저장소를 확인한 뒤, 다음 세 사유 중 하나일 때만 묻는다.

1. **해석이 크게 갈림**: 두 해석이 사용자에게 다른 결과를 만들고, 사다리의 어떤 단계도 둘을 가르지 못하며, 잘못 고르면 항목 대부분을 다시 해야 한다.
2. **되돌릴 수 없거나 외부로 나가는 효과**: 데이터 삭제, 파괴적 마이그레이션, 가격·법률·계약 문구·권한·결제 동작 변경, 저장소 밖으로 무엇이든 보내는 일.
3. **충돌**: 두 항목이 서로 모순되거나, 항목이 저장소에 기록된 제품 결정과 모순된다.

묻는 방법:

- 한 번에 결정 하나를, 사용자의 언어로, 권장안과 그 이유를 붙여 묻는다.

```text
[결정] <정할 것>
[영향] <선택마다 무엇이 바뀌는지>
[선택지] A: ... (추천) / B: ...
```

- 그 항목만 `awaiting_input`으로 표시하고 다른 항목은 먼저 끝낸다.
- 사다리로 답이 나오는 질문, 저장소 관례를 따르는 이름·파일 위치·스타일 질문, "혹시 몰라서" 하는 질문은 허용하지 않는다.

## 3. Direct-Edit Budget

다음을 모두 만족하면 항목을 바로 수정한다.

- 기존 모듈만 바꾸고 새 라우트, 모듈, 패키지, 서비스 경계를 만들지 않는다
- 스키마 변경, 데이터 마이그레이션, backfill이 필요 없다
- 공개 API 계약을 깨지 않고 의존성을 추가하거나 올리지 않는다
- 인증, 권한, 결제, 과금 로직을 바꾸지 않는다(그 주변 문구는 괜찮다)
- 단계적 배포가 필요한 시스템 간 순서 의존이 없다

한 줄이라도 만족하지 않으면 그 항목은 `handoff`다. 계획 단계가 요청을 다시 읽지 않고 쓸 수 있도록 `.hyper/feedback/<slug>/brief.md`에 기록한다.

```markdown
# <title>

- 원문: "<verbatim quote>" (출처: <author / relay>)
- 원하는 결과: <outcome>
- 수용 기준: <observable checks>
- 예산 초과 사유: <the budget line that failed>
- 확인한 위치: `path:line` - <what it does now>
- 변경 지도 초안: <surface rows from the checklist, with known locations>
- 가정·미확인: <open points>
```

예산 안의 항목은 같은 실행에서 그대로 반영한다. handoff 항목이 있어도 다른 항목을 붙잡지 않는다.

## 4. Wording and Constraints

- 작성자가 최종 사용자에게 보일 문구로 쓴 텍스트는 띄어쓰기와 문장부호까지 글자 그대로 반영한다. 저장소의 문구 규칙과 충돌하면 그대로 반영한 뒤 어긴 규칙을 보고서에 적는다.
- 작성자가 밝힌 제약("나머지는 그대로")은 수용 확인의 일부다. 잔여 검색으로 유지할 부분이 바뀌지 않았음을 확인한다.
