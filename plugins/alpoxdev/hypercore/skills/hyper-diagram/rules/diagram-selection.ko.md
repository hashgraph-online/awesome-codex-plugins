# 다이어그램 선택

영어판: [diagram-selection.md](diagram-selection.md)

무엇을 그릴지 정하기 전에 이 규칙 파일을 사용합니다. 구조에서 타입을 고르는 기준, 나누는 기준, 모든 spec이 따르는 내용·표현 규칙을 담습니다.

## 1. Structure → Type

독자가 무엇을 알고 싶은지 묻고, 맞는 첫 줄을 고릅니다.

| 독자의 질문 | 구조 | 타입 |
|---|---|---|
| 어떤 부분이 있고 어떻게 이어지나? | 구성 요소, 서비스, 경계 | `architecture` |
| 다음에 무엇이 일어나고 어디서 갈라지나? | 단계, 분기, 반복 | `flowchart` |
| 데이터가 어디로 가고 무엇이 바꾸나? | 출처, 변환, 도착지 | `dataflow` |
| 누가 누구를 어떤 순서로 부르나? | 참여자, 순서 있는 메시지 | `sequence` |
| 어떤 상태가 있고 무엇이 옮기나? | 상태, 전이 | `state` |
| 어떤 테이블이 있고 어떻게 엮이나? | 엔터티, 키, 관계 수 | `erd` |
| 어떤 타입이 있고 어떻게 의존하나? | 클래스, 인터페이스, 멤버 | `class` |
| 무엇이 무엇을 담나(부모는 하나)? | 엄격한 계층 | `tree` |
| 한 주제에서 어떤 생각이 뻗나? | 방사형 정리 | `mindmap` |
| 언제 무슨 일이 있었나? | 날짜 순 사건 | `timeline` |
| 각 작업이 얼마나 걸리고 무엇을 기다리나? | 날짜가 있는 작업, 선후 관계 | `gantt` |
| 어떤 계층이 어떤 계층 위에 있나? | 구성원이 있는 층 | `layers` |

Tie-breaks:

- 사용자가 타입을 지정하면 그 타입을 씁니다. 그 타입으로 구조를 그릴 수 없으면 그 이유를 말하고 맞는 타입을 씁니다.
- 분기가 있는 처리는 `flowchart`, 서비스가 서비스를 부르는 처리가 대부분이면 `sequence`입니다.
- 서로 이어지는 선이 있는 포함 관계는 `tree`가 아니라 그룹이 있는 `architecture`입니다.
- Mermaid 입력은 스타일이 아니라 의미를 가져옵니다: `flowchart`/`graph` → `flowchart`(구성 요소 지도면 `architecture`), `sequenceDiagram` → `sequence`, `stateDiagram` → `state`, `erDiagram` → `erd`, `classDiagram` → `class`, `gantt` → `gantt`, `mindmap` → `mindmap`, `timeline` → `timeline`.

## 2. Size And Split

- 요소는 5-25개를 목표로 합니다. 노드가 약 40개를 넘거나 시퀀스 참여자가 9명을 넘으면 전체 다이어그램과 영역마다 상세 다이어그램을 하나씩 그리고, 각각 spec과 파일을 따로 둡니다.
- 다이어그램 하나는 질문 하나에 답합니다. 두 번째 질문은 두 번째 다이어그램이 됩니다.
- 답을 바꾸지 않는 요소는 뺍니다. 같은 인스턴스가 반복되면 노드 하나로 합치고 `sub`에 개수를 적습니다("워커 ×4").

## 3. Content Rules

- `title`: 대상과 관점을 명사구로 씁니다("결제 서비스 아키텍처"). "다이어그램"만 쓰지 않습니다.
- `subtitle`: 범위와 기준 시점을 씁니다("범위: 주문 생성부터 정산까지 · 기준 2026-11-08").
- `label`: 팀이 쓰는 짧은 이름이며 제품·코드 이름은 쓴 그대로 둡니다. `sub`: 역할, 기술, 포트 중 하나를 적습니다.
- 간선 `label`: 무엇이 오가는지 말하는 동사나 프로토콜을 씁니다("토큰 검증", "SQL", "정산 이벤트"). "사용", "연결", "호출"만 쓰지 않습니다. 양 끝만 봐도 뜻이 분명할 때만 라벨을 비웁니다.
- `kind`는 취향이 아니라 의미입니다. 노드가 실제로 무엇인지에 맞는 종류를 써야 범례가 맞게 읽힙니다. 주 경로 하나에만 `primary`를 쓰고, `async`, `auth`, `data`, `error`, `return`, `deploy`는 간선이 실제로 그것일 때만 씁니다.
- `description`: 두세 문장으로 주 경로를 말로 따라가고, 추정한 요소를 모두 밝힙니다("인증 서버의 위치는 설정 파일에 없어 추정했습니다").
- 한국어 표현은 사용자의 언어 규칙을 따릅니다. 평서문으로 쓰고 군더더기를 넣지 않습니다.

## 4. Evidence

- 저장소에서 그릴 때는 각 요소를 증명하는 파일(진입점, 설정, compose, 스키마, 라우트)을 먼저 읽습니다.
- 증거가 없는 요소는 빼면 그림이 오해를 부를 때만 그리고, `description`에 추정이라고 밝힙니다.
