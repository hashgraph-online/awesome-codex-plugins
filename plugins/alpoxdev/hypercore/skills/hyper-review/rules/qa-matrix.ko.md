# QA 매트릭스

리더 레인이다. 리뷰어는 코드를 읽고, 리더는 실행한다. 행 하나는 기준 하나를 실제 표면에서 실행한 것이고, 실제 관찰이 없는 행은 증거가 아니다.

## 1. Find the real surface

아무것도 실행하기 전에 프로젝트 자체의 매니페스트와 설정을 읽고 명령을 적는다.

- 무엇이 빌드하고, 실행하고, 테스트하는가. `package.json` 스크립트, `Makefile`, `pyproject.toml`, `Cargo.toml`, `go.mod`, `justfile`, `bin/`이나 `scripts/` 폴더, CI 워크플로 파일.
- 수동 확인을 위해 어떻게 띄우는가. 개발 서버, CLI 바이너리, 라이브러리 진입점, 큐 소비자.
- 어떤 상태가 필요한가. 데이터베이스, 픽스처, 시드 명령, 가짜 외부 서비스.
- 변경이 무엇을 건드리는가. 네트워크 호출, 파일 형식, 마이그레이션, 권한 경계, 사용자 화면.

직접 만든 명령보다 프로젝트가 선언한 명령을 먼저 쓴다. CI에서 가져온 명령이 손으로 조립한 것보다 좋은 증거다. 변경이 영향을 주는 일에 프로젝트가 명령을 두지 않았으면 그렇게 밝히고 가장 가까운 실제 표면을 실행한다.

## 2. Matrix columns

모든 행에 이 열이 다 있다. 빠진 열이 있으면 불완전한 행이다.

| Column | Content |
|---|---|
| 기준 | 그 행이 확인하는 것, 한 줄 |
| 시나리오 | 정확한 입력, 사용자 행동, 명령. 어색한 부분까지 포함한다 |
| 기대 | 무엇이 일어나야 하는가. 실행 전에 목표나 제약에서 이끌어 쓴다 |
| 관찰 | 원본 결과. 상태 코드, 본문, 종료 코드, 출력 줄, 스크린샷 경로, 오류 문자열 |
| 판정 | `pass`, `fail`, `unproven`, `N/A` |
| 산출물 | 경로, 보고서에 출력을 담은 명령, 또는 스크린샷 파일 |
| 정체성 | 그 행을 실행한 내용 정체성 |
| 정리 | 무엇을 만들었고 무엇을 지웠는가 |

`기대`를 `관찰`보다 먼저 쓴다. 나중에 채우면 행이 그냥 일어난 일의 설명이 된다.

## 3. Criterion rows

해당되면 아래 행을 반드시 덮고, 변경이 만든 목표별 기준마다 행을 하나 더한다. 행을 더하지, 아래 행을 빼지 않는다.

| Row | 확인하는 것 |
|---|---|
| 목표 | 목표가 말하는 주 경로가 끝까지 동작한다 |
| 바뀐 경로 | diff가 건드린 특정 분기, 엔드포인트, 플래그, 컴포넌트가 목표대로 동작한다 |
| 정상 입력 | 장난감이 아닌 현실적인 입력 |
| 비었거나 없는 입력 | 아무것도 주지 않음, 빈 컬렉션, 빠진 선택 필드 |
| 경계 | 여기서 의미 있는 최솟값, 최댓값, 오프바이원 값 |
| 잘못된 형식 | 잘못된 타입, 잘린 값, 잘못된 인코딩, 예상 밖 필드, 허용 집합 밖 값 |
| 실패 경로 | 의존성이 실패하거나, 오류를 반환하거나, 시간 초과하거나, 닿지 않는다 |
| 동시성·반복 | 호출자 둘이 동시에, 같은 요청을 두 번, 재시도된 작업 |
| 권한·인가 | 권한 없는 호출자가 거절되고, 거절이 데이터를 흘리지 않는다 |
| 기존 동작 | 바뀌면 안 되는 이전 동작이 여전히 동작한다 |
| 테스트 | 프로젝트 테스트 명령이 돌고, 새 테스트가 실제로 변경을 건드린다 |
| 빌드·정적 검사 | 프로젝트가 선언한 빌드, 타입 검사, 린트 |

마지막 두 행은 덤이 아니라 게이트다. 테스트가 돌지 않거나 선언한 빌드가 실패하는 변경은 `passed`가 아니다.

## 4. Raw observation

- 실제 출력을 인용한다. 가운데만 줄이고 머리와 실패 꼬리는 남기며, 어디서 잘랐는지 적는다.
- 모든 명령 옆에 종료 코드를 적는다.
- 렌더링 화면은 스크린샷을 저장하고 뷰포트, 테마, 입력 방식을 적는다.
- API는 상태 줄, 관련 헤더, 본문을 남긴다. 읽지 않은 본문을 요약하지 않는다.
- 시간이나 메모리 주장은 측정 방법, 실행 횟수, 편차를 적는다. 한 번 잰 숫자를 값인 것처럼 쓰지 않는다.
- "잘 된다"고 쓰지 않는다. 무엇을 보냈고 무엇이 돌아왔는지 쓴다.

## 5. `N/A` and `unproven`

`N/A`는 이 목표와 이 변경에 묶인 이유가 있을 때만 허용한다.

- 좋은 예: "동시성 행: `N/A`. 이 변경은 가져오기 시점에 쓰이는 상수 이름만 바꾸며, 공유 가변 상태를 더하거나 건드리지 않고, 바뀐 모듈에 요청 경로가 없다."
- 나쁜 예: "동시성: `N/A`, 해당 없음."
- 나쁜 예: "실패 경로: `N/A`, 작성자가 테스트했다." 작성자의 주장은 면제 사유가 아니다.

`unproven`은 행이 적용되지만 실행할 수 없었을 때의 정직한 결과다. 빠진 기능, 실패한 정확한 명령, 무엇이면 확정되는지를 적는다. 필수 행이 `unproven`으로 남으면 판정은 `passed`가 아니라 `inconclusive`다.

## 6. Cleanup

상태를 만든 행은 무엇을 만들었는지 적는다. 임시 파일, 데이터베이스 행, 백그라운드 프로세스, 큐 메시지, 컨테이너, 브랜치.

- 지우고, 지우는 명령과 종료 코드를 적는다.
- 확인을 위해 띄운 프로세스는 멈추고, 잡은 포트는 푼다.
- 지우지 못한 상태는 보고서와 마무리 요약에 경로나 식별자와 함께 적는다.
- 마이그레이션한 데이터베이스, 시드한 테이블, 실행 중인 서버를 조용히 남기지 않는다.

## 7. Depth by risk

변경이 깨뜨릴 수 있는 것에 비례해 노력을 맞춘다.

| 위험 | 예 | 깊이 |
|---|---|---|
| 낮음 | 상수, 메시지 문구, 동작 변화 없는 내부 이름 변경 | 목표 행, 기존 동작, 빌드와 테스트 |
| 중간 | 기존 로직의 새 분기, 검증 규칙, 쿼리 변경 | 낮음 집합에 정상·빈·경계·잘못된 형식 입력 |
| 높음 | 인가, 결제나 금액, 데이터 삭제, 마이그레이션, 공개 인터페이스, 동시성, 비밀·개인정보를 만드는 모든 것 | 전체 표. 실패, 동시성, 권한 행을 추론이 아니라 실행으로 |

위험 수준은 매트릭스 옆에 적어, 읽는 사람이 판정이 얼마나 많은 근거에 기대는지 볼 수 있게 한다.
