# 범위와 정체성

어떤 확인보다 먼저 이 파일을 읽는다. 무엇을 판정했는지 이름 붙이지 않은 리뷰는 나중에 신뢰할 수 없고, 범위를 추측한 리뷰는 다른 변경을 통과시킬 수 있다.

## 1. Resolve the target

요청을 대상 블록 하나로 바꾼다. 보고서 맨 위에 기록한다.

| Kind | 베이스를 확인하는 방법 | 검토 대상 내용 |
|---|---|---|
| 작업 트리 | 저장소 기본 브랜치, 또는 요청이 지목한 병합 베이스 | 스테이징한 변경과 스테이징하지 않은 변경, 그리고 변경에 속하는 추적되지 않은 파일 |
| 이름 붙은 diff, 커밋 범위 | 사용자가 지목한 범위 그대로 | 범위 안의 모든 커밋 |
| 브랜치 | 브랜치 업스트림 또는 저장소 기본 브랜치 | 병합 베이스부터 브랜치 끝까지 |
| 끌어오기 요청 | 끌어오기 요청의 베이스 브랜치 | 베이스 위에 끌어오기 요청이 더한 커밋 |

규칙:

- 저장소 기본 브랜치를 `git symbolic-ref --short refs/remotes/origin/HEAD`로 확인하고, 없으면 `main`, 그다음 `master`를 쓴다. 가정하지 않는다.
- 브랜치나 끌어오기 요청에는 베이스 브랜치 끝이 아니라 병합 베이스를 쓴다. 베이스에 들어온 무관한 커밋이 변경의 일부로 검토되지 않게 한다.
- 바뀐 경로를 그것을 만든 명령과 함께 적는다. 예를 들어 `git diff --name-status <base>...<target>`.
- 추적되지 않은 파일은 작업 트리 리뷰의 일부다. 프로젝트의 무시 규칙으로 빌드 산출물과 캐시를 변경에 속한 파일과 나눈다.
- 서로 무관한 변경 여러 개, 저장소 전체, 또는 아무것도 지목하지 않은 요청은 대상이 아니다. 어느 변경인지 한 번 묻고 `awaiting_input`으로 멈춘다.
- diff를 깨끗하게 만들려고 트리를 정리하지 않고, 리뷰하려고 stash, reset, 다른 브랜치 체크아웃을 하지 않는다.

## 2. Recover the goal and the constraints

루브릭 첫 두 항목은 비교할 목표가 필요하다. 요청, 그다음 이슈나 끌어오기 요청 설명, 계획이나 명세, 커밋 메시지 순서로 모은다.

- 목표를 낯선 사람이 확인할 수 있는 한 문장으로 쓴다.
- 명시된 제약을 모두 적는다. 호환성 약속, 성능 상한, 이름 규칙, 바뀌면 안 되는 인터페이스, 되돌릴 수 있어야 하는 마이그레이션.
- 작성자의 주장과 사용자가 확인한 사실을 구분해 표시한다. 주장은 확인할 대상이지 요구 사항이 아니다.
- 어디에도 목표가 없으면 그렇게 밝히고, 변경이 스스로 밝힌 의도를 `goal inferred`로 표시해 목표로 쓴다. 추론한 목표는 신뢰도를 낮추지만 실행을 막지는 않는다.

## 3. Compute the content identity

첫 확인 전에 한 줄을 기록한다.

```sh
git rev-parse HEAD
git diff --binary HEAD | shasum -a 256
git ls-files --others --exclude-standard -z | xargs -0 shasum -a 256 2>/dev/null | shasum -a 256
git ls-files --others --exclude-standard | wc -l
```

보고서의 줄은 이렇다.

```text
Identity: HEAD <sha> | diff sha256:<hex> | untracked sha256:<hex> (n files) | base <ref>
```

참고:

- 추적되지 않은 파일의 다이제스트를 경로와 함께 이어 붙이고 `git ls-files`가 나열하는 순서로 정렬해 해시한다. 그래야 두 파일이 내용을 맞바꿔도 같은 정체성이 나오지 않는다.
- diff 다이제스트는 `HEAD` 대비 스테이징·비스테이징 추적 변경을 덮는다. 추적되지 않은 내용은 두 번째 다이제스트가 덮는다.
- 커밋 범위에는 작업 diff 대신 범위 패치를 해시하고 그 사실을 줄에 적는다. `diff sha256:<hex> (range <a>..<b>)`.
- 다이제스트 명령을 쓸 수 없으면 정확한 이유를 적고 `HEAD`와 바뀐 경로 목록에 의존한다. 정체성이 약하다고 밝힌다.

## 4. Staleness

판정은 커밋 id도 브랜치 이름도 아닌 정체성에 속한다.

- 판정을 쓰기 직전에 정체성을 다시 계산한다. 매트릭스를 만든 줄과 다르면 영향받은 행이 낡은 것이다.
- 새 변경이 건드리는 행만 다시 돌리고, 새 정체성으로 판정을 다시 낸다.
- 저장된 보고서의 정체성이 현재 내용과 다르면 `stale`이다. 두 정체성과 움직인 경로를 적는다.
- 리베이스, 스쿼시, 브랜치 강제 갱신, 헤드가 움직인 끌어오기 요청 뒤로 판정을 넘기지 않는다. 메시지가 같아도 검토한 내용이 바뀌었다.
- `failed` 판정을 뒤집으려고 일부러 두 번째 리뷰를 돌리는 것은 허용하지 않는다. 허용되는 교체는 [verdicts.md](verdicts.md)의 단일 리뷰다.

## 5. Reportable gaps

기능이 없으면 보고서에 어느 행에 영향을 주는지, 무엇이면 확정되는지 적는다. 흔한 경우:

| 공백 | 행 결과 |
|---|---|
| 렌더링 화면을 볼 브라우저나 드라이버가 없다 | `unproven`, 실제로 돈 정적 확인은 따로 적는다 |
| 자격 증명이 없거나 서비스가 떠 있지 않다 | `unproven`, 정확한 명령과 그 오류 |
| 변경이 겨냥한 하드웨어가 없다 | `unproven`, 대상을 적는다 |
| 리뷰어 레인을 위한 서브에이전트 기능이 없다 | `review: self`, 전체 루브릭은 그대로 적용 |
| 막힌 네트워크 호출이 필요한 테스트 | `unproven`, 막힌 호스트를 적는다 |

공백은 `N/A`가 되지 않는다. `N/A`는 그 기준이 이 목표에 적용되지 않는다는 뜻이고, 그 목표에 맞춘 이유가 붙는다.

### Evidence grade

정체성 결속은 `MECHANISM`이다. 줄 형식, 추적되지 않은 파일 다이제스트 구성, 공백 표는 `LOCAL`이다. 정체성 줄은 검증된 최적값이 아니라 고른 설계다.
