# 그래프 계획

노드를 정의하기 전과 모든 `amend` 전에 이 규칙을 읽습니다. 이 규칙 없이 정의한 그래프는 검증 없는 몇 개의 거대한 노드로 무너집니다. 이 문서의 각 절은 그 실패에 이미 이름이 붙어 있기 때문에 존재합니다.

계획은 노드를 쓰는 일이 아닙니다. 리더는 선별, 목표, justification, 토폴로지를 한 번에 적고 그 계획을 실행합니다. 현실이 바꾸게 하면 리더는 소리 내어 다시 계획하고, 노드 하나씩 흔들리는 대신 `amend`를 기록합니다.

## 1. 먼저 선별

그래프는 위임의 기본 형태가 아닙니다. 계획 전에 판단합니다.

| 조건 | 판정 |
|---|---|
| 두 개 이상의 작업이고 어떤 작업이 다른 작업보다 먼저 끝나야 함 | 그래프 |
| fan-out 결과를 하나의 검토나 검증으로 합쳐야 함 | 그래프 |
| 작업이 독립적이고 순서가 없음 | 그래프 없음, 단순 병렬 subagent |
| 작업이 하나이거나, 전체 문제를 한눈에 봐야 하는 일관된 판단 | 직접 실행 |
| 모든 작업자가 같은 넓은 문맥을 필요로 하거나 하위 작업이 서로 강하게 얽힘 | 한 에이전트, fan-out 없음 |
| 결과물이 작성된 계획 파일을 체크박스 순서대로 실행하는 것 | 범위 밖 |
| 결과물이 조사 리포트 | 범위 밖 |
| 작업이 여러 단계나 체크포인트에 걸침 | 단계마다 실행 하나, 리더가 연결 |

그래프가 없애는 병목을 밝힙니다. 문맥 고갈, 직렬 지연, 격리 부재, 자기 채점 가운데 무엇인지 정합니다. 이 가운데 아무것도 없애지 못하는 그래프는 장식이며, 정직한 행동은 작업을 직접 실행하는 것입니다.

## 2. 시작 전 목표

모든 실행은 목표에 묶입니다.

- 목표는 그래프가 만드는 산출물을 한 문장으로 지목합니다.
- 각 성공 기준은 그것을 증명할 근거를 지목합니다. 명령과 기대 결과, 파일과 그 안에 있어야 할 내용, 또는 엔드포인트와 관찰 가능한 응답입니다.
- 실행은 마지막 노드가 보고할 때가 아니라 기준이 캡처한 근거와 함께 통과할 때 끝납니다.
- 바깥 실행 루프가 이미 목표를 소유하고 있으면 두 번째 목표를 등록하지 않습니다. 실행은 그 목표와 근거를 물려받습니다.
- 사용자만 결정할 수 있는 사항은 그것에 의존하는 실행이 시작되기 전에 묻습니다. 되돌리기 어렵거나 파괴적인 변경, 비용 지출, 자격 증명이나 계정 접근, 외부 전송이나 게시가 여기에 해당합니다. 시간 초과, 무시, 추정한 답은 답이 아닙니다. 한 번에 질문 하나만 하고 권장안을 붙입니다.

## 3. 실행당 한 단계

단계는 루프가 체크포인트로 삼는 단위입니다. 목표 기준 하나, worktree 하나, 근거 게이트 하나, 계획 wave 하나가 단계입니다. 수확 wave나 파이프라인 스테이지는 단계이고, "조사하고, 구현하고, 배포한다"는 세 단계이자 세 실행입니다.

- 첫 실행의 검증 출력이 두 번째 실행을 시작할지 결정하는 입력입니다.
- 각 실행은 자기 key, 목표, 기준, 그래프, journal을 가집니다.
- 실행을 잇는 일은 정산 사이에서 리더가 합니다. 그래프 자체에는 분기 구조가 없습니다.

## 4. Justification 기록

`run.created` 전에 `graph.json` 안의 justification 객체를 씁니다. 여섯 필드가 모두 필요하고, 하나라도 비어 있으면 self-check가 시작을 거부합니다.

| 필드 | 내용 |
|---|---|
| `ceiling_removed` | 그래프가 없애는 병목, 또는 그래프를 쓰는 비용을 정당화하는 이유 |
| `topology` | 1-6개 컴포넌트와 노드가 각 컴포넌트에 어떻게 대응하는지 |
| `state` | 노드 사이에 그래프가 나르는 것(handoff 파일, 저장소 상태)과 의도적으로 나르지 않는 것 |
| `bounds` | 적용되는 상한. 기본값을 덮는 사용자 상한 포함 |
| `approval` | 되돌리기 어려운 작업이나 사용자만 결정할 수 있는 작업을 가진 노드, 그리고 그 답이나 `not required` |
| `rollback` | 결과가 기준을 통과하지 못할 때 실행을 되돌리는 방법. 되돌릴 경로, worktree 폐기, 파일을 건드리지 않음 |

이 기록은 "왜 이것이 그래프이고, 무엇이 안전하게 실행되게 하는가"에 대한 답입니다. 채팅의 산문이 아니라 정의의 일부입니다.

## 5. 토폴로지 고정

노드를 쓰기 전에 각각 독립적으로 성공하거나 실패할 수 있는 최상위 컴포넌트 1-6개를 나열합니다. 모든 노드는 정확히 한 컴포넌트에 대응합니다.

- "작아 보인다"는 이유로 여러 컴포넌트짜리 요청을 하나의 덩어리 노드로 합치지 않습니다.
- 요청에 없는 컴포넌트를 만들지 않습니다.
- 요청에 컴포넌트가 여섯 개를 넘으면 단계가 섞인 것입니다. 먼저 단계로 나눕니다.

## 6. 먼저 나누고, 나중에 배정

기본 질문은 "이 덩어리에 어떤 tier가 필요한가"가 아니라 "이 덩어리를 어떻게 더 많은 `low` 노드로 바꾸는가"입니다.

다음일 때 나눕니다.

- 조각이 독립적이고 동시에 실행해도 안전함
- 쓰기 범위가 겹치지 않음
- 각 조각에 자기 완결적인 prompt와 스스로 통과 여부를 정하는 확인이 있음

다음일 때 나누지 않습니다.

- 조각이 풀 수 없게 얽힌 쓰기 범위를 공유함. 직렬화하거나 합칩니다.
- 전체 문제를 한눈에 봐야 하는 일관된 판단임. 나누면 확신에 찬 부분 답만 나옵니다.
- 조각이 너무 작아서 설명 비용이 작업보다 큼. 이웃 노드에 합칩니다.

실제 의존이 있는 노드 두 개짜리 그래프는 정당합니다. 노드가 세 개 미만이고 실제 의존도 없으면 그래프가 아닙니다. 단순 병렬이나 직접 실행을 씁니다.

## 7. Tier와 전문 kind

Tier는 중요도가 아니라 난이도입니다.

| Tier | 용도 |
|---|---|
| `low` | 기본값. 기계적이거나 단일 파일이거나 패턴을 따르는 작업 |
| `medium` | 통합 표면이 실제로 있는 표준 다중 파일 변경 |
| `high` | 전체 문제의 문맥을 잃지 않고는 나눌 수 없는 하나의 어려운 문제 |

- `low`가 아닌 모든 tier에는 소리 내어 말할 수 있는 한 줄 이유가 붙습니다("세 패키지에 걸쳐 파일 여섯 개를 건드림").
- 그래프당 `high` 노드는 최대 하나이고, 나머지 그래프가 그 판단에 의존할 때만 씁니다.
- 모든 노드가 `high`인 그래프는 라우팅 실패입니다. 기계적인 레인에 가장 비싼 작업자를 쓰는 것입니다.

`kind`는 난이도가 아니라 작업의 종류로 고릅니다. 문서와 산문은 `writing`, UI와 스타일은 `visual`, 저장소 작업은 `git`입니다. 전문 종류가 필요 없는 노드는 `kind`를 생략합니다.

## 8. 구현과 그 증명은 함께

한 노드가 산출물 하나를 처음부터 끝까지 소유합니다. 변경과 그것을 증명하는 확인이 함께 있습니다. 쓰기만 하는 노드와 테스트만 하는 노드는 같은 파일에서 직렬화되고 조정 비용을 두 배로 만듭니다.

예외는 종단 검증 노드입니다. 자기 작업이 아니라 그래프 전체를 채점하기 때문에 분리합니다.

## 9. Fan-out 후 하나의 검토를 거쳐 Fan-in

기본 형태는 병렬 생산 노드 N개와, 그 모두에 의존해 join을 만드는 노드 하나입니다.

- 다음 wave의 모든 노드가 이전 wave의 모든 노드에 의존해야 하면 전체 엣지 격자를 그리지 않습니다. wave 사이에 검토 노드 하나를 넣습니다.
- wave의 일부만 소비하는 노드는 그 분기에 자체 검토를 두고, 전체 wave가 아니라 그 분기가 끝날 때 시작합니다.
- join은 출력 형태를 선언합니다. 쓰는 파일, 반환하는 표, 기록하는 판정 가운데 하나입니다. "전부 합치기"는 형태가 아닙니다.
- 대량 수확은 항목을 보고서 계약에 맞춘 배치 노드로 나눕니다. 각 노드는 정해진 배치를 모아 정해진 크기의 파일 보고서 하나를 씁니다. 노드 수는 `ceil(전체 항목 / 배치 항목)`이고, 종합은 배치 보고서를 읽으며 노드의 날 출력을 읽지 않습니다. 한 실행의 상한을 넘으면 각자 aggregator를 가진 동시 실행으로 나눕니다.

## 9.1 배치 노드 위의 Digest 축약

배치 하나를 넘는 노드를 합치는 reducer는 digest 파일을 내고, 최종 reducer는 digest만 읽으며 노드의 날 출력은 읽지 않습니다.

- digest 파일은 크기 상한을 밝힙니다. 패키지 기본값은 5,000 토큰이며, 실행이 `graph.json` justification에 다른 상한을 적으면 그 상한을 따릅니다.
- digest의 모든 주장은 가져온 handoff 경로를 지목합니다. handoff 인용이 없는 digest 주장은 self-check를 통과하지 못합니다.
- 클러스터 reducer는 클러스터마다 digest 하나를 씁니다. 최종 reducer는 그 digest들만 소비합니다. digest를 거치지 않고 날 노드 출력을 직접 읽는 종합 노드는 self-check를 통과하지 못합니다.

작업에 노드가 고를 수 있는 접근 목록이 있지만 목록 안에 머물러야 하며(**MUST**) 노드에 `solutionSpace`를 둡니다. node prompt에 목록을 적고, 목록 밖 접근은 조용히 통과하지 않고 self-check에서 실패합니다. `resolvedModel`은 계획이 아니라 관찰입니다. 관찰한 결과에서만 쓰고, tier에서 예측해 쓰지 않습니다.

## 10. 쓰기 범위와 handoff 채널

`dependsOn`은 순서를 정하고, 파일이 데이터를 나릅니다.

- `writes`는 노드가 바꿀 수 있는 정확한 경로나 glob을 나열하며 handoff 파일도 포함합니다.
- 병렬로 돌 수 있는 노드 둘은 같은 쓰기 경로를 공유할 수 없습니다. 의존으로 연결하거나 합칩니다.
- 모든 노드는 마지막 동작으로 `.hyper/mass/<run-key>/nodes/<node-id>.md`에 handoff를 씁니다.
- 하위 노드는 그 정확한 경로를 `reads`와 prompt에 적고, prompt는 없는 파일을 빈 결과가 아니라 FAIL로 다룹니다.
- 하위 노드가 상위 노드가 쓰는 것을 소비할 때만 엣지를 추가합니다. 리더가 이미 아는 사실은 엣지 없이 prompt에 넣습니다.
- 모든 prompt는 그 자체로 완결됩니다. "위에서 논의한 대로"나 노드가 해석할 수 없는 변수를 쓰지 않습니다.

## 11. Node prompt 계약

각 `prompt`는 다음 표지를 이 순서로 담습니다.

```text
TASK: 산출물을 지목하는 명령형 문장 하나.
DELIVERABLE: 반환하는 구체적 아티팩트. 바뀐 파일, 보고서 형태, 만든 근거.
SCOPE: 읽고 쓸 수 있는 범위와 정확한 경로. 이웃 노드가 소유한 것을 범위 밖으로 명시한 단단한 경계.
VERIFY: 노드가 자기 작업에 대해 실행하는 확인. 문자 그대로의 명령과 기대 결과.
STOP WHEN: 노드 실행을 끝내는 관찰 가능한 조건 하나.
```

prompt가 지켜지게 만드는 규칙:

- 자기 완결: 정확한 경로, 사실, 제약을 prompt에 붙입니다.
- 최소 충분 문맥: 붙인 모든 사실이 노드의 행동을 바꿔야 합니다.
- 이진 관찰: "exit code 0이고 `dist/index.js`가 존재함"이지 "잘 되는지 확인"이 아닙니다.
- 긍정적 서술: 무엇을 하라고 말합니다. NEVER와 ONLY는 진짜 불변 조건에만 씁니다.
- 노드당 역할 하나: 생산자가 자기 작업을 채점하지 않습니다.
- handoff 경로가 `DELIVERABLE`과 `SCOPE`에 모두 나타납니다.

## 12. 검증 노드

코드를 바꾸는 모든 그래프는 모든 생산 노드에 의존하는 검증 노드를 하나 이상 끝에 둡니다.

- 실제 확인을 실행합니다. 테스트 명령, 빌드, 엔드포인트 호출, 렌더링된 페이지입니다.
- prompt에 정확한 호출과 통과 여부를 정하는 이진 관찰을 적습니다.
- 자기가 믿는 요약이 아니라 캡처한 출력을 보고합니다.
- 의존 노드가 약속한 모든 handoff가 존재하고 비어 있지 않은지 확인합니다.
- 상위 결과 위에 쌓는 하위 노드는 의존하는 특정 사실을 다시 확인한 뒤 신뢰합니다.
- 생산자와 판정자는 다른 노드입니다. 판정자는 생산자의 요약이 아니라 아티팩트와 기준을 받습니다.
- 별도 작업자가 없으면(`sequential` 모드) 검증 노드는 handoff에 `verifier: self (no subagent capability)`를 적고, 결정적 판정만 냅니다. 캡처한 출력이 있는 명령, 파일 존재, diff입니다. 자기 평가를 독립 검토처럼 제시하지 않으며, 정산은 `maker-checker not available`을 밝힙니다.

## 13. 시작 전 Self-check

다음 줄이 모두 통과할 때까지 `run.created`를 쓰지 않습니다.

- [ ] 한 단계, 하나의 목표, 근거가 붙은 성공 기준.
- [ ] justification에 여섯 필드가 모두 있음.
- [ ] 컴포넌트 1-6개이고 모든 노드가 하나에 대응.
- [ ] id가 고유하고, 모든 `dependsOn` id가 존재하고, 순환이 없음.
- [ ] 모든 wave에 실행 가능한 노드가 하나 이상.
- [ ] 병렬 가능한 노드의 `writes`가 겹치지 않음.
- [ ] 모든 노드에 실행 디렉터리 안의 `handoff`가 있음.
- [ ] 종단 검증 또는 검토 노드가 모든 생산자에 의존.
- [ ] `high` 노드가 최대 하나이고, `low`가 아닌 모든 tier에 이유가 있음.
- [ ] 상한을 지켰거나, 작업을 새 key로 나눴음.
- [ ] 종합 노드가 제한 없는 날 노드 출력을 소비하지 않음. 배치 하나를 넘는 모든 reducer는 밝힌 크기 상한과 handoff 인용이 붙은 digest를 내고, 최종 reducer는 digest만 읽음.
- [ ] `solutionSpace`를 선언한 모든 노드는 prompt에 목록을 적고, 보고한 접근을 목록과 대조하며, 모든 `resolvedModel` 값이 관찰한 결과에서 나왔는지 봅니다.

같은 key와 같은 정의는 resume입니다. 예전 key 아래 바뀐 정의는 충돌이며 `amend`를 거칩니다. 다른 key는 다른 실행이지 retry가 아닙니다.
