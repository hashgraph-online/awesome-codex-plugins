# 한국어 서식

> 한국어 워크북의 숫자 서식, 날짜, CSV 인코딩. 함정은 로캘과 인코딩이지 번역이 아닙니다.

## 숫자 서식

| 용도 | 서식 코드 | 저장 값 |
|---|---|---|
| 원화 금액 | `#,##0"원"` | `1200000` |
| 원화, 음수 빨강 | `#,##0"원";[Red]-#,##0"원"` | `-5000` |
| 천 단위, 소수 없음 | `#,##0` | `1200000` |
| 천 단위, 소수 2자리 | `#,##0.00` | `1200000.5` |
| 퍼센트 1자리 | `0.0%` | `0.153` → `15.3%` |
| 음수 괄호 회계 | `#,##0;(#,##0)` | `-1200` → `(1,200)` |
| 우편번호·코드 텍스트 | `@` | `"00123"` |
| 날짜 | `yyyy-mm-dd` | `46053` (직렬 값) |
| 날짜+시간 | `yyyy-mm-dd hh:mm` | `46053.5` |
| 연월 | `yyyy-mm` | `46053` |

규칙:

- 단위는 서식의 일부이고 값의 일부가 아니다. 값에 `"원"`을 넣으면 셀이 텍스트가 되고 모든 합계가 깨진다.
- 퍼센트 값은 분수다. `15%`는 `0.15`로 저장된 `0.15`를 표시한다. `15`를 저장하면 `1,500%`가 보인다.
- 앞자리 0 코드는 텍스트여야 하고 `@`가 붙어야 한다. 그러지 않으면 엑셀이 다음 편집에서 친절하게 숫자로 되돌린다.
- `#,##0"원"`과 `₩#,##0`은 다르다. 후자는 통화 서식이라 운영체제 통화 설정을 따르고, 전자는 리터럴이라 기기 간에 안정적이다.

## 날짜

엑셀은 날짜를 1899-12-30(1900 체계) 또는 1904-01-01(1904 체계)부터 세는 직렬 숫자로 저장한다. 서식이 표시를 정한다.

- 직렬 값을 쓰고 `yyyy-mm-dd`를 적용한다. `"2026-01-31"`을 텍스트로 쓰지 않는다.
- `inspect`가 통합 문서 속성(`workbookPr`)에서 `date1904`를 보고한다. 1904 체계로 만든 파일을 1900 체계에서 열면 날짜가 4년 하고 하루 어긋난다. 날짜 산술을 믿기 전에 확인한다.
- 한국 엑셀은 텍스트 서식 셀에 날짜를 입력하면 `2026. 1. 31.`로 쓴다. 이 문자열은 한국 로캘에서 2026-01-31로 파싱되고 다른 로캘에서는 실패하거나 잘못 파싱된다.

2026-11-13 이 기기 측정: `2026. 1. 31.`, `2026-01-31`, `2026/01/31`은 모두 같은 날짜로 파싱된다. `profile`은 이것들을 `LOCALE_DATE_TEXT`로 보고한다. 텍스트로 저장되었지만 로캘에 뒤집히지는 않는다. `01/31/2026`이나 `31/01/2026`을 담은 열은 `AMBIGUOUS_DATE`로 심각도 `high`로 보고된다. 값 안에 둘 중 무엇인지 알려주는 정보가 없기 때문이다.

## CSV 인코딩

한국어 CSV는 네 가지 인코딩 중 하나로 온다. 실제로 통하는 탐지 순서:

1. `utf-8-sig` — BOM이 있다. 벗겨내지 않으면 첫 헤더 셀에 보이지 않는 `\ufeff`가 남아 모든 헤더 조회가 실패한다.
2. `utf-8` — 엄격 디코딩이 성공한다.
3. `cp949` — 마이크로소프트의 한국어 코드페이지. 실용적으로는 `euc-kr`의 상위 집합이라 `cp949`로 디코딩하면 둘 다 덮는다.
4. `euc-kr` — `cp949`가 실패할 때만 도달하며 드물다.
5. `latin-1` — 최후 수단. 어떤 바이트열이든 디코딩하지만 깨진 글자를 만든다. 그러므로 디코딩 결과가 아니라 추정으로 다룬다. `profile`은 그래도 성공하고 `encoding: latin-1`을 보고하며, 같은 파일에서 `build`는 `W_ENCODING_GUESS`를 올린다. 둘 중 하나라도 보면 인코딩 가정을 보고에 밝히고 텍스트를 확정된 값처럼 제시하지 않는다.

`profile_table.py`가 이 순서로 시도하고 어느 것을 썼는지 보고한다. 인코딩은 항상 보고에 적는다. 깨진 글자를 받은 사용자는 무엇이 가정되었는지 알아야 한다.

한국어 윈도우의 메모장은 BOM 없이 `cp949`로 저장하고, 엑셀의 "CSV UTF-8" 내보내기는 `utf-8-sig`를 쓴다. 둘 다 흔하다.

## 구분자와 소수점

한국어 CSV는 구분자가 쉼표, 소수점이 마침표로 미국과 같다. 문제가 되는 가져오기는 유럽 시스템에서 내보낸 것(세미콜론 구분자, 쉼표 소수점)이나 모든 필드를 인용하는 ERP 내보내기다. `profile`은 감지한 구분자를 `delimiter` 필드에 보고한다. 잘못 감지했을 때의 경고는 없으므로, 넓을 것으로 예상한 파일의 열 개수가 1이면 `--delimiter`를 직접 주고 다시 실행해 열 개수를 비교한다.

## 시트 이름

- 한글 시트 이름은 유효하고 화면에서 인용이 필요 없다. 다만 수식 참조는 이름에 공백, 하이픈이 있거나 숫자로 시작하면 인용해야 한다: `='월별 손익'!B2`.
- 시트 이름 한도는 31자이고 금지 문자는 `: \ / ? * [ ]`다.
- 엑셀에서 시트 이름을 바꾸면 그 시트를 참조하는 수식이 갱신되지만, 원시 XML 이름 변경은 그렇지 않다. `patch --rename-sheet`는 `<sheet>` 이름만 바꾸고 인용된 수식과 정의된 이름은 재작성하지 않는다고 계획에 경고를 남긴다. 이름을 바꾼 뒤에는 그 참조를 직접 고치고 `verify`한다.
- 엑셀은 중복 시트 이름을 거부하고, 대소문자만 다른 이름도 열 때 거부한다. `build`는 완전히 같은 이름은 거부하지만 대소문자만 다른 충돌은 검사하지 않으므로, `Data`와 `data` 같은 이름을 넣기 전에 직접 확인한다.

## 수식처럼 보이는 텍스트

`=`, `+`, `-`, `@`로 시작하는 고객 이름은 수식 주입(DDE) 경로다. 빌더는 그런 값을 텍스트로 쓰고, 빌드 출력의 `I_NEUTRALIZED`에 개수와 셀 목록을 담아 보고한다. 값을 조용히 지우지 않는다. 어느 열에 몇 개인지 보고해 사람이 판단하게 한다.

## 출력의 한글

- 원본 언어를 유지한다. 한국어 워크북의 헤더, 시트 이름, 단위는 한국어로 남는다.
- 보고는 한국어이고, 셀 내용은 그대로 인용한다.
- 한글 열 너비는 라틴 문자 수의 약 1.6배가 필요하다. 음절 하나가 라틴 문자 두 개 폭을 차지하기 때문이다. 고정 기본값이 아니라 가장 긴 값을 보고 너비를 정한다.
