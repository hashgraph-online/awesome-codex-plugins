# HWP tooling survey, 2026-11-13

## 1. Why a survey at all

Korean word-processor files come in three shapes (.hwp 3.x, .hwp 5.x, .hwpx) and the ecosystem around them is split between parser libraries, format-specific generators, MCP wrappers, and full editors. Picking one is a decision that outlives the task, so every candidate that claims to read or write these files was listed, measured, and read at the source level before one was chosen.

> `last_verified_at: 2026-11-13`

Method: `gh api` for stars, licence, last push, and primary language; then a blobless clone of the top candidates and `git show HEAD:<path>` to read their actual entry points and skill documents rather than their READMEs.

## 3. Why rhwp

Four criteria decided it, in this order.

1. **One binary, every direction.** Read (`export-text`, `export-structure`, `export-tables`), edit (`replace-text`, `set-cell`, `fill-fields`, `insert-*`), create (`scaffold`), convert (`convert`, `export-hwpx`), and verify (`hwpx-roundtrip`, `hwp5-roundtrip`, `layout-anomaly`, `verify`). Every other candidate owns one arrow of that diagram. The two that come closest, `airmang/python-hwpx` and `ai-screams/HwpForge`, are HWPX-only, which excludes the .hwp files most Korean offices actually hold.
2. **A machine-readable contract.** `rhwp capabilities` prints the binary's own command and option inventory as JSON, so a probe can detect a too-old binary instead of failing on a missing flag halfway through an edit. No other candidate exposes this.
3. **It is maintained now.** Last push 2026-11-13, v0.9.0 published 2026-11-08, 361 forks. Three of the four most-starred alternatives were last touched in 2025 or earlier, and `hwp-rs` stopped in 2022.
4. **MIT, and an agent-facing guide written by the maintainer.** `mydocs/manual/rhwp_cli_skill_guide.md` and `agent_toolkit_cli.md` describe intended agent usage, which is the difference between a tool that happens to be scriptable and a tool designed to be driven.

What rhwp does not have, and what was checked: no HWP 3.x writer (editing an HWP3 file silently produces HWP5), no HML output for non-HML sources, table property JSON accepted without schema checking, and rendering needs a Skia build plus a downloaded webfont. Each of these is documented in `rules/` as a limit rather than papered over.

## 4. What was taken from the others

| Repository | Taken |
|---|---|
| `chrisryugj/kordoc` | the why → what → how document structure and the list of phrasing that makes a report read as machine-written (`rules/gongmunseo.md` §7) |
| `jkf87/hwpx-skill` | the seven-level item numbering and the notation table (dates, amounts, ranges, colons), restated from 행정안전부 별지 제1호서식 |
| `Canine89/hwpxskill`, `UpstageAI/korean-report-hwpx` | confirmation that 공문서 template generation is a crowded space; neither offers editing, so neither was used |
| `kangdacool/hwpx-editing-skill` | the idea that an edit must be verified against a re-read and a structural check, not just a success code |

Nothing was copied as code. Every command in this skill was executed against the rhwp v0.9.0 binary; the others informed conventions and the shape of the verification ladder.

## 5. What this survey could not settle

- `law.go.kr` returned a 302 redirect from this environment, so the 행정안전부 numbering rule is recorded as a secondary source (reproduced in `jkf87/hwpx-skill`) rather than the original document.
- Star counts are a popularity signal, not a quality one. `hwplib` and `hwp.js` are older and better tested than their star position suggests, and they remain the right choice for a JVM or browser embedding. They are wrong here only because a shell task needs a CLI.
- The survey says nothing about how faithfully rhwp renders compared with the Hangul application. That comparison needs the application, which is not installed.
