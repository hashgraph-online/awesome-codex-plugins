## Claims Used by This Skill

1. **Static frontend packaging.** Tauri integrates a separately built frontend and bundles its configured distribution. Therefore a Vite SPA must emit static assets to the configured distribution directory; the project must test the real production handoff, not only a development URL. Sources: [Frontend integration](https://v2.tauri.app/start/frontend/), [Vite guide](https://v2.tauri.app/start/frontend/vite/), [Configuration](https://v2.tauri.app/reference/config/).
2. **Native RPC boundary.** Tauri commands are registered Rust functions called from the frontend through `invoke`; they can be asynchronous and return values/errors. Keep raw invocation behind a narrow typed desktop API and validate/authorize every privileged command in Rust. Sources: [Calling Rust](https://v2.tauri.app/develop/calling-rust/), [Security overview](https://v2.tauri.app/security/).
3. **State belongs on the Rust side when it is native/application state.** Managed state is available to commands, but synchronization, persistence, and access policy are application responsibilities. Source: [Rust state](https://v2.tauri.app/develop/state-management/).
4. **Least privilege is configuration plus enforcement.** Capabilities and permissions constrain command/plugin access and can apply to selected windows/webviews, platforms, or remote URLs. Scopes and CSP reduce exposure but do not turn client code into authorization. Sources: [Capabilities](https://v2.tauri.app/security/capabilities/), [Permissions](https://v2.tauri.app/security/permissions/), [CSP](https://v2.tauri.app/security/csp/).
5. **Choose IPC by semantics.** Use commands for request/response, events for small one-way notifications, and channels for ordered or high-throughput streams. React listeners survive SPA navigation and must be removed during effect cleanup; Tauri 2.12 additionally reclaims listeners when a webview is destroyed, which does not remove the cleanup obligation. Sources: [IPC model](https://v2.tauri.app/concept/inter-process-communication/), [Calling frontend](https://v2.tauri.app/develop/calling-frontend/).
6. **Custom commands need an ACL path.** Registering a command does not by itself make it least-privilege: `invoke_handler` commands are allowed for every window and webview until `AppManifest::commands` declares them. Declare application commands, map them through permissions/capabilities, and enforce scopes plus domain authorization in Rust. Sources: [Application manifest](https://v2.tauri.app/security/capabilities/), [Runtime authority](https://v2.tauri.app/security/runtime-authority/), [Command scopes](https://v2.tauri.app/security/scope/).
7. **Native and packaging behavior need native evidence.** Tauri documents tests across layers; unit/mocked frontend tests cannot by themselves prove a packaged webview, OS integration, or rejected privileged operation. Sources: [Testing](https://v2.tauri.app/develop/tests/), [Mocking](https://v2.tauri.app/develop/tests/mocking/), [WebDriver](https://v2.tauri.app/develop/tests/webdriver/).
8. **Channel and large-response IPC has a version floor.** Below `2.11.6`, large channel responses were queued app-wide under sequential identifiers and the internal `plugin:__TAURI_CHANNEL__|fetch` command returned them from a renderer-supplied header without the normal ACL rejection, so another webview could read or drain them. `2.11.6` binds each entry to its webview, randomizes identifiers, and purges entries when the owning webview closes; `2.12.0` stops queueing large channel payloads for a closed webview. Sources: [GHSA-w28w-mhc8-qvjv](https://github.com/tauri-apps/tauri/security/advisories/GHSA-w28w-mhc8-qvjv), [tauri v2.12.0](https://github.com/tauri-apps/tauri/releases/tag/tauri-v2.12.0).
9. **Application permissions are unprefixed identifiers.** `AppManifest::commands` autogenerates `allow-$command` and `deny-$command` permissions for the application manifest, and capability entries without a prefix resolve against that manifest. A `prefix:base` identifier selects the plugin manifest named by the prefix, so an application permission written as `settings:allow-read` is resolved as a plugin permission and fails the ACL build. Sources: [Permissions](https://v2.tauri.app/security/permissions/), [tauri-build ACL source](https://raw.githubusercontent.com/tauri-apps/tauri/dev/crates/tauri-build/src/acl.rs).
10. **WebView permission requests are a separate layer from the ACL.** `on_permission_request` receives a `PermissionKind` and returns `PermissionResponse::{Allow, Deny, Default}` for webview-level capabilities such as geolocation, notifications, camera/microphone, MIDI, sensors, local fonts, pointer lock, automatic downloads, file system access, and autoplay. This is enforced by the webview, not by capabilities, so the ACL cannot substitute for it. Sources: [Announcing Tauri 2.12](https://tauri.app/blog/tauri-2.12/), [tauri v2.12.0](https://github.com/tauri-apps/tauri/releases/tag/tauri-v2.12.0).
11. **Capability denies are scoped to their execution context since 2.12.0.** Before that fix a capability that denied a command for a remote URL also denied it for the local app. Upgrading can therefore re-enable local calls that were previously blocked, so allow/deny pairs need re-testing. Source: [tauri v2.12.0](https://github.com/tauri-apps/tauri/releases/tag/tauri-v2.12.0).

## Application Caveats

- Registry observations are a snapshot, not version pins or a compatibility guarantee. Use the target lockfile and installed package metadata for implementation decisions.
- Official pages describe product mechanisms, not authority to access files, credentials, signing keys, production services, or publish/release an app. Those actions require explicit user authority.
- Preserve the source URL and `last_verified_at` when citing a claim. Replace stale claims rather than blending old and new vendor behavior.
- Tauri 3 is pre-release (3.0 alpha) and is not an upgrade target for this skill; its announced ACL storage changes are not guidance for a 2.x project.
