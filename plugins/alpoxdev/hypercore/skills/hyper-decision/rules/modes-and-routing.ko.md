# 모드와 라우팅

**목적**: 요청의 모양으로 맞는 모드를 고르고, 요청이 결정 모델에 속하는지 판정하고, 경로 층에 배치하고, 요청이 흔히 비워 두는 부분을 채웁니다.

모든 요청은 네 가지를 이 순서로 정합니다. 어떤 모드인지, 결정 모델이 맞는 도구인지, 어느 경로 층이 맡는지, 요청이 말하지 않은 곳에 어떤 기본값을 쓰는지입니다. 모드는 사용자가 쓴 키워드가 아니라 원하는 산출물로 정합니다. "분류"라고 말하면서 Python 파일을 원하는 요청은 code 모드입니다.

## 1. 모드 판별

사용자가 열어 볼 산출물을 보고 한 행에 맞춥니다. 두 행이 비슷하면 사용자가 먼저 읽는 산출물의 행을 고릅니다.

| Mode | English signals | Korean signals | Produced artifact |
|---|---|---|---|
| `design` | "should this use a decision model", "is this a judgment problem", "model or code", "decision contract", "how should I split this" | "결정 모델로 하는 게 맞나", "판단 문제인가", "결정 계약", "어떻게 나눌까" | 적합성 판정과 결정 계약. 각 부분이 무엇을 정하고, 누가 맡고, 검토가 어디에 있는지 |
| `questions` | "write the questions", "question set", "criteria", "options", "levels", "scale" | "질문 만들어", "질문 묶음", "선택지", "기준", "점수 단계" | 경로의 방언으로 쓴, 요청에 바로 붙일 질문 묶음 |
| `code` | "call it from", "integration code", "client", "wire this into", "TypeScript", "Python" | "호출 코드", "연결 코드", "클라이언트", "연동" | 경로 하나와 언어 하나의 호출 코드 |
| `template` | "request json", "constants file", "routing table", "starter", "skeleton" | "요청 JSON", "상수 파일", "라우팅 표", "템플릿", "뼈대" | 요청 JSON, 상수 파일, 라우팅 표 |
| `eval` | "evaluate", "test set", "labels", "thresholds", "how accurate", "compare models", "before we ship" | "평가", "라벨", "임계값", "정확도", "모델 비교", "검증 세트" | 평가 계획, 케이스 뼈대, 임계값 조정 계획 |
| `audit` | "audit", "find the LLM calls", "what should we replace", "where do we waste calls" | "감사", "LLM 호출 찾아", "교체 대상", "어디서 낭비하나" | 기존 호출을 순위로 정리한 읽기 전용 감사 표 |
| `provider` | "which provider", "which route", "Jev or GPT", "gateway", "connect it", "setup", "environment" | "어느 공급자", "어느 경로", "어디로 연결", "설정", "환경 변수" | 경로와 층 선택, 설정 안내 |

"설계하고 코드도 줘"처럼 요청 하나가 두 행에 걸칠 수 있습니다. 사용자가 산출물을 읽는 순서대로 실행하고 어떤 모드를 돌렸는지 밝힙니다.

## 2. 적합성 관문

어떤 모드보다 먼저 이 관문을 돌립니다. 다섯 질문에 순서대로 답합니다.

1. 답이 닫힌 선택지 중 하나, 순서 있는 척도의 한 점, 예/아니오 판정, 이미지 속 영역 중 하나가 될 수 있습니까?
2. 모델 없이 정확한 코드로 같은 답을 낼 수 있습니까?
3. 결과물이 새로 쓴 산문이나 새로 쓴 코드여야 합니까?
4. 답이 산술, 세기, 날짜 비교, 숫자에 대한 여러 단계 추론에 달려 있습니까?
5. 입력이 경로가 받는 텍스트, JSON, 이미지이고, 오디오나 비디오, 코드가 바로 읽을 수 있는 데이터베이스 행이 아닙니까?

그다음 판정을 읽습니다.

행을 위에서 아래로 읽고 처음 맞는 행을 고릅니다. Q1이 아니오면 답이 닫힌 선택지, 척도, 예/아니오, 영역이 아니므로 결정하는 질문에 따라 `llm`(Q3 예)이나 `code`(Q2 예)로 다룹니다. 둘 다 아니면 결정 모델 판단이 아니라고 말하고 평범한 대안을 제시합니다.

| Verdict | When it applies | What to do |
|---|---|---|
| `decision` | Q1 예, Q2 아니오, Q3 아니오, Q4 아니오, Q5 예 | 모드를 실행합니다. 질문 묶음이나 호출을 만들고, 모든 선택형 질문에 맞는 선택지가 없다고 말할 길을 두고, 신뢰가 낮은 구간에 검토 경로를 둡니다. |
| `decompose` | Q4 예이고, 요청에 Q1 예, Q2 아니오, Q3 아니오, Q5 예를 통과하는 판단 부분도 있음 | 일을 나누는 설계를 돌려줍니다. 산술과 정책은 코드가, 판단은 결정 모델이 맡고, 나뉜 양쪽을 이 관문에 다시 대 봅니다. |
| `code` | Q2 예, 또는 판단 부분 없이 Q4 예, 또는 Q5 아니오 | 멈춥니다. 코드가 정확하게, 오프라인으로, 테스트 가능하게 답하는 이유를 말하고 결정 산출물은 만들지 않습니다. 대신 일반 코드 경로를 제시합니다. |
| `llm` | Q3 예 | 멈춥니다. 결과물이 생성된 글이나 코드이고, 결정 모델은 쓰지 않고 주어진 선택지에서 고릅니다. 이미 그 일을 하는 모델을 그대로 둡니다. |
| `hybrid` | 요청에 판단 부분과 생성 부분이 섞여 있음. 판단과 생성이 섞인 요청이면 `llm`보다 먼저 확인 | 아직 결정 산출물을 만들지 않습니다. 먼저 나눕니다. 어느 문장이 결정 모델로, 어느 문장이 언어 모델로 가는지 밝힌 뒤 결정 쪽 절반만 실행합니다. |

생성 전에 두 가지 점검으로 `decision` 판정을 다듬습니다.

- **결정이 아니라 판단을 묻습니다.** 모델에게 업무 결정을 내리라고 묻는 질문("이 티켓을 상위로 올려야 하나?")은 대개 층위가 틀렸습니다. 결정이 기대는 판단(고객이 화났는가, 돈이 걸렸는가, 보안 신고인가)을 묻고, 결정은 코드 안의 진리표로 둡니다.
- **사람 시험.** 유능한 사람이 이 state와 이 질문만 받고 바로 답할 수 있어야 합니다. 다른 문서, 조회, 계산이 필요하다면 그 일을 먼저 코드나 state로 옮깁니다.

예시 행입니다.

| Request | Verdict | Why |
|---|---|---|
| "두 날짜의 차이를 계산해줘" | `code` | 날짜 계산은 정답이 하나이고, 결정 모델은 날짜에 약하다고 문서에 적혀 있습니다. |
| "답장 메일을 써줘" | `llm` | 결과물이 새 산문입니다. 결정 모델은 주어진 선택지에서 고를 뿐 글을 쓰지 않습니다. |
| "이 티켓들을 큐 5개로 분류해줘" | `decision` | 큐 5개는 닫힌 선택지이고, 티켓은 텍스트이며, 티켓마다 선택이 하나입니다. |
| "이 리드를 적합도 1~10점으로 매겨줘" | `decision` | 텍스트에 대한, 단계가 정해진 순서 척도입니다. |
| "이 제품 사진에서 손상 위치를 찾아줘" | `decision` | 이미지 속 영역입니다. box 타입을 나열한 경로만 맡습니다. |
| "이 조항이 위험한지 판단하고 위험하면 고쳐 써줘" | `hybrid` | 위험 판단은 텍스트에 대한 예/아니오이고, 고쳐 쓰기는 생성입니다. |
| "환불 금액을 계산하고 승인이 필요한지 판단해줘" | `decompose` | 금액은 코드가 규칙으로 계산하고, 승인 여부는 결정 모델이 판단합니다. |
| "이 문서를 요약해줘" | `llm` | 요약은 아직 없는 글을 만듭니다. |

판정이 `decision`이 아니면 분명히 말하고 대안을 줍니다. 틀릴 결정 산출물로 답을 무르지 않습니다.

관문은 요청이 모델에게 맡기려는 판단에 적용합니다. `audit`에서는 후보 호출마다, 그 호출을 표에 올리기 전에 한 번씩 돌립니다. `provider`와 "이 키를 코드에 넣고 돌려줘"처럼 판단이 아니라 동작이 결과물인 요청은 결정 산출물을 만들지 않으므로 관문이 적용되지 않고, 안전 규칙이 실행을 이을지 멈출지 정합니다. 판정에 이르기 전에 안전 규칙이나 빠진 권한에서 실행이 끝날 수도 있습니다.

## 3. 경로 층

모든 경로는 한 층에 속하고, 층이 생성된 산출물이 무엇을 가정해도 되는지 정합니다. 경로 행, 엔드포인트, 방언은 [`../references/providers.ko.md`](../references/providers.ko.md)에 있고, 이 표는 각 층이 약속하는 것만 적습니다.

| Tier | What it is | Returns probabilities | What the artifact does |
|---|---|---|---|
| T1 | state에 대한 타입 질문에 답하는 네이티브 decision API | 공급자 참조에 따라 예. 공급자별 빈틈이 있습니다(예/아니오에 확신도가 없을 수 있고, box는 항상 가장자리를 돌려줍니다) | 고른 선택지의 확률에 임계값, 검토 구간, 공급자가 제공하면 버전 있는 모델 아이디 고정 |
| T2 | T1이나 T3 경로 앞의 SDK나 게이트웨이 | 라우팅된 모델이 네이티브일 때만. SDK나 게이트웨이가 보정을 더해 주지 않습니다 | 라우팅된 층과 같게 하고, SDK나 게이트웨이 버전을 고정하고, 추상화가 감추는 것을 적습니다 |
| T3 | 범용 LLM 위 에뮬레이션. enum이 있는 구조화 출력과, 공급자가 아직 돌려주는 곳에서만 토큰 로그 확률 | 대개 분포가 없습니다. 프롬프트로 받은 자기 추정치는 보정된 확률이 아닙니다 | 문서화된 확률 출처가 있고 라벨 데이터로 검증되지 않았다면 임계값 대신 검토 경로 |
| T4 | 고정 분류 체계의 분류기, 가드레일, 판정기 | 호출자가 아니라 공급자가 정한 라벨에 대한 점수나 서수 등급 | 감사나 설계에서 정책 필터로 이름만 대고, 결정 경로로 생성하지 않습니다 |

사용자가 행동의 근거로 쓸 확률이 필요하면 T3 경로를 말없이 고르지 않습니다. 확률을 돌려주지 않는다고 말하고 T1 경로나 검토 경로를 제시해 사용자가 고르게 합니다.

## 4. 필수 입력 기본값

묻기 전에 저장소에서 채웁니다.

- **언어.** `package.json`이 있고 `pyproject.toml`이 없으면 TypeScript입니다. `pyproject.toml`이 있으면 Python입니다. 둘 다 없거나 둘 다 있으면 TypeScript입니다. 무엇을 골랐는지 한 줄로 밝힙니다.
- **경로.** [`../references/providers.ko.md`](../references/providers.ko.md)의 경로 선택 순서를 위에서부터 따릅니다. 프로젝트 파일이 환경 변수 이름보다 우선합니다. 참조가 나열하지 않은 경로를 지어내지 않습니다.
- **모델과 계약 세부.** [`../references/official/`](../references/official/) 아래 맞는 파일에서 읽습니다. 생성된 산출물 안에 고정값처럼 다시 쓰지 않습니다.
- **모호함.** 가장 가까운 모드로 진행하고 빠진 사실을 정확히 하나만 묻습니다. 묻기 쉬운 사실이 아니라 답에 따라 산출물이 바뀌는 사실을 고릅니다. 질문 묶음으로 작업을 시작하지 않습니다.

## 5. 출력 위치

사용자가 위치를 정했으면 그곳에 씁니다. 아니면 `.hyper/decision/<topic>/` 아래에 쓰며, `<topic>`은 요청에서 딴 짧은 슬러그입니다.

```text
.hyper/decision/<topic>/
├── request.json
├── constants.ts
└── eval-cases.jsonl
```

기존 파일은 확인 없이 덮어쓰지 않습니다. 먼저 읽고, 옆에 새 파일을 쓰거나 바꾸기 전에 묻습니다. 쓴 파일의 경로를 모두 보고합니다.

### Evidence grade

`LOCAL`: 라우팅 규칙과 층 나누기는 저장소 정책과 사용자 지시입니다. `VENDOR`: 판단을 묻는 규칙과 사람 시험은 공급자가 배포한 스킬에서 왔고, 결정 모델의 문서화된 한계는 여기서 다시 쓰지 않고 링크한 스냅샷이 담습니다.
