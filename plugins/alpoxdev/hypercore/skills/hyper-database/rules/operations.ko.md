# 운영

operate 모드에서, 그리고 design과 choose 모드에서 보고서의 운영 절을 쓰기 전에 이 규칙을 사용합니다. 엔진 중립 DBA 체크리스트이며, 명령과 설정, 한도는 각 엔진 가이드가 밝힙니다. 발견 사항은 아래 `OP-*` ID를 인용합니다.

## 1. 백업과 복구

| ID | Severity | Rule |
|---|---|---|
| OP-01 | critical | 원본 저장소는 RPO와 RTO를 문서로 갖고, 이를 만족하는 백업 방식을 갖습니다. 작은 RPO에는 연속 아카이빙이나 특정 시점 복구, 나머지에는 스냅샷이나 논리 덤프입니다. |
| OP-02 | critical | 백업은 복구로만 증명됩니다. 일정에 따라(최소 분기마다, 백업 방식 변경 때마다) 별도 대상으로 복구하고, 행 수나 체크섬을 확인하며, 걸린 시간을 RTO와 비교해 기록합니다. |
| OP-03 | high | 최소 한 사본은 프라이머리의 계정, 리전, 장애 도메인 밖에 두고, 데이터베이스를 운영하는 같은 자격 증명으로 삭제할 수 없게 보호합니다(변경 불가 또는 별도 소유 저장소). |
| OP-04 | high | 복제본, 실행 중인 볼륨의 스냅샷, `RAID`는 백업이 아닙니다. 삭제와 손상을 그대로 복제합니다. |
| OP-05 | medium | 논리 덤프(`pg_dump`, `mysqldump`, `mongodump`)는 작은 데이터베이스와 버전 간 이전에 적합합니다. 큰 데이터베이스는 로그 아카이빙을 동반한 물리 또는 증분 백업이 필요합니다. |
| OP-06 | medium | 원본에서 다시 만들 수 있는 캐시는 백업이 필요 없지만 워밍업 계획이 필요합니다. 어떤 키를 다시 만들고 얼마나 빠른지 밝힙니다. |

## 2. 복제와 장애 조치

| ID | Severity | Rule |
|---|---|---|
| OP-10 | high | 토폴로지(단일 노드, 복제본을 둔 프라이머리, 쿼럼 클러스터, 다중 리전)와 노드, 영역, 리전 상실이 읽기와 쓰기, 데이터에 미치는 영향을 밝힙니다. |
| OP-11 | high | 비동기 복제는 장애 조치 시 아직 복제되지 않은 쓰기를 잃습니다. 허용할 수 없으면 동기 또는 쿼럼 커밋을 쓰고 그 지연 시간을 받아들입니다. |
| OP-12 | high | 장애 조치는 두 프라이머리를 막는 펜싱이나 합의 메커니즘이 있을 때만 자동입니다. 아니면 수동 승격 절차를 문서화합니다. |
| OP-13 | medium | 복제 지연을 모니터링하고 경보를 겁니다. read-your-writes 경로는 뒤처진 복제본에서 읽지 않습니다. |
| OP-14 | medium | 비운영 환경에서 장애 조치 훈련을 하고 관측한 다운타임과 데이터 손실을 기록합니다. |

## 3. 연결

| ID | Severity | Rule |
|---|---|---|
| OP-20 | high | 서버리스, 엣지, 인스턴스가 많은 애플리케이션은 풀러나 제공자의 풀링 엔드포인트를 거칩니다. 모든 풀의 합은 데이터베이스의 연결 한도 안에 두고, 풀마다 크기는 OP-23으로 정합니다. |
| OP-23 | medium | 풀 설정을 바꾸기 전에 연결 수를 계산합니다. 서버 연결 수 = 프로세스당 풀 크기 x 프로세스 수(MongoDB 드라이버는 x 복제본 세트 구성원 수)이고, 서버 한도에서 예약 연결과 플랫폼 연결을 뺀 값보다 작아야 합니다. 각 풀은 CPU 수만이 아니라 관측한 동시성(초당 요청 수 x 평균 쿼리 시간, 여유분 포함)으로 정하고, 서버의 활성 연결 지표로 확인합니다. |
| OP-21 | medium | 트랜잭션 모드 풀링은 세션 상태(세션 `SET`, 트랜잭션을 넘겨 잡는 어드바이저리 잠금, `LISTEN`, 일부 준비된 문장 모드)를 깨뜨립니다. 마이그레이션과 세션 의존 작업은 직접 연결에서 실행합니다. |
| OP-22 | medium | 모든 클라이언트는 연결, 쿼리, 유휴 시간 제한을 설정하고 멱등 작업만 재시도합니다. |

## 4. 보안

| ID | Severity | Rule |
|---|---|---|
| OP-30 | critical | 인증과 TLS 없이 공개 인터넷에서 닿는 데이터베이스 포트가 없습니다. 사설 네트워크에 바인드하고 출처를 허용 목록으로 제한합니다. |
| OP-31 | critical | 모든 애플리케이션 쿼리는 매개변수화된 문장이나 드라이버의 바인딩을 씁니다. 문자열로 만든 SQL, 원시 JSON 입력에서 만든 Mongo 필터, 이스케이프하지 않은 Lua/스크립트 인자를 쓰지 않습니다. |
| OP-32 | high | 역할을 분리합니다. 마이그레이션 소유자, 필요한 DML만 갖는 애플리케이션 역할, 분석과 지원용 읽기 전용 역할을 두고, 애플리케이션이 슈퍼유저를 쓰지 않게 합니다. |
| OP-33 | high | 자격 증명은 비밀 관리자나 플랫폼의 비밀 저장소에 두고, 일정과 인력 변동 때 회전하며, 저장소 파일과 로그, 보고서에 나타나지 않습니다. |
| OP-34 | high | 전송 중(TLS와 인증서 검증)과 저장 시 암호화합니다. 개인 또는 결제 데이터를 담은 컬럼을 분류하고 읽을 수 있는 대상을 제한합니다. |
| OP-35 | medium | 개인 데이터는 보존 기간과, 백업, 복제본, 캐시, 검색 인덱스까지 포함하는 삭제 경로를 갖거나, 그럴 수 없는 이유를 문서화합니다. |
| OP-36 | medium | 감사 로깅이 권한 있는 작업과 스키마 변경을 기록합니다. |

## 5. 용량과 유지보수

| ID | Severity | Rule |
|---|---|---|
| OP-40 | high | 테이블 또는 키 계열마다 1년 뒤 크기를 추정하고(행 수 곱하기 평균 행 크기 더하기 인덱스 크기), 디스크와 메모리 여유를 유지하며, 사용률 80% 전에 경보를 겁니다. |
| OP-41 | medium | 엔진 자체 유지 작업을 계획합니다. PostgreSQL vacuum과 랩어라운드, InnoDB purge와 히스토리 길이, MongoDB와 Cassandra 컴팩션, Redis 메모리 단편화입니다. |
| OP-42 | medium | 바쁜 테이블에서 행을 하나씩 삭제하는 대신 보존 규칙으로 데이터를 아카이브하거나 파티션합니다. |
| OP-43 | medium | 접근 패턴 표가 핫스팟을 예측하는 설계는 출시 전에 부하 시험합니다. |

## 6. 업그레이드

| ID | Severity | Rule |
|---|---|---|
| OP-50 | high | 지원되는 주 버전을 유지하고, 엔진 가이드의 날짜가 붙은 지원 표를 확인하며, 지원 종료 전에 다음 업그레이드를 계획합니다. |
| OP-51 | high | 복구한 사본에서 예행하고, 중간의 모든 릴리스 노트를 읽고, 롤백 경로(논리 복제 또는 블루-그린 전환, 또는 직전에 뜬 복구 가능한 백업)와 애플리케이션 호환성 시험을 갖춰 업그레이드합니다. |
| OP-52 | medium | 마이너 릴리스는 즉시 적용합니다. 보안과 데이터 손상 수정을 담고 있습니다. |

## 7. 모니터링

| ID | Severity | Rule |
|---|---|---|
| OP-60 | high | 데이터베이스의 핵심 신호를 지켜봅니다. 쿼리 지연 시간 백분위, 처리량, 오류, 포화(CPU, 메모리, 디스크, 연결, I/O)입니다. |
| OP-61 | medium | 문장 수준 통계 원천을 켜 두고(`pg_stat_statements`, Performance Schema, 프로파일러, `SLOWLOG`), 총 시간 기준 상위 문장을 검토합니다. |
| OP-62 | medium | 복제 지연, 디스크 여유, 연결 포화, 잠금 대기, 교착, 캐시 적중률 하락, 축출, 백업 실패에 경보를 겁니다. |
| OP-63 | medium | 모든 경보는 런북 항목을 연결합니다. 무엇을 뜻하는지, 어떻게 확인하는지, 첫 안전 조치가 무엇인지입니다. |
