# 검증

`hyper-git`의 변경을 완료로 선언하기 전, 또는 어느 모드든 실행을 성공으로 보고하기 전에 이 검사를 실행한다.

## 스킬 품질 검사

- description이 네 가지 결과(푸시되는 커밋, 워크트리 작업, 이슈 작업, 브랜치·풀 리퀘스트·병합 작업)를 밝히고, 모든 경계(로컬 커밋만, 이력 재작성, 릴리스, CI, 컨테이너 격리)를 다른 스킬 이름이 아니라 요청한 결과로 진술한다.
- `SKILL.md`가 표 하나로 모드를 정하고, 모드마다 소유 규칙을 정확히 하나씩 가리킨다: commit -> `rules/commit-and-push-policy.md`, worktree -> `rules/worktree-lifecycle.md`, issue -> `rules/issue-workflow.md`, workflow -> `rules/branch-workflow.md`.
- `assets/evals/hyper-git-cases.jsonl`이 모드마다 should-trigger, should-not-trigger, 경계, 근접 오답, 안전, 적대적, 회귀 사례를 구성하고 모드 라우팅 사례를 더한다. 모든 사례가 자체 `intent`, `runs`, `threshold`, `metrics`를 밝힌다. 기존 사례가 검사하지 않는 지점을 시험할 때만 사례를 추가한다.
- core는 간결하게 유지하고 규칙과 스크립트를 중복 없이 가리킨다. 하위 에이전트 레인 규칙은 `rules/agent-parallelism.md`에만 둔다.
- 스크립트 추가는 결정적 속도나 안전 개선으로 정당화된다.
- 연결된 워크트리는 모든 모드에서 유효한 컨텍스트다. 체크아웃 루트는 서로 분리되고 `.git`이 디렉터리라고 가정하지 않는다.
- 인자가 없거나 `current`/`CURRENT`이면 현재 세션 변경을, `all`/`ALL`이면 모든 미커밋 변경을 선택하고, `&&` 대상은 변경 전에 검증한다.
- 모든 게시 행동(이슈 생성·편집·댓글·닫기·다시 열기, 풀 리퀘스트 열기, 이름을 댄 브랜치로의 병합)은 사용자가 그 행동을 요청했는지로 게이트한다.

## 런타임 검사: commit 모드

- 저장소 루트에서 `bash -n skills/hyper-git/scripts/git-fast.sh`가 통과한다.
- `scripts/git-fast.sh inspect . --jobs 2`가 `repos|begin`, `repo-status|begin`, 파일 인벤토리 블록을 출력한다. 연결된 워크트리 안에서는 `worktree|linked`와 연결된 체크아웃 루트의 `repo|...` 경로를 보여 준다.
- 사용자가 푸시를 요청하지 않는 한 푸시 helper는 실제 원격에 대해 시험하지 않는다. 동작 검사는 로컬 픽스처를 쓴다.
- 커밋은 대상 지정 스테이징과 커밋당 하나의 논리적 변경을 쓰고, 메시지는 영어 Conventional Commit이다: 명령형 subject, 콜론 뒤 소문자, 끝 마침표 없음, 72자 이하, 본문 앞 빈 줄, 사용자나 저장소가 요청하지 않은 서명·출처 트레일러 없음.
- 푸시는 모든 커밋 그룹이 성공한 뒤에만 자동으로 실행하고, force push는 `main`과 `master`에서 계속 차단된다.
- 이번 실행이 만든 커밋만 왼쪽에서 오른쪽 순서로 각 `&&` 대상에 닿는다. 기계적인 충돌 하나는 묻지 않고 해결·검증하고, 의미가 모호한 동작 충돌은 뒤 대상으로 넘어가기 전에 집중된 질문 하나를 한다.
- 모든 푸시 뒤에 원격에서 다시 읽어 확인했다. 푸시한 브랜치와 각 `&&` 대상에 대해 `git branch -r --contains <sha>` 또는 `+` 줄이 없는 `git cherry origin/<target> <branch>`를 쓴다.
- 하위 에이전트를 썼다면 그 작업은 읽기 전용이었고, 메인 통합자만 스테이징·커밋·푸시했다.

## 런타임 검사: worktree 모드

- `git rev-parse --show-toplevel`이 성공하고, 경로를 구성하거나 변경하기 전에 `git worktree list --porcelain`을 읽는다.
- `hyper-git worktree <ARGUMENT>` 직접 호출은 어떤 워크트리를 만들지 묻지 않고 인자로 생성한다. 그 밖의 경우 작업 의도가 없으면 현지화된 질문 하나를 한다.
- 중첩 생성 전에 `.hyper/worktree/`가 무시되거나 로컬 제외로 등록되어 있다.
- 생성 뒤 후속 명령이 새 경로에서 실행되었고(지속되는 `cd` 또는 `workdir=<path>`), 리포트가 어느 방식이었는지 밝힌다.
- 삭제는 먼저 `git -C <path> status --short`를 읽고, 메인 워크트리를 거부했으며, `--force`는 명시 요청이 있을 때만 썼다. 정리는 `git worktree prune` 전에 `git worktree prune --dry-run`을 실행했다.

## 런타임 검사: issue 모드

- 어떤 이슈 명령보다 먼저 `gh auth status`와 `gh repo view`가 성공했거나, 실행을 멈추고 실패한 검사를 밝혔다.
- 게시한 모든 텍스트가 리포트에 보이는 것과 일치하고, 사용자가 그 행동을 요청하지 않은 게시는 없었다.
- 레이블, 마일스톤, 이슈 번호, 담당자를 지어내지 않았다.
- 풀 리퀘스트가 기본 브랜치가 아닌 곳을 향하면 연결된 이슈가 열린 채로 남는다고 리포트가 밝힌다.

## 런타임 검사: workflow 모드

- 모델을 추천하거나 병합하기 전에 기본 브랜치, 허용된 병합 방식, 브랜치 목록을 읽었다.
- 사용자가 이름을 대지 않은 `main`, `master`, 기본 브랜치, 배포 브랜치로 병합하지 않았고, `--admin`도, 건너뛴 검사도, 설정 변경도 없었다.
- 모든 병합 대상이 병합 전에 원격에서 fast-forward되었고, 병합 결과에서 저장소 검사를 실행했으며, 푸시 출력이 각 대상을 확인한다.
- 브랜치와 워크트리 삭제는 원격에서 병합이 확인된 뒤에만 일어났다.

## 재독 검사

다음 관점으로 읽는다.

1. 트리거 모델: 커밋만 요청, 개념 질문, 계획 실행, 릴리스 작업은 스킬을 활성화하지 않는다. 활성화되는 요청은 모드 하나에 정확히 들어간다.
2. 급한 운영자: 모드마다 가장 빠른 안전 명령이 분명하다.
3. 커밋 리뷰어: 생성된 subject가 영어 명령형 변경으로 읽힌다.
4. 유지보수자: 규칙마다 집이 하나이고, 새 동작이 들어갈 파일이 분명하다.
5. 브랜치 운영자: `hyper-git && dev`, `hyper-git CURRENT && dev && deploy/staging`, "dev와 main에 머지하고 푸시해"의 범위, 순서, 정지 동작이 모호하지 않다.
