# 목표와 기준

`brief.md`나 `goals.json`을 쓰기 전, 그리고 목표·기준·의존·상태를 추가하거나 바꿀 때 이 규칙을 읽는다.

## 1. 파일과 소유권

실행 하나가 디렉터리 하나를 소유한다. `.hyper/loop/<slug>/`이며 `<slug>`는 요청에서 딴 짧은 소문자 케밥 표기 이름이다. 그 실행만 네 파일을 쓴다.

| 파일 | 역할 | 쓰기 규칙 |
|---|---|---|
| `brief.md` | 요청, 의도한 결과, 제약, 실행 id | 한 번 쓰고 이후에는 덧붙이기만 한다 |
| `goals.json` | 상태·의존·기준을 담은 목표들 | 통째로 다시 쓴다. id는 재사용하지 않는다 |
| `ledger.jsonl` | 캡처·체크포인트·조향·실패의 추가 전용 이력 | 덧붙이기만 한다. 편집하거나 잘라 내지 않는다 |
| `final-gate.json` | 표면 증거를 담은 완료 기록 | 최종 체크포인트에서 한 번 쓴다 |

증거 파일은 그 옆에 둔다. 보통 `.hyper/loop/<slug>/evidence/` 아래다. 다른 slug는 다른 실행이다. 두 실행을 한 디렉터리에 합치지 않고, 끝난 실행의 디렉터리를 지우지 않는다.

## 2. 목표

목표는 다른 목표가 의존할 수 있는, 끝낼 수 있는 요청의 한 덩어리다.

| 필드 | 필수 | 계약 |
|---|---|---|
| `id` | 예 | 실행 전체에서 고유하다. 예: `G1`. 다른 목표로 대체된 뒤에도 재사용하지 않는다 |
| `title` | 예 | 한 줄. 가능하면 사용자의 말을 쓴다 |
| `objective` | 예 | 이 목표가 끝났을 때 참이 되는 것. 관찰 가능한 형태로 적는다 |
| `status` | 예 | `pending`, `in_progress`, `complete`, `failed`, `blocked`, `cancelled` |
| `depends_on` | 예 | 이 목표를 시작하려면 `complete`여야 하는 목표 id 배열. 없으면 빈 배열 |
| `criteria` | 예 | 기준이 최소 하나. §3을 따른다 |
| `surfaces` | 아니오 | 이 목표가 건드리는 사용자 표면 배열. 예: `cli`, `http`, `browser`, `data`. 최종 게이트에 표면마다 행이 필요하다 |
| `attempt` | 아니오 | 현재 실패 서명에 쓴 시도 횟수 |
| `cycles` | 아니오 | 이 목표에 쓴 순환 횟수 |

의존 규칙:

- `depends_on`의 모든 id가 같은 파일에 있다.
- 그래프에 순환이 없다. 순환은 계획 오류다. 목표를 고리를 만들지 말고 나눈다.
- 의존 목표가 `complete`일 때만 다음 목표를 시작할 수 있다. `failed`, `blocked`, `cancelled` 의존은 다음 목표를 열지 않는다.
- 끝낼 수 있는 단위보다 커진 목표는 `split_subgoal`로 나누고 증거를 유지한다.

실행 루트에는 `schema_version`, `objective`, `status`(`active`, `paused`, `blocked`, `failed`, `complete`, `cancelled`), `current_goal_id`도 있다. 정확한 모양은 [references/state-schemas.md](../references/state-schemas.md)에 있다.

## 3. 기준

기준은 사람이 다시 실행할 수 있는 이분형 검사 하나다.

| 필드 | 필수 | 계약 |
|---|---|---|
| `id` | 예 | 목표 안에서 고유하다. 예: `C1` |
| `scenario` | 예 | 관찰 가능한 상황. 무엇을 어떤 입력과 어떤 환경에서 실행하는지 적는다 |
| `pass_condition` | 예 | 참이나 거짓 하나로 판정되는 문장. "대부분", 백분율 같은 표현은 쓰지 않는다 |
| `expected_evidence` | 예 | 캡처가 쓰는 파일 경로. 이 파일이 비어 있으면 기준은 통과할 수 없다 |
| `essential` | 예 | `true`면 이 기준 없이는 비최종 체크포인트를 넘길 수 없다. `false`면 최종 게이트까지 기다릴 수 있다 |
| `cleanup` | 예 | 이 기준이 책임지는 정리, 또는 지울 자원이 없다는 명시 |
| `adversarial_classes` | 아니오 | `{name, status: "pass"|"not_applicable", evidence?, reason?}` 배열. `pass` 항목에는 캡처한 증거가, `not_applicable` 항목에는 이유가 필요하다 |
| `status` | 아니오 | `pending`, `in_progress`, `pass`, `fail`, `blocked`, `cancelled`. durable한 진실은 장부 행이다 |

기준을 증명 가능하게 유지하는 규칙:

- 서로 독립적인 결과를 "그리고"로 이은 조건은 기준 둘이다. 하나를 나눠야 한쪽 실패가 다른 쪽에 가려지지 않는다.
- 거짓이 될 수 없는 조건은 기준이 아니다. "코드가 작성됐다", "테스트가 존재한다"는 이 검사를 통과하지 못한다. "명령이 0으로 끝나고 출력에 주문 id가 있다"는 통과한다.
- `expected_evidence` 경로는 캡처 전에 쓰고, 캡처가 마침 만든 결과에서 끌어오지 않는다.
- 적용할 적대 클래스가 없으면 배열을 비워 두고 설명하지 말고 이유를 담은 `not_applicable` 항목 하나를 남긴다.
- 증명이 사용자 표면에 걸린 기준은 목표의 `surfaces`에 그 표면을 선언한다. 그래야 최종 게이트가 그 표면을 보여야 한다.

## 4. 상태와 전이

| 이전 | 이후 | 조건 |
|---|---|---|
| `pending` | `in_progress` | 재개 규칙이 골랐다 |
| `in_progress` | `complete` | 체크포인트면 핵심 기준 모두가 신선한 증거로 통과하고 의존이 모두 `complete`이며, 최종 게이트면 모든 기준이 통과했다 |
| `in_progress` | `failed` | 서명을 남긴 채 실패 한도에 닿았다 |
| `in_progress` | `blocked` | 의존이 충족되지 않았거나, 능력이 없거나, 사용자가 판단해야 한다 |
| `in_progress` | `cancelled` | 사용자가 취소했고 정리를 기록했다 |
| `blocked` | `pending` | 해소 단계가 실제로 일어났고 사용자나 기록이 재시도를 말한다 |
| `pending` | `cancelled` | 사용자가 시작하지 않은 목표를 취소했고 정리를 기록했다 |
| `blocked` | `cancelled` | 옛 증거를 보존한 채 `mark_blocked_superseded`로 은퇴했다 |

`paused`는 목표가 아니라 실행의 상태다. 멈춘 목표는 `in_progress`를 유지하고 사용자의 지시가 있을 때만 재개한다. 취소한 목표는 자동으로 재개하지 않는다.

## 5. 재개 선택

재개할 때마다, 컨텍스트 압축 뒤에도 `brief.md`, `goals.json`, `ledger.jsonl`의 끝부분을 코드보다 먼저 읽는다. 그다음 디스크에 실제로 있는 것과 장부가 주장하는 것을 맞춘다.

선택 순서는 고정이다.

1. 사용자가 멈추지 않았고 상태가 `in_progress`인 목표.
2. 없으면 파일 순서에서 처음으로 `depends_on`이 모두 `complete`인 `pending` 목표.
3. 둘 다 없으면 고를 것이 없다. 진행을 막는 목표를 적고 실행을 `blocked`로 기록한다.

멈춘 목표는 이 규칙으로 재개하지 않는다. 현재 대화에서 사용자의 지시가 필요하다. 끝난 목표를 다시 실행하거나, 그 캡처를 다시 돌리거나, 그 행을 다시 쓰는 것은 재개가 아니다.

## 6. 브리프

`brief.md`는 짧고 안정적이다. 사용자가 말한 요청, 실행이 스스로 묶은 결과, 제약(브랜치, 금지 동작, 기한), slug, 실행 id를 담는다. 중간 목표가 새 작업을 드러낼 때 목적이 흔들리지 않게 붙잡는 파일이다. 목적을 바꾸는 목표는 조용한 편집이 아니라 사용자와의 대화다.
