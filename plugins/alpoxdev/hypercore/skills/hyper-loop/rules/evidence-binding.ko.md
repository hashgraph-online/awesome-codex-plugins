# 증거 묶기

첫 캡처 전, 그리고 증거를 통과·낡음·없음·실패로 보고할 때 이 규칙을 읽는다. 증거가 무엇에 묶이고 그 묶임이 언제 끝나는지 정한다.

## 1. 지문이 덮는 것

증거는 검사한 내용에 대해서만 의미가 있다. 이 패키지는 증거를 값 둘과 명령 하나에 묶는다.

| 값 | 만드는 방법 | 두는 이유 |
|---|---|---|
| `tree` | `git rev-parse 'HEAD^{tree}'` | 메시지나 작성자만 바뀐 커밋은 내용이 같으므로 증거를 무효로 만들지 않는다 |
| `diff_sha256` | `git diff --binary HEAD` 뒤에 정렬한 미추적 파일마다 `<sha256>\t<path>` 한 줄을 붙인 것의 SHA-256 | 커밋하지 않은 편집과 새 파일도 증거의 일부다. 그래서 커밋하지 않은 변경을 그대로 둔 채 `HEAD`가 같다는 이유로 숨길 수 없다 |
| `command` | 캡처가 실제로 실행한 명령줄 | 나중에 읽는 사람이 다시 실행할 수 있고, 다시 실행할 수 없다면 그 증거가 보기보다 약하다는 것을 안다 |

무시 대상 파일은 제외한다. 그래서 빌드 산출물, 의존성 폴더, 캐시가 지문을 흔들지 않는다. 루프 디렉터리 자체도 제외한다. 넣으면 `ledger.jsonl`에 덧붙일 때마다 앞선 모든 증거가 무효가 되기 때문이다. 루프 디렉터리가 저장소 안에 있으면서 자기 장부를 깨지 않는 이유가 이 제외다.

이 값은 번들 검증기가 계산한다. 손으로 계산하지 않는다.

```bash
bash <skill-dir>/scripts/verify-loop-state.sh snapshot --dir .hyper/loop/<slug>
```

`tree`, `diff_sha256`, 미추적 항목, 제외 경로를 출력한다. 정확한 필드 목록은 [references/state-schemas.md](../references/state-schemas.md)에 있다.

## 2. 장부 행

기준 증명 하나는 `ledger.jsonl`에 덧붙이는 JSON 객체 하나다.

```json
{"event":"evidence","goal_id":"G1","criterion_id":"C2","verdict":"pass",
 "tree":"<tree>","diff_sha256":"<digest>","command":"<실제로 실행한 명령>",
 "evidence":"<캡처가 보여 준 것>","artifacts":["<경로>"],"rationale":"<이 증명이 그 기준에 답하는 이유>"}
```

행 규칙:

- 덧붙이기만 한다. 잘못된 행은 같은 기준의 새 행으로 덮고 옛 행은 이력으로 남긴다.
- `verdict`는 `pass`, `fail`, `blocked` 중 하나다. `blocked` 행은 시나리오를 실행할 수 없었다는 뜻이며 통과가 아니다.
- `command`는 증거를 실제로 만든 명령이다. 만들어야 했던 명령이 아니다.
- `evidence`는 관찰한 것을 구체적으로 적는다. 종료 코드, 출력 줄, 측정값을 쓴다.
- `artifacts`는 캡처가 쓴 파일을 저장소 루트 기준이나 절대 경로로 적는다. 관찰은 산출물 하나나 `expected_evidence` 파일에 담겨 있어야 한다.

체크포인트 행은 `event: "checkpoint"`를 쓰고 목표, tree, 다이제스트, 통과한 기준을 담는다. 조향은 `event: "steering"`에 동사와 이유를 담는다. 실패 한도는 `event: "failure"`에 서명을 담는다.

## 3. 신선함, 낡음, 없음, 실패

검증기는 기준의 마지막 증거 행을 지금 계산한 지문과 비교한다.

| 상태 | 뜻 |
|---|---|
| `pass` | 행의 `verdict`가 `pass`이고, tree와 다이제스트가 현재 값과 같고, `expected_evidence` 파일이 비어 있지 않게 있다 |
| `stale` | 행은 통과했지만 tree나 다이제스트가 현재 작업 트리와 다르다. 캡처 뒤에 내용이 움직였다 |
| `failing` | 마지막 행의 판정이 `fail` 또는 `blocked`다 |
| `missing` | 기준에 증거 행이 없다 |
| `missing-evidence-file` | 행은 신선하지만 `expected_evidence` 파일이 없거나 비었다 |

증거로 인정하는 상태는 `pass` 하나다. `stale`이 바로 이 장치가 존재하는 이유다. 코드가 바뀌었으므로 그 변경이 무관해 보여도 옛 출력은 더 이상 현재 동작을 설명하지 않는다.

## 4. 다시 캡처하지, 이름표를 바꾸지 않는다

기준이 `stale`이면 답은 새 캡처다.

1. 기준의 `scenario`가 적은 대로 시나리오를 다시 실행한다.
2. 새 관찰을 같은 `expected_evidence` 경로에 쓴다. 옛 내용을 대체한다.
3. 현재 tree와 다이제스트로 새 증거 행을 덧붙인다.
4. `--goal <id>`를 다시 돌리고 새 상태를 읽는다.

다음은 하지 않는다.

- 옛 출력을 그대로 둔 채 행의 `tree`와 `diff_sha256`만 고치는 것.
- "영향이 없을 수 없다"는 이유로 옛 로그를 새 지문에 붙이는 것.
- 행 없이 `goals.json`에서 기준을 `pass`로 표시하는 것.

변경이 정말로 그 기준에 영향을 줄 수 없다면 시나리오를 다시 돌리는 비용은 작다. 실행은 논쟁하지 않고 다시 돌린다.

## 5. 증거 파일

- 기준마다 파일 하나면 충분하다. `expected_evidence`의 경로가 검증기가 확인하는 주소다.
- 파일에는 나중에 쓴 요약이 아니라 관찰이 담긴다. 명령 출력, 기록, diff, 측정값, 시각 표면이면 스크린샷 경로를 쓴다.
- 가능한 한 작고 텍스트에 가깝게 유지한다. 시각 표면의 스크린샷은 괜찮지만, 아무도 게이트에서 다시 읽지 않을 수 메가바이트 덤프는 좋지 않다.
- 정리 영수증은 기준의 `cleanup`에 적고, 중요하면 행의 `rationale`에도 적는다. 어떤 프로세스를 멈췄고, 어떤 임시 디렉터리를 지웠고, 어떤 자원을 만들지 않았는지 적는다.
- 증거 파일을 지우면 그 기준이 `missing-evidence-file`이 된다. 증거를 임시 경로가 아니라 실행 디렉터리 안에 두는 이유다.

## 6. 지문이 증명하지 않는 것

- 시나리오가 좋은 시험이었다는 것은 증명하지 않는다. 약한 기준은 약하게 통과한다.
- 저장소 밖 파일, 원격 서비스, 파일을 건드리지 않고 바뀌는 상태는 덮지 않는다.
- 내용이 같으면 두 기기를 구분하지 못한다. 도구 체인이 다른 기기에서 같은 바이트에 다른 명령을 실행했을 수 있다.

증거가 이런 한계에 기대면 그 한계를 함께 적는다. 그리고 내부 값보다 제품 표면을 관찰하는 시나리오를 고른다.
