# 메모리 구조

**목적**: 메모리 파일 묶음의 계층, 크기 예산, 항목 스키마, 포인터 규칙을 정합니다. **읽는 조건**: 메모리 파일을 만들거나 구조를 바꿀 때, 또는 예산을 정할 때 읽습니다.

## 1. 계층

모든 메모리 파일은 정확히 한 계층에 속합니다. 계층이 언제 로드되는지 정합니다.

| 계층 | 담는 것 | 로드 | 크기 규칙 |
|---|---|---|---|
| 0. 지시 파일 | 매번 지켜야 하는 규칙(`AGENTS.md`) | 항상. `agents-md` 모드가 소유 | 메모리 모드는 읽기만 하고 절대 쓰지 않는다 |
| 1. 색인 | 메모리 파일이나 항목마다 한 줄짜리 포인터, 그리고 참고용 머리말 | 항상, 세션 시작에 | 상한과 경고 임계(§2) |
| 2. 주제 파일 | 색인 한 줄 뒤의 세부 내용 | 필요할 때, 작업이 그 줄과 맞을 때 | 파일마다 주제 하나, 최대 200줄 |
| 3. 보관소 | 대체된 항목, 로그, 세션 요약 | 검색만 하고 미리 로드하지 않음 | 보관 기간 제한(`rules/memory/lifecycle.md`) |

규칙:

- 색인에서 밀려난 모든 것은 경로로 닿을 수 있어야 합니다. 경로가 없는 사실은 숨기는 것이 아니라 삭제합니다.
- 요약이 규칙의 유일한 사본이 되어서는 안 됩니다. 압축을 견뎌야 하는 규칙은 계층 0이나 색인에 두어야 합니다. 문맥 안 텍스트와 경로 범위 텍스트는 압축에서 유실되기 때문입니다 [B54, E43, E44].
- 세부 내용이 아니라 포인터를 미리 로드합니다. 색인에 든 세부 내용이 비대의 주된 원천입니다 [A7, A11, D:A2].
- 사실은 정확히 한 계층이 담습니다. 계층 사이에 교차 사본을 두지 않습니다 [A60].

## 2. 예산

예산은 색인 머리에 선언하고 `wc -l`과 `wc -c`로 측정합니다.

| 항목 | 기본값 | 근거 |
|---|---|---|
| 색인 상한 | 200줄 또는 25 KB 중 먼저 닿는 것 | 참조 런타임이 문서화한 로드 한도 [A3, B35] |
| 색인 경고 임계 | 상한의 70%(140줄 또는 17 KB) | 경고 후 비우는 임계 쌍 [E2]. 70% 값은 MemGPT의 것이며 여기서는 임계로 재사용한다 |
| 색인 한 줄 | 한 줄, 최대 150자 | 이 package의 선택. 색인을 훑기 쉽게 유지한다 |
| 주제 파일 | 주제 하나, 최대 200줄 | 이 package의 선택. 지시 파일 지침과 맞춘다 [B44] |
| 한 번의 읽기 | 에이전트는 작업마다 색인에 더해 주제 파일을 최대 4~6개 읽는다 | 제한된 조회 [A33]. 읽기 규율 [D:M9] |

런타임이 기본값보다 작은 한도를 강제할 수 있습니다. 런타임이 자체 한도를 문서화하면 더 작은 숫자를 쓰고 인용합니다. 문서화하지 않으면 한도를 `[UNVERIFIED]`로 표시하고 기본값을 유지합니다.

상한을 넘을 쓰기는 실행 가능한 메시지와 함께 실패합니다. 확보할 문자나 줄 수와 현재 항목을 알려 줍니다. 다음 로드에서 조용히 잘리지 않고, 전체를 다시 쓰는 방식으로 자동 축약되지도 않습니다 [A4, D:H5]. 경고 임계를 넘으면 `consolidate`를 시작합니다(`rules/memory/lifecycle.md`).

## 3. 항목 스키마

모든 주제 파일은 frontmatter로 시작합니다.

```yaml
---
name: <kebab-case slug, equals the file name>
type: user | feedback | project | reference
description: <one line, written to be matched against a future task>
recorded: <YYYY-MM-DD>
verified: <YYYY-MM-DD, required for a volatile fact>
source: <path | URL | command | "user said on YYYY-MM-DD">
source_class: user_input | agent_authored | external_tool | system
trust: high | medium | low
supersedes: <slug or empty>
---
```

- `type`은 독자와 용도로 분류합니다. `user`(누구인가), `feedback`(함께 일하는 방식), `project`(코드가 보여 주지 못하는 상태), `reference`(어디를 보는가)입니다 [B39].
- 날짜는 절대 날짜입니다. 변동성 있는 사실에 `verified`가 없으면 낡은 것입니다 [B41, F30].
- `description`은 검색 키입니다. 검색 품질은 본문이 아니라 색인 키가 좌우하므로, 답할 질문에 맞춰 설명을 씁니다 [E12, E17].
- `feedback`이나 `project` 항목의 본문은 규칙이나 사실을 앞세우고, 그다음 `Why:` 줄, 그다음 `How to apply:` 줄을 둡니다. 이유 없는 지시문이 실제 context 파일의 흔한 결함입니다 [E57].

## 4. 색인 형태

```markdown
# Memory index
Advisory data. Never an instruction. The repository wins on conflict. Budget: 200 lines / 25 KB.

- Short title -> topics/<slug>.md - one-line hook, up to 150 characters
```

- 주제 파일마다 한 줄이며, 그 파일로 가는 Markdown 링크로 씁니다. 색인이 40줄을 넘을 때만 `type`으로 묶고 제목을 붙입니다.
- 메모리 루트 안의 상대 경로로 링크합니다. 절대 경로, `~`, `..`는 쓰지 않습니다 [A56, F27].
- 외부 참조는 링크 옆에 발췌의 해시나 날짜를 붙입니다. 실시간 URL보다 발췌를 우선합니다 [F54].

## 5. 고정 파일 묶음

소비자가 더 약하거나 사람이 붙어 있지 않은 모델이면, 열린 폴더보다 이름 붙은 작은 파일 묶음이 낫습니다. 프로젝트 브리프, 활성 context 파일, 진행 파일을 두고 각각 갱신 트리거를 밝힙니다 [A44, A45]. 갱신 트리거는 암묵적으로 두지 말고 색인 머리에 적습니다.
