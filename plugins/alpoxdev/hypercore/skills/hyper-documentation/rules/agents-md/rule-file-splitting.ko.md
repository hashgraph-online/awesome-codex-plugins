# 규칙 파일 분리

**목적**: 항상 로드되어야 하는 지침을 숨기지 않으면서, 같은 범위의 세부 내용을 인접한 `rules/` 디렉터리로 옮겨 관할 `AGENTS.md`를 간결하게 유지한다.

## 1. 분리 시점

기존 또는 작성 중인 `AGENTS.md`를 훑어보기 어려워졌거나, 합산 지침 예산을 지나치게 사용하거나, 일부 작업에만 적용되는 상세 절차를 담고 있을 때 이 규칙을 사용한다.

다음 순서로 판단한다.

1. 일반적이거나, 저장소에서 발견 가능하거나, 오래됐거나, 중복됐거나, 실질적 역할이 없는 텍스트를 삭제한다.
2. 실제 하위 트리 차이는 가장 가까운 정당한 중첩 `AGENTS.md`로 옮긴다.
3. 항상 필요한 범위, 권위, 명령, 안전 게이트, 중단 조건은 관할 `AGENTS.md`에 유지한다.
4. 같은 범위에 속하지만 조건부로만 필요한 세부 내용만 해당 `AGENTS.md` 옆의 `rules/*.md`로 옮긴다.

`rules/` 분리는 progressive disclosure 수단이지 admission test를 통과하지 못한 모든 내용을 보존하는 방법이 아니다.

## 2. 위치와 형태

루트 지침 파일의 경우:

```text
repository/
├── AGENTS.md
├── AGENTS.ko.md
└── rules/
    ├── architecture.md
    ├── architecture.ko.md
    ├── testing.md
    └── testing.ko.md
```

중첩 지침 파일의 경우, 규칙이 같은 하위 트리를 관할할 때만 해당 하위 트리에서 지침 파일 옆에 지원 규칙을 둔다. 기존의 인접한 `rules/` 디렉터리가 이미 지침 문서를 담고 있고 새 이름이 충돌하지 않을 때만 재사용한다. 제품 코드, 생성 파일, 또는 이미 다른 목적으로 쓰는 디렉터리에 에이전트 정책 Markdown을 섞지 않는다. 대신 저장소의 기존 지침 문서 위치를 사용하고 직접 링크한다.

`architecture-boundaries.md`, `testing.md`, `release-safety.md`처럼 판단 영역을 나타내는 설명적인 kebab-case 이름을 사용한다. `misc.md` 같은 포괄 파일은 만들지 않는다.

## 3. 로딩 계약

임의의 `rules/*.md` 파일이 런타임에서 자동 발견되거나 자동 import된다고 가정하지 않는다. 관할 `AGENTS.md`는 모든 지원 파일을 직접 링크하고 언제 읽어야 하는지 정확히 명시해야 한다.

좋은 예:

```markdown
## 조건부 규칙

- 테스트 인프라나 테스트 명령을 바꾸기 전에 `rules/testing.md`를 읽는다.
- 패키지 경계를 넘어 코드를 옮기기 전에 `rules/architecture-boundaries.md`를 읽는다.
```

각 항목은 지원 파일로 가는 Markdown 링크 하나와 그 파일을 읽어야 하는 조건으로 이루어진다. 위에 나온 경로는 대상 저장소 내부의 예시 경로이므로, 이 package에서는 해석되지 않을 링크 대신 code span으로 표기한다.

“`rules/` 참고” 같은 모호한 안내를 사용하지 않는다. 대상 런타임과 문법을 명시적으로 검증하지 않았다면 공유 `AGENTS.md`에서 런타임 전용 import 문법을 사용하지 않는다. 일반 Markdown 링크와 읽기 조건을 함께 쓰는 것이 이식 가능한 기본값이다.

링크된 파일은 조건부 context이므로 필수 범위, 권위, 안전, 필수 명령, 완료 게이트를 `AGENTS.md` 밖으로 옮기지 않는다. 지원 규칙을 하나도 열지 않은 상태에서도 core는 안전하고 실행 가능해야 한다.

## 4. 정본 소유권

각 규칙의 정본 위치는 하나다.

| 내용 | 위치 |
|---|---|
| 항상 필요한 저장소 계약 | 관할 `AGENTS.md` |
| 하위 트리 전용 차이 | 가장 가까운 정당한 중첩 `AGENTS.md` |
| 같은 범위에서 일치하는 작업에만 쓰는 상세 정책이나 절차 | 인접한 `rules/*.md` |
| 이미 다른 곳에서 관리되는 상세 architecture 또는 API 지식 | 직접 링크한 기존 프로젝트 문서 |
| 결정적 강제 | hook, CI, lint 규칙, schema, 실행 가능 설정 |

최소한의 routing 안내를 제외하고 지원 규칙을 core에 다시 요약하지 않는다. 루트 또는 중첩 지침을 되풀이하는 지원 파일을 만들지 않는다.

## 5. 언어 쌍

에이전트가 로드하는 규칙 파일은 관할 `AGENTS.md`와 같은 언어로 작성한다. 루트 `AGENTS.md`가 이 skill의 기본 영어 정본과 한국어 미러 계약을 따를 때, 새로 만들거나 실질적으로 변경한 각 `rules/name.md`에 `rules/name.ko.md`를 짝으로 둔다. `AGENTS.md`의 링크는 영어 파일을, `AGENTS.ko.md`의 링크는 한국어 미러를 가리킨다.

중첩 규칙 미러는 관할 중첩 `AGENTS.md`에 선택한 것과 같은 정책을 따른다. 번역 사이에서 명령, 경로, 식별자, 규범 강도를 보존한다.

## 6. 검증 게이트

- [ ] 지원 규칙을 만들기 전에 삭제와 중첩 배치를 검토했다.
- [ ] `rules/` 디렉터리가 관할 `AGENTS.md` 옆에 있거나 기존의 문서화된 지침 위치를 대신 사용했다.
- [ ] 모든 지원 파일에 하나의 책임, 직접 링크, 명시적인 읽기 조건이 있다.
- [ ] 항상 로드되어야 하는 필수 계약을 `AGENTS.md` 밖으로 옮기지 않았다.
- [ ] 지원 규칙이 루트, 중첩, 기존 프로젝트 문서를 중복하지 않는다.
- [ ] 기존의 비문서용 `rules/` 내용을 덮어쓰거나 에이전트 정책과 섞지 않았다.
- [ ] 미러가 필요할 때 영어/한국어 링크가 의미상 정렬된 파일로 해석된다.
- [ ] 루트와 적용 가능한 중첩 지침 파일이 설정된 런타임 예산에서 여유를 유지한다.
