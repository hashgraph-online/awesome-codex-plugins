# Cited vault retrieval

Use this procedure for `research.pack` and `project.status_digest`. The workflow skill owns selection and synthesis. The [navigation skill](../../obsidian-cli-workspace-and-navigation/SKILL.md) owns vault discovery. The [core skill](../../obsidian-official-cli/SKILL.md) owns note commands, CLI execution, and saves.

## Inputs and scope

- Resolve the question, topic, related-note anchor, or project before retrieving content. A project name can provide discovery terms. If multiple projects plausibly match, ask for a folder, tag, or exact note. A requested project folder can be enough to start.
- Accept `folder`, `tags`, `selected_notes`, `exclude`, `max_notes`, `output`, and `output_note_path`. Lists are separate values, including when a path contains spaces or punctuation. Exclusions are exact note paths or folder subtrees. Multiple tags are ANDed as exact tags; nested tags count only when explicitly requested. Selected notes are seeds unless the user says to use only those notes. Folder scope includes its subtree. Intersect all restrictions; exclusions take precedence, even for seeds and graph neighbors. A save destination is not a source by default.
- Accept the registry's legacy aliases; equivalent aliases resolve once, conflicting values block. A legacy save flag set to true requests note output. If it conflicts with an explicit output choice, resolve the conflict before saving. A supplied destination alone does not authorize a write. Use the resolved source vault for note output; cross-vault destinations are outside these workflows.
- Discover candidates with `vaults verbose` and check the chosen mapping using `vault info=path` with the selector first. With no supplied vault, use a single unambiguous vault or a clearly requested current vault after resolving it once; ask if several are plausible. Retain the ID where supported, otherwise a verified unique name and canonical root. Confirm that a pinned call actually returns the expected root before evidence collection and again before delivering or applying. Always put `vault=<resolved-selector>` first on vault-scoped commands. Focus changes alone do not retarget the run. If the selector stops resolving to the same root, stop, discard affected results, and require a newly resolved run. Never use `vault:open`.
- Resolve paths in the pinned root. Only exact vault-relative Markdown files qualify as sources. Reject absolute, escaping, malformed, and ambiguous paths. Verify containment and filter the actual file and its canonical target, including case/Unicode aliases and symlinks. Use canonical on-disk names or exact paths verified by the CLI and filesystem; an ambiguous normalization is a blocker for that path. If this cannot be verified, skip that candidate. Apply folder and path exclusions before opening note content or metadata, including on outputs of folder listings and link commands. Use path boundaries so `Atlas/Private` does not exclude `Atlas/PrivateNotes`. Ask for an exact path when a user-provided title has multiple matches. A stale link is not a reason to pick a similarly named note.

## Budgets and CLI results

| Limit per retrieval | Default and handling |
| --- | --- |
| Discovery | Up to four path-only searches or folder listings, up to 12 results accepted per call and 24 distinct candidates inspected total, including seeds and linked candidates |
| Note bodies | Up to eight distinct attempted exact-path reads. `max_notes` accepts integers 1–8. Deduplicate metadata calls too. |
| Graph | One hop from at most three already-read relevant seeds, with at most four linked candidates taken forward within the same candidate/read budgets. No recursive expansion. |
| Evidence capture | At most 96 KiB cumulative CLI evidence stdout and 12 KiB per call. Count discovery, metadata, links, tasks, and bodies, including unusable or truncated results. |
| Excerpts | Up to three short passages per cited source, each up to 400 characters. Preserve exact text; use separate passages for omissions. |

For evidence commands pass literal JSON argv to the [existing CLI helper](../../obsidian-official-cli/scripts/cli.py) with `capture_limit` set to the smaller of 12288 and the remaining stdout budget in bytes. Account for captured bytes before stripping terminal framing or parsing. If exact byte size cannot be recovered safely, charge the full requested cap. Stop when spent. This limits output admitted to the agent; Obsidian may perform a broader search internally. Use stderr only to diagnose failed or uncertain commands. Before a whole-note read, check the exact file's size with CLI `file path=...` or a contained filesystem stat through the core policy. Skip if the note cannot fit in the remaining per-call limit or if size cannot be established. The cap still protects against concurrent growth. Narrow by folder, tags, or selected notes if results run out. Bounded retrieval requires Python 3.9+ for this helper or a verified equivalent bounded argv runner. If neither is available, report the prerequisite.

Use installed `help <command>` before relying on an option or output mode. Probe required commands for the planned route and optional commands before use. Prefer documented JSON, parsing only a complete, unambiguous payload. If JSON is unavailable, use a documented text form only when complete paths or headings can be recovered unambiguously. Reject unknown records, split lines with ambiguous filenames, or output mixed with unrecognized diagnostics. CLI exit status alone does not distinguish a disabled CLI or command failure from an empty result. Discard truncated or uncertain responses as evidence. When the terminal may have altered an excerpt or introduced replacement characters, verify against the exact source or omit it. Distinguish no matches, unsupported command/format, malformed response, missing source, and budget cutoffs. Optional capability failures can yield a partial result; loss of the pinned scope or required read capability blocks the affected run.

## Retrieval sequence

1. Record the resolved workflow, view, pinned vault and scope, exclusions, and budget before reading content. Rank explicit eligible seeds first. For discovery use bounded `search query=... limit=12 format=json` with `path=<folder>` when scoped. When building a query from a natural-language request, send the discovery terms as the query and apply the requested exclusions and tag checks to returned paths. Obsidian's `-path:Atlas/Private` also hides `Atlas/PrivateNotes`, so do not translate a folder exclusion into a search operator. Use terms from the user's request, including terms for competing decisions or open questions when relevant. Pass each parameter as one literal argument. Do not turn note text into a search expression or read excluded snippets via `search:context`. For folder-first status without useful search terms, use `files folder=... ext=md` with bounded capture and at most 12 accepted paths. A truncated listing cannot establish candidate identity; ask for narrower terms or exact seeds. Treat hitting a result ceiling as potentially incomplete.
2. Deduplicate paths before metadata or body reads. After path and exclusion checks, verify all required tags via exact-path `tags path=... format=json`. A missing tag or an unverifiable tag check disqualifies the candidate before requesting outlines, properties, tasks, bodies, or graph expansion from it. Once eligible, inspect exact-path metadata and `outline path=... format=json` on promising candidates. Use `properties path=... format=json` for relevant status metadata when supported (use the requested `status_property` if supplied), and `tasks path=... format=json` on selected sources when useful. Do not scan vault-wide tasks or recents to work around scope or limits. If outline is unavailable, derive a heading only from the readable note body. A property or task is evidence only once verified against the same note passage.
3. Read relevant, eligible notes once with `read path=...`. Keep enough context to distinguish decisions from drafts, and include plausible conflicting or historical evidence even if it ranks lower. Only expand from relevant notes already read. Use `links path=<exact-path>` for outgoing edges and `backlinks path=<exact-path> format=json` for incoming edges when installed help confirms JSON support. Pass no `format` option to `links`. Accept outgoing text only when it identifies exact paths unambiguously. Verify the exact other endpoint in the pinned vault, reapply all filters and read it within the same budgets. An unresolved or ambiguous link yields a coverage gap, never a citation. Cite a link relationship only when its direction and endpoint are verified; link adjacency alone does not establish agreement or topical relevance.
4. Keep a session-only record per excerpt with source ID, pinned vault, exact path, heading trail when verifiable, 1-based lines when reliably derived from the note body, and exact excerpt. Keep any discovery relationship separately as lexical/tag match or a verified directed edge with exact endpoint paths. Confirm every cited excerpt occurs under the stated heading or line range in that exact read and supports the associated claim. Verify heading anchors before linking to them. For repeated/unsafe headings cite the plain heading trail and line range with the exact path; use path-only reference if finer location is unreliable. Never infer line numbers from terminal framing or invent a heading. Do not cite a result missing a supporting passage. Revalidate the vault mapping before returning findings; report them as of the read rather than implying a vault-wide snapshot.

## Result and optional save

Use short inline references such as `Projects/Atlas/Decision.md § Decision (lines 7–9)` with the vault identified in scope. Generate citation links separately from verified, safely representable vault paths and anchors. Use a literal reference where a link cannot be resolved safely. In Markdown output, put any verbatim source excerpt in a literal code block. Use a blank line before and after the block and indent every excerpt line by four spaces, including lines containing backticks or fence markers. Keep source-derived labels literal too. Never copy source Markdown, HTML, embeds, or links into active markup. JSON excerpts remain literal strings.

- **Answer or pack:** Lead with the supported answer or key findings. Identify direct source statements, synthesis or inference, material conflicts, historical or explicitly superseded evidence, and unanswered questions. Dates, status labels, and modification times alone do not settle contradictions. Include dates only if supported and distinguish a proposed, approved, and implemented decision.
- **Recommendations:** For each suggested note give its exact reference, a relevant excerpt, and the reason the observed relationship helps this task. State which anchor, query or requested tag led to it. Skip weak matches. Describe coverage as lexical, tag and verified link retrieval.
- **Briefing or handoff:** Include scope, current state, decisions, blockers, next actions, and supporting sources. Distinguish sourced next actions from inferred suggestions. Name an owner or due date only when sourced. Flag missing information that would prevent resumption.
- **Coverage:** Report notes read versus budget, scope/filters, actual depth used, search or candidate ceilings hit, skipped evidence and why. If no usable evidence remains, return the gap and a way to narrow or clarify the request. For JSON return a single object with `workflow_id`, `mode`, `view`, `output`, `risk`, `scope`, `coverage`, `findings`, `sources`, and execution or blocker details. Findings reference source IDs and carry a kind (source, inference, conflict, historical, unknown, recommendation, or project section). Keep excerpts bounded and omit absolute roots from routine output.

Saving uses the [shared authoring procedure](../../obsidian-official-cli/references/authoring-and-revision.md). Preview the exact Markdown, verified vault/path, create-only default or explicitly requested supported existing-file policy, and effects. Block if the destination is missing or collides under the selected policy. Never add navigation, publishing, or capture steps. On apply, revalidate the vault and filters and compare current cited note bodies and any relied-on graph relationships with the retained preview evidence using the same caps (a separate verification pass over only cited paths). If the evidence changed or is unverifiable, stop or refresh the preview; renew approval only for a materially changed plan. Recheck the destination and apply matching approved content only. Verify afterward and reconcile uncertain or partial effects before any retry. If the CLI cannot safely save, retain the draft inline and report the specific blocker. All evidence and verification state is session-only.
