# Table dashboard authoring

Ask for a dashboard over an explicit folder. For example, “Preview an Atlas dashboard at Dashboards/Atlas.base with open work grouped by status, sorted by due date, and showing owner and estimated effort.” Select the authoring skill or use `workflow_id=base.dashboard mode=preview vault=Work`.

## Resolve data and capability

Resolve the canonical vault root and exact `.base` destination. Check every parent component and reject symlink or path aliases that would make the written artifact differ from the reviewed target. The create route requires absence, and an edit requires one exact existing table view. Use the core skill to inspect representative notes via exact-path `properties format=json` and, if needed, verify types in the note source or the vault's existing property configuration. Record expected rows and example cells, including known excluded files, missing values, and ordering ties. Report inconsistent or absent schema information and narrow the collection or resolve it explicitly. Metadata repair is a separate user decision.

Probe `version`, `help create`, `help base:query`, and any other planned command. On macOS with Obsidian desktop and installer 1.15.0, the bundled launcher verified `create path=... content=...` and explicit `overwrite` both preserve the `.base` extension and UTF-8 bytes. `base:create` creates an item through an existing view. The definition workflow uses the general create command. Other CLI versions need equivalent capability evidence before writing. A live scratch capability probe is a separate authorized operation.

## Build the candidate

Run [base_definition.py](../scripts/base_definition.py) from the installed skill with Python 3.9+ and a literal UTF-8 JSON object on stdin. It returns exact candidate content and operation, plus the shared fingerprint and diff for an edit. It never opens vault files or dispatches commands. [The Atlas request](../assets/fixtures/dashboard-request.json) is a runnable example.

- Creation takes `folder`, `schema`, and one to eight named `views`. `schema` maps observed note property names to `text`, `number`, `date`, `boolean`, or `list`. Names use ASCII letters, digits and underscore, starting with a letter or underscore. Reference columns as `note.status`, `file.name`, or `formula.weighted`. The renderer scopes all views to Markdown in the folder and subfolders. Use an existing, contained folder. A scoped table still may contain missing values.
- Each view requires `name` and ordered `columns`. Optional `where` is a list of typed comparisons ANDed together. Missing values do not match a comparison. `sort` is an ordered list of `{"property":"note.due","direction":"ASC"}` objects. `group` takes one such object. Optional `limit` is 1–500 and changes expected membership. `summaries` maps properties to compatible supported built-ins such as `Sum`, `Average`, `Earliest`, and `Filled`.
- Optional `formulas` maps names to numeric `{"left":"note.hours","op":"*","right":2}` objects. Operands are numeric constants or known numeric note, file, or formula references. Operators are `+`, `-`, `*`, and `/`. The renderer rejects unknown references, nonnumeric operands, literal zero divisors, and cycles. Report sparse numeric inputs or possible zero divisors and check actual values against representative rows. The renderer does not evaluate Obsidian formulas.
- An edit takes literal `before` bytes decoded as UTF-8, exact `view`, observed `schema`, and `changes` with any of `columns`, `where`, `sort`, `group`, `summaries`, or `limit`. Optionally map known existing formula names to observed types in `formula_types` for typed comparisons or summaries. Keep global filters, formulas, other views, and existing extension fields intact. Review the effective scope of existing global and view filters before changing a filter.
- Creation emits JSON-form YAML and uses the Python standard library. Editing YAML requires PyYAML 6 in the selected Python environment. If missing, report the prerequisite. Install only at the user's direction. The editor uses YAML source marks, rewrites only selected field values or inserts new supported fields, and reparses to verify the expected structure. Ambiguous views, duplicate keys, aliases, anchors, explicit tags, unsupported layouts, and grouping changes that would conflict with a retained `groupOrder` block the edit. Existing formulas remain opaque. The editor does not add, replace, or remove global formulas in an existing definition.
- Input is bounded to 64 KiB and the definition to 12 KiB. Both paths reuse the core launcher's content preflight. Lossless transport must be established for the actual candidate. CRLF, literal transport escapes, and unsupported encodings can block writes. Return the candidate or blocker in that case.

## Apply and verify

Preview the full create candidate or minimal update diff and the expected result matrix. Runtime evaluation of a new candidate needs an applied file or a separately approved disposable test. Treat the write and query outcomes independently.

After approval, recheck canonical containment, vault identity and the target's absence or exact before bytes. Use the shared literal-argv helper with `vault=` first. For creation omit `overwrite`. For a revision, disclose whole-file transport even when the diff is scoped. Avoid concurrent edits while applying. The state check is optimistic and leaves a race before dispatch. Verify the resulting file's exact path and bytes and recheck the vault mapping.

Use the Bases and Bookmarks skill to query `base:query path=<exact-base> view=<exact-name> format=json` for every affected view. Prefer a bounded representative fixture for verification. Compare exact row paths, order and calculated cells against independently expected values. Check the response for failures, unsupported output, and truncation even on a zero exit. `base:views` is active-file based on 1.15.0 and must not be used as a pinned-path query. Verify it only when navigation to the exact file is authorized and its active identity has been confirmed. Group headers and summary display are separate from row output. Report which UI checks were observed and which were unavailable. Recompute an expected summary from returned cells when possible and label that calculation separately.
