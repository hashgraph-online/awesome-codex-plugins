# Dev Verify Examples

## Skill 变更

仓库校验脚本检查 frontmatter、引用资源和分发一致性,另一次独立评估用真实场景检查指令是否会误阻塞或扩权。

可以报告结构校验及已评估的场景,不能将脚本 PASS 等同于“所有模型执行效果均改善”。

## 验证证据仍有效

测试覆盖最终修改后文件,随后只进行只读 review。已有命令输出可以复用,不用因为另一个回合或 handoff 再跑一遍。

如果 review 后修改了生产代码、fixture 或相关配置,重新运行受影响检查;不要沿用过期绿灯。

## 本地与设备

协议构建单测通过,但没有连接设备。报告该请求字段与本地转换已验证,设备执行未验证。不能从局部成功推导完整设备工作流成功。

## 不同 Git 快照

working tree 测试通过,但 index 是较早版本。对“当前工作区测试通过”的声明有效,对“暂存内容可提交”的声明不足。验证对应 index 快照或明确缺口。

## 隐藏失败

命令退出码为零但关键集成测试被跳过。读取结果后将该行为标成未验证,不要只根据 exit 0 宣布全部通过。

## 复用已有命令

在本仓库验证 skill 文档改动时,先读 `scripts/validate-repo.sh` 的检查范围,再运行已有入口 `bash scripts/validate-repo.sh` 并检查实际输出。链接原脚本即可,不用另建一份 `verify.sh` 或命令清单。

如果声明涉及 Agent 是否会重复索取确认,还需要相应行为案例的执行记录;结构脚本通过不能替代这项证据。检查一次即可完成的文档变更不需要新建项目验证配方。

## 过期配方与只读设备验证

用户要求只读验证移液协议转换。项目旧说明仍使用已删除的启动脚本,但当前 CI 有可用的转换单测入口。沿 CI 中维护的命令运行本地检查,记录输出和当前文件状态;在报告中指出旧说明已过期。

没有连接设备时,将本地转换与设备执行分开报告。旧配方曾经运行过,也不能作为本次设备证据。验证 lane 不自动修正文档、新建 harness、启动设备动作或改 index;把过期入口交给已有授权的主执行 lane。若后者获准保存新设备路径但尚未跑过,该路径只能标为 draft,不影响已完成的本地检查。
