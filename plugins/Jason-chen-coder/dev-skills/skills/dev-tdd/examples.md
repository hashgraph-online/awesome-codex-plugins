# Dev TDD Examples

## 新行为

用户:「给 retry helper 加最多三次尝试。」

先读当前 helper 和调用约定,确认“三次”包含首次调用。用受控 operation 测试前两次失败第三次成功,观察修复前的行为失败;实现后同一测试通过。再检查三次仍失败时抛出最后一次错误,以及立即成功时不多调用。

若“三次重试”在业务契约中不清楚是否包含首次调用,先找项目已有约定;无法确定且会改变行为时再澄清。

## 保持行为的重构

用户:「把解析逻辑移到共享模块,保持行为。」

先运行已有解析测试确认基线,必要时补边界 characterization test。它在旧实现上应当通过;移动实现后再次运行,并检查调用路径和公开导出。不要为了“先红”故意制造业务失败。

## 低影响修改

用户:「把按钮文案改成‘重新连接’。」

使用现有渲染检查或直接检查变更后的相关状态与布局即可;不要新增只断言字面字符串的测试来满足 TDD 仪式。

## 测试失败原因错误

新测试因 fixture 缺少应用 provider 而崩溃,这不证明目标业务失败。先修正测试环境,再观察业务断言。不能把测试 setup 报错记作回归测试捕获缺陷的证据。
