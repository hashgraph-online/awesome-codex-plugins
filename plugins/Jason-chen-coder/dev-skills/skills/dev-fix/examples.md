# Dev Fix Examples

示例展示判断方式;命令与结果仅为场景示意,实际使用时必须执行并读取真实输出。

## 简单边界错误

用户:「购物车三个单价 10 元的商品只显示 20 元,帮我修。」

追溯 UI 展示值到 total getter,发现循环条件为 `i < items.length - 1`,漏掉最后一项。先在现有测试中断言三个商品合计 30,观察实际得到 20;将边界修为 `i < items.length`,再验证相同测试和相关空购物车用例。

这里一次明确的 red/green 已证明测试能捕获缺陷,无需为了流程再运行三次或 stash 反证。总结应说明完整因果链,而非只列修改位置。

## 只解释原因

用户:「为什么设置 60 秒还是超时?先别动代码。」

读取实际请求入口、客户端构造、生成请求代码和底层超时配置。若生成代码覆盖默认值,报告覆盖在哪一步发生、最终请求使用哪个值以及证据位置。不能只看到默认配置为 60 秒就断言它已生效,也不写 failing test 或 fix artifact 等文件。

## 并发问题

用户:「偶尔重复扣库存,排查并修复。」

从重入请求追到读后写流程,用同步屏障控制两个请求都读到旧库存,再同时执行写入。通过这个可控交错复现,判断事务/条件更新是否能够建立正确不变量。无需凑满五个假设;验证正常并发、库存不足和重试语义。无法取得真实数据库环境时,明确模拟证明与真实数据库验证的界限。

## 本地无法复现

用户提供设备错误日志,本地没有设备。继续分析动作构建、字段映射和调用链,为可验证的协议转换补充测试。若只证明请求字段正确,报告“本地转换测试通过;设备执行结果未验证”,不能宣称设备故障已修复。

## 需要额外证明测试敏感度

已有测试第一次就通过,尚未证明能捕获原始问题。先检查断言和真实调用路径。确有必要时,在临时副本保留回归测试并仅反转本次修复;确认出现预期失败后检查最终版本。不要对含用户改动的工作区执行通用 stash/reset。

## 需要扩大设计范围

证据表明当前公开契约无法表达业务要求。先完成因果分析和必要的选项比较,说明必须改变哪个契约、兼容性影响及当前授权缺口。仅暂停依赖该决定的修改;不以“修改了两个文件”或“尝试三次失败”作为必须升级的理由。
