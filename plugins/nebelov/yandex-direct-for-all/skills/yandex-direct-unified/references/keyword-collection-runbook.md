# Сбор и проверка ключевых фраз

1. Создать таблицу продуктовых направлений и маршрутов на посадочные.
2. Для каждого направления выписать синонимы, действия, коммерческие признаки, варианты языка и написания.
3. Сохранить происхождение каждой маски до обращения к Wordstat.
4. Собрать Wordstat v2 по целевой географии: topRequests, associations, regions, при необходимости dynamics.
5. Добавить поисковые фразы из подтверждённого кабинета и результаты поиска с сохранением источника.
6. Присвоить каждой исходной строке candidate_id; не удалять строки до решения.
7. Разбирать строки последовательными частями. Для каждой указать смысл, сегмент, посадочную, решение и причину.
8. Отдельно проверить защищённые слова перед предложением минус-слов.
9. Сопоставить все исходные строки с таблицами включения, исключения и отложенных решений.
10. Создать отчёт о непокрытых целевых запросах. Любой необъяснённый разрыв блокирует сборку.

Допустимые сценарии: сбор исходных ответов, нормализация формата без потери строк, нумерация, разбиение, объединение, проверка схемы и полноты. Запрещены автоматический смысловой отбор, оценка коммерции, готовый пакет ключей и автоматический статус покрытия.

# Подробный порядок

## Главный принцип

Результат сбора ключей пригоден, только если доказано: откуда пришла каждая сырая строка; как она попала в кандидаты; кто и почему принял смысловое решение; почему строка включена, исключена, отложена или отправлена в минус-слова; какие сегменты и синонимы покрыты; какие целевые сегменты остались непокрытыми и почему; какие стоп-слова безопасны и какие защищены.

Порядок: сырой Wordstat и поисковые запросы → кандидаты `SAFE_STOP` только после проверки защищённых слов → предварительная пометка без удаления строк из очереди → личный построчный разбор всех строк → карты включения, исключения и покрытия → итоговый стоп-пакет. Стоп-пакет до сырых данных запрещён; пометка до проверки защищённых слов запрещена; помеченные строки остаются в очереди личного просмотра.

## Вводные для режима сборки

Для режима сборки поля `product`, `buyer`, `geo`, `quality_lead`, `forbidden_or_restricted` и `landing` должны быть `confirmed`. При `candidate`, `unknown`, `waiting_input` или `blocked` хотя бы по одному из них запрещены полный пакет Wordstat и семантики, окончательная структура, сборка и черновики; вводные закрываются, а независимые задачи идут параллельно.

Режим «только исследование» или «только маски» допускает первичную выборку конкурентов и черновую карту JTBD по данным-кандидатам из проверяемых источников (услуга, предварительное гео, ограничения, покупатель). Каждое неподтверждённое значение остаётся `candidate` или `hypothesis`, неизвестные ограничения и сегменты — `unknown`; запреты на сборку и запись это не снимает. Для окончательного результата исследования по Wordstat или конкурентам подтверждены минимум продукт, гео, ограничения и покупатель.

## Базовые файлы

Создать или обновить `client-kb.md`, `source-register.tsv`, `human-review.tsv`, `access-status.md`, `product-map.md`, `product-language-map.tsv`, `routing-map.tsv`.

- `product-map.md`: что продаётся; кто покупает; целевые гео; качественная заявка; нецелевой клиент; запрещённые темы и обещания; защищённые слова (продукт, услуга, бренд, гео, материалы, характеристики, синонимы, термины клиента).
- `routing-map.tsv`: `intent cluster landing_url allowed_geo forbidden_words comment target_status landing_or_needed_landing allowed_campaign_or_group`. Без `cluster`, `landing_url`, `allowed_geo`, `forbidden_words` и `comment` маршрутизация непригодна для проверки защищённых слов.
- `product-language-map.tsv`: `route landing_url facet_type term source source_evidence status comment`. Обязательные `facet_type`: `canonical_name`, `professional_name`, `jargon`, `spelling_variant`, `construction`, `material`, `application`; для неприменимой грани — строка `not_applicable` с причиной. До Wordstat и итогового ядра все маршруты товаров и услуг покрыты картой построчно. Общий термин без определителя не становится целевым только потому, что стоит рядом с продуктом на сайте.
- `client-scope.tsv`: `campaign_name landing_or_domain campaign_status why_client_scope source status`. Снимок кабинета собирается только после него; область не доказана — остановка с блокером.

Приоритет источников продаж и заявок: CRM или база продукта → Roistat → Метрика → отчёты Директа как вторичный слой.

## Источники семантики

Источники: бриф и переписка клиента; сайт и посадочные; текущий Директ и поисковые запросы; Wordstat по целевому гео; органическая и рекламная выдача Яндекса; конкуренты по конкретным посадочным; реальные формулировки клиента, менеджеров, заявок и отзывов. Каждый источник записывается в `raw-source-register.tsv`: `source_id source_type source_path_or_url geo date_collected collector status`.

## Wordstat

Подробный справочник — навык yandex-wordstat. Wordstat второго поколения доступен через Yandex Cloud Search API или через XMLRiver (навык xmlriver-serp-research); провайдер выбирается в сборщике параметром `--provider`.

- Перед массовым сбором: контрольный вызов на чтение и учёт почасового бюджета (метода `userInfo` во втором поколении нет); дерево регионов, если нужен код региона.
- Сырьё сохраняется по каждой маске; ошибки, пустые ответы, HTTP 429 с `Retry-After` и повторы записываются. Для Yandex Cloud — не больше 10 запросов в секунду и 100 тарифицируемых запросов в час, с сохранением состояния для продолжения без дублей.
- Методы Yandex Cloud (`POST https://searchapi.api.cloud.yandex.net/v2/wordstat/...`, обязателен `folderId`):
  - `topRequests` — `phrase`, `numPhrases` 1–2000, `regions` до 100, `devices` до 3 → `totalCount`, `results[].phrase/count`, `associations[].phrase/count`;
  - `dynamics` — `phrase`, `period` (`PERIOD_MONTHLY`, `PERIOD_WEEKLY`, `PERIOD_DAILY`), `fromDate` и `toDate` в RFC3339, `regions`, `devices` → `results[].date/count/share`;
  - `regions` — `phrase`, `region` (`REGION_ALL`, `REGION_CITIES`, `REGION_REGIONS`), `devices` → `results[].region/count/share/affinityIndex`; путь `/v2/wordstat/regions`;
  - `getRegionsTree` — только `folderId`; не тарифицируется, но расходует квоту запросов.
- Доступ к Yandex Cloud: ключ API с областью `yc.search-api.execute` и ролью `search-api.webSearch.user` либо IAM-токен.
- Файлы волны: `wordstat-run-manifest.tsv`, `raw_top_requests_waveN.tsv`, `raw_associations_waveN.tsv`, `mask_summary_waveN.tsv`, `wordstat_errors_retry_log.tsv`, `coverage_gap_backlog.tsv`. Третья волна нужна, если ассоциации, конкуренты, поисковые запросы или источники клиента дали новые целевые синонимы.
- Волна не закрывается, пока каждая целевая маска не дала сырой результат либо доказанный `blocked` после записанного повтора.

## Одно решение для повторяющегося запроса

После слияния частей разбора и до карт включения и исключения создать `normalized-query-consistency-ledger.tsv` для `normalized_query`, которые повторяются в разных масках, волнах и частях: `normalized_query occurrence_count candidate_ids source_waves_or_masks decisions_seen canonical_decision exception_reason reviewer status`. Каждый повторяющийся запрос получает одно каноническое решение либо `exception_reason`, почему разные решения допустимы по контексту.

Проверки смыслового контроля проверяют схему, значения словарей, покрытие `candidate_id`, наличие полей доказательств и отсутствие потери строк; они не отклоняют корректный ручной разбор из-за другой формулировки причины. Ограничения «волна до 60 000 строк, один проверяющий до 10 000 кандидатов» действуют при любом общем размере. Полная схема выхода части разбора: `candidate_id row_id mask query count synonym_family root_variant broad_root_risk verdict reason cluster landing_hint intent confidence new_cluster_needed service_intent_proof business_scenario landing_or_needed_landing route_reason negative_candidate stop_word_candidate evidence_source`; проверяющий сохраняет тот же `candidate_id`, набор и порядок строк.

## Проверка ложных включений и пропусков

До публикации — два независимых смысловых прохода:

- проверка ложных включений: каждое включение сверяется с товаром или услугой, маршрутом, посадочной и `product-language-map.tsv`; в итоговом ядре нет неподтверждённых материалов и конструкций и неоднозначных общих фраз без определителя;
- проверка пропусков: все исключения, пересекающиеся с защищёнными каноническими, профессиональными, жаргонными терминами и вариантами написания, пересмотрены; готовность блокируется, если подтверждённая целевая фраза осталась исключённой без доказанной причины.

Если после первичной разметки появились новые страницы, группы, услуги или решения пользователя, перед сборкой пакета перечитать по текущим группам и посадочным строки, ранее помеченные как смежные, информационные с названием услуги и конкурентные с названием процедуры. Минус-слова проверяются по смыслу, а не только совпадением с включёнными фразами: сверка со всеми целевыми строками сырья и смысловой проход по списку против каталога услуг. Название материала или препарата не минусуется, если клиент оказывает услугу с материалом заказчика. Внутренние поля (`source`, `source_evidence`, `reason`, решения проверяющего) хранятся в доказательных TSV и не выводятся в клиентскую таблицу согласования без прямого запроса.

## Группы, исследование и готовность к сборке

`search-group-map.tsv`: `map_row_id group_uid campaign_name adgroup_name cluster intent landing_url geo source group_decision decision_reason status`. Группы строятся по смыслу, посадочной или планируемой странице, гео, маршрутизации и коммерческому намерению. Целевой спрос без текущей посадочной остаётся целевым с точным маршрутом и `needs_new_page`, для будущей группы — `group_decision=needs_landing`; `support_route` ставится только по смыслу, а не из-за отсутствия адреса.

Результат «только исследование» — карта спроса, кандидаты, сегменты, пробелы, стоп-слова и рекомендации, но не сборка; сырые строки широких масок нельзя выдавать за подтверждённый спрос на услугу без вердикта. «Готово к сборке» — только когда пройдены: вводные, сырое покрытие, покрытие синонимов, полный список кандидатов, карты включения и исключения, покрытие сегментов, покрытие стоп-слов, карта групп, посадочные, досье сборки и надзорная проверка. Нельзя писать «готово к запуску» или «готово к черновику», если есть только исследование спроса.

Двойная проверка полноты:

1. Линейная трасса: сырая строка → `candidate_id` → часть разбора → решение → итоговый ключ, исключение, отложено или проверка минуса.
2. Покрытие: у каждой сырой строки есть `candidate_id` или решение; у каждого `candidate_id` ровно одно решение; у каждой целевой семьи синонимов — покрытие или пробел; у каждого крупного сегмента — покрытие по строкам и частотности; у каждого включённого ключа — посадочная и причина; каждый минус прошёл проверку защищённых слов; у каждого `support_route` заполнены 4 поля; нет строк, оставленных только в трассе; нет широкого корня в ключах без коммерческого вердикта; нет итогового PASS от скрипта смысловой классификации; каждый маршрут покрыт `product-language-map.tsv`; исключения с защищённой лексикой перепроверены; клиентское представление без внутренних источников и причин, если их не просили.
