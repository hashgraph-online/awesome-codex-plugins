# Правила работы

Правила действуют в любой задаче по Директу и дополняют [основной порядок](main-workflow.md) и [правила решений](decision-rules.md). Пути к скриптам и шаблонам указаны от корня модуля.

## Транспорт: сначала API, интерфейс только при доказанном отсутствии метода

Для каждой операции и поля сначала определить фактический тип кампании (Поиск, РСЯ, товарная, ретаргетинг, единая перфоманс-кампания), а не судить по названию. Если нужный метод Директа есть в API, работать через API, а запись — только через ворота записи модуля. Правка в интерфейсе — не штатный маршрут модуля: она допустима, только когда официальная документация или проверенный ответ API доказывают, что метода нет, и пользователь отдельно разрешил именно эту правку как ручную операцию вне ворот. Без такого разрешения это блокер `tooling`. При разрешённой ручной правке:

- сверить аккаунт, кабинет, кампанию, исходное и ожидаемое значение;
- после сохранения заново открыть сущность с сервера и перечитать все затронутые поля;
- поля, доступные через API, дополнительно сверить через API.

Отсутствие метода в скрипте, неверная форма запроса, ошибка доступа или временный сбой API не доказывают отсутствие метода: сначала исправить инструмент или причину сбоя. Открытая вкладка с входом, видимый логин и адрес с `ulogin` подтверждают только сессию интерфейса и не заменяют проверку доступа по API.

## Приоритеты при конфликте правил

1. Явная команда пользователя в текущем диалоге выше навыков, если она не требует опасного действия без разрешения. API остаётся первым транспортом: просьба «сделай через интерфейс» сама не доказывает отсутствие метода.
2. Этот навык выше узких навыков yandex-direct-client-lifecycle и yandex-performance-ops.
3. yandex-wordstat — справочник по методам, лимитам и квотам Wordstat.
4. roistat-reports-api и amocrm-api-control — справочники по своим API. Ключи, проекты и сопоставление источников берутся из данных текущего клиента, а не из примеров.
5. Конфликт, который этот порядок не снимает, — остановиться и спросить пользователя.

## Бюджет независимых проверок

Независимая проверка назначается на задачу или законченный пакет, а не на каждый вызов, строку или пакет API. На одну задачу:

- низкий риск — без независимой проверки;
- средний — одна итоговая проверка пакета;
- высокий — не больше одной проверки полного плана и одной итоговой проверки.

Простое точное действие: одно свежее чтение перед записью, одна узкая запись, одно объединённое чтение после неё. Операция, разбитая на несколько пакетов API из-за лимитов, считается одной операцией. Проверки плана, доступа, семантики, текстов, изображений, пробного прогона и чтения после записи объединяются в одну проверку пакета. Найденный дефект исполнитель исправляет сам и лично проверяет его и связанные свойства; новый полный аудит без новой причины не запускается. Пользователю сообщается результат и существенный остаток, а не перечень внутренних проверок.

## Доказательства на уровне элементов

Для аудита, оптимизации и решения об эффективности раскладывать доказательства на понятные элементы: текст объявления, посадочная, аудитория, площадка, устройство, расписание, регион, быстрые ссылки и уточнения, цель. Итоги кампании и группы — только сводка.

- Компонент, который встречается в нескольких объявлениях или группах, агрегировать по всем совпадающим строкам до вывода. Варианты с разными наборами ссылок, уточнений, посадочной или аудитории держать раздельно.
- Одну продажу, заявку или достижение цели нельзя засчитать нескольким дочерним элементам только из-за совпадения названия или общей кампании. Выбрать явную модель атрибуции (`single_owner`, `cohort_owner`, `shared_component_aggregate`, `ambiguous_combined_evidence`) и пометить вывод как комбинированный.
- Рекомендованный бюджет и рост объёма опираются на свежий снимок кабинета, историческую ёмкость, данные CRM, Roistat или Метрики либо явно помеченное допущение. Произвольная цифра не подаётся как расчёт и как потолок масштабирования.
- Корректирующая правка сохраняет работающий объём и меняет только дефектное поле. Если затронуты хорошие кампании, группы, объявления или посадочные — нужен реестр «сохранить или заменить» и чтение затронутых элементов после записи.

## Доступ: только кампании клиента, «0 кампаний» — блокер

В действующем кабинете сначала определить область клиента, а не читать весь доступный агентский аккаунт. В общем аккаунте с чужими кампаниями полный снимок запрещён: получить минимальный список кампаний и сузить его по признакам клиента (название, бренд, домен, посадочная, подтверждённые кампании). Не удаётся сузить надёжно — остановиться и спросить. Чужие кампании не читаются даже «для полноты».

Если пользователь сказал, что Директ есть, назвал логин или кампании, а API вернул 0 кампаний, это блокер доступа (не тот аккаунт или `Client-Login`, нет агентского доступа), а не факт о бизнесе. Выводы по кабинету и любая запись запрещены до исправления доступа; независимая работа (сайт, спрос) продолжается с пометкой «кабинет не проверен». Старый токен «того же» клиента нельзя брать по названию папки: сначала проверить запросом к API без вывода секрета, что он видит нужный аккаунт и `Client-Login`.

OAuth-приложение клиента не является кандидатом доступа: не открывать его настройки, не копировать идентификатор и секрет, не выпускать через него токены. По умолчанию используется встроенное опубликованное приложение пакета; аккаунт клиента нужен только для выбора аккаунта и согласия. Своё приложение пользователя допустимо только как явно настроенная замена через защищённую настройку (см. основной порядок, раздел «Доступ»).

## Метрика только через API

Метрика работает через API, если токен позволяет нужный метод: не открывать интерфейс Метрики для чтения и не создавать и не менять в нём счётчики и цели только потому, что вкладка авторизована. Исключение — страница согласия OAuth. Если метод API есть, а инструмент его не реализует, доработать скрипт или записать блокер `metrika_api_tooling_blocker`.

- Для профиля с `redirect_uri=https://oauth.yandex.ru/verification_code` локальный адрес возврата не используется; ошибка «redirect_uri не совпадает» означает неверный поток, а не отсутствие доступа.
- Токен, вставленный пользователем, не сохранять молча: сначала проверить запросом `/management/v1/counters`. Ответ 401 — сбой процедуры авторизации, а не вина пользователя.
- Цели и счётчики, прочитанные старым токеном из чужого проекта, не считаются проверенными.
- При создании или изменении счётчика флаги `code_options.visor`, `track_hash`, `clickmap` передавать в формате, который принимает метод: схема описывает их как логические, а на практике метод принимал целые 1/0 там, где `true/false` давали `400 invalid_json`. После записи перечитать и сверять значение по истинности (1 и `true` — включено), а не по типу. При `400 invalid_json` счётчик не считать созданным: перед повтором перечитать список счётчиков, чтобы не получить дубль.

## Инварианты сборки объявлений

1. Для устаревшего пакета отдельных текстовых объявлений — ровно 5 уникальных объявлений на поисковую группу. Для комбинаторных форматов счётчик 5 не применяется: сначала проверить активный формат, обязательные количества ассетов и ограничения модерации.
2. `DisplayUrlPath` обязателен для каждого объявления: русский текст до 20 символов, без латинской автогенерации и обрезанного хвоста, содержит часть ключевой фразы своей группы. Не строить его из названия кампании или бренда и не резать молча по лимиту.
3. Быстрые ссылки обязательны, если у клиента есть 4 и больше отдельных предложений или разделов. Целевой стандарт — 8 ссылок с описаниями на группу; иначе все подтверждённые страницы и запись `asset_gap`. Якоря (`#…`), фрагменты одностраничных приложений и идентификаторы элементов страницы в основных и быстрых ссылках запрещены; одинаковые адреса страниц внутри набора допустимы. Если площадка не принимает адреса, сохранить точную ошибку и согласовать адреса с пользователем, а не выдумывать якоря. Уточнения — при 4 и больше подтверждённых фактах: 12–20 кандидатов или максимум, который позволяют факты и лимиты; иначе `asset_gap`.
4. РСЯ — не копия Поиска, а отдельный пакет текстов. Второй заголовок в РСЯ может не показываться, поэтому первый заголовок и текст сами несут предложение; второй заголовок не единственный носитель смысла, цены, преимущества или призыва.
5. В РСЯ у каждого объявления по умолчанию своё изображение; повтор допустим только как документированный `asset_gap` после поиска источников и попытки сделать другое. Изображения не искажать, не растягивать, не обрезать важное и не дорисовывать холст автоматически. Исходник не того размера использовать как образец для нового изображения нужного формата. Каждое изображение открыть и проверить глазами до загрузки. Для объявлений РСЯ с изображением или видео проверить кнопку действия: метод API есть — задать и перечитать кнопку через API; нет — по правилу о транспорте выше.
6. Тексты не готовы, если они общие, взаимозаменяемые, не связаны с ключами группы, не используют язык клиента и его конкурентное преимущество. Нужны карты углов и языка клиента. Ранний пакет, признанный общим или необоснованным после перечитывания посадочных, помечается `INVALID_COPY_BASIS`. В финальный текст попадают только проверенные факты; непроверенное преимущество остаётся пустым, `needs_proof` или `blocked`.
7. Запрещённые для модерации слова проверять во всех материалах: заголовки, тексты, ссылки и их описания, уточнения, отображаемые ссылки, названия креативов, кнопки, метки UTM, файлы импорта и выгрузки. Поиск — как подстроки без учёта регистра. Находка = BLOCKED. Список слов задаёт пользователь или клиент.

## План каналов и архитектура кампаний

Для нового клиента, новой стратегии или сборки вести `channel-plan.tsv`: Поиск, РСЯ, товарная кампания или галерея, конкуренты, ретаргетинг — по каждому решение `build_now`, `defer`, `exclude`, `needs_assets` или `blocked` с причиной и источником. План только из Поиска допустим, если пользователь явно ограничил объём. РСЯ нельзя молча пропускать: нет изображений, аудиторий или фида — это `needs_assets` или `blocked`.

`campaign-architecture.tsv` обосновывает разделение или объединение по каналу, гео, продукту, этапу воронки, стратегии, бюджету, посадочным и рискам. Одна кампания «по умолчанию» и чрезмерная нарезка запрещены. При объединении проверенного пакета меняются только родительская кампания и её имя; группы, объявления, фразы, изображения, посадочные и `group_uid` остаются прежними либо попадают в отдельную утверждённую дельту.

## Двухпроходная приёмка сборки

Для нового клиента, сборки по нескольким сайтам, комбинаторных объявлений и записи новых черновиков вести `full-build-acceptance.tsv` в два прохода: `pre_write=PASS` до записи и `post_write=PASS` до закрытия. Сверка только числа кампаний, частичная первая волна или неточное совпадение `entity_key` и обязательных значений = BLOCKED. Неизвестное обязательное значение не выдумывать: задать точный вопрос до записи. Полный порядок — в [приёмке новой сборки](new-client-full-build-acceptance.md).

## Деньги: стратегия, ставки и цели — независимые поля

Цель, стратегия, бюджет и денежные параметры подтверждаются отдельно и для конкретной записи. Нельзя выводить одно поле из другого, подставлять минимум API или отраслевую догадку.

- `PriorityGoals.Value`, `BidCeiling`, `Cpa`/`AverageCpa`, цена заявки, цель стратегии и `WeeklySpendLimit` — разные поля, и одно не выводится из другого. Смысл `PriorityGoals.Value` зависит от стратегии: в стратегиях с несколькими целями по средней цене конверсии и с оплатой за конверсию это целевая цена конверсии по цели, в стратегии максимальной прибыли — маржа, в остальных — ценность цели. Перед записью свериться с контрактом метода для выбранной стратегии. Добавлять, менять или удалять `PriorityGoals` без подтверждённого назначения и точного значения запрещено.
- Маржа, ROI, CAC и юнит-экономика считаются только отдельной согласованной задачей; исключение — стратегия максимальной прибыли, где маржа сама становится обязательным значением от заказчика.
- Если подтверждены цели-заявки и нужна оптимизация по заявкам, запись блокируют: `PriorityGoals=null`; цель «Вовлечённые сессии» вместо цели-заявки (`engaged_sessions_substituted_for_lead_goal`); `BidCeiling=null` при заданной пользователем максимальной ставке (`bid_ceiling_owner_value_missing`).
- Нужна понятная карта «кампания → основная цель-заявка → дополнительные цели → подтверждённое достижение формы». После записи читать стратегию, `GoalId` и множество `PriorityGoals` поэлементно. В `Campaigns.add` элементы `PriorityGoals` передаются без `Operation`, в `Campaigns.update` — с `Operation=SET`.
- Ответ Директа по стратегии нельзя сравнивать с запросом сырым равенством: сервер добавляет нормализованные поля. Сверять тип стратегии, недельный лимит, цель, потолок ставки, каналы, места показа и множество целей.
- Для товарных кампаний до текстов и запуска подтвердить реальные цены и условия оплаты по актуальному источнику.

## Технические лимиты API и записи

- `Campaigns.add` и фильтр `AdGroups.get.SelectionCriteria.CampaignIds` — пакеты не больше 10 элементов, с чтением каждого пакета. Лимит проверять отдельно для каждого метода.
- Сетевой обрыв после записи — не повод повторять `add`, `update` или `delete`. Повторяется только чтение; затем кабинет перечитывается, и запись продолжается так, чтобы готовое пропускалось.
- При замене кампании сначала прочитать весь новый контур и старую кампанию в статусе OFF. Старый черновик (DRAFT) удаляют, а ранее работавшую остановленную кампанию архивируют — но ворота записи модуля пока не поддерживают `Campaigns.delete` и архивирование кампаний, как и загрузку изображений, наборов быстрых ссылок и уточнений. Сейчас ворота принимают: кампании (add, update, suspend), группы (add, update), объявления (add, update, suspend, resume, archive, moderate), ключевые фразы (add, update), общие наборы минус-фраз (add). Для остального — блокер `tooling` или отдельная разрешённая ручная операция по правилу о транспорте выше.
- Количества в проверках не задавать константами.
- TSV из Reports API разбирать с `csv.QUOTE_NONE`. Сумму Cost отчёта сверять с итогом по кампаниям; расхождение больше 2 % — стоп. Если отчёт падает по всем кампаниям из-за поля, недопустимого для выбранного типа отчёта, это `request_shape_failure`, а не отсутствие данных.
- Директ при сохранении может сам склеить дубли ключей или нормализовать минус-фразы. После `update` сохранить запрос, позиционный ответ и немедленное чтение и сопоставить каждую пропавшую форму ровно с одной сохранившейся (`api-keyword-equivalents.tsv`, `api-negative-equivalents.tsv`). Необъяснённая потеря блокирует продолжение; слепой повтор запрещён.
- Отчёты — не чаще 16–18 запросов за 10 секунд (на 20 и больше Reports API отвечает ошибкой). При ошибке лимита ждать и повторять, а не терять кампанию.

## Построчные реестры Поиска и РСЯ

Для общего семантического объёма Поиска и РСЯ сравнения числа ключей недостаточно. До и после записи вести построчный двусторонний реестр `keyword → channel → target_group`; множества «Поиск минус РСЯ» и «РСЯ минус Поиск» должны быть пустыми.

- Группы в `search-group-map.tsv` имеют стабильный `group_uid`; сверка по названию группы запрещена. Сравнивать `group_uid + campaign_name + adgroup_name + landing_url + cluster`.
- Потеря группы между картой, манифестом и живым кабинетом без решения `include`, `defer`, `exclude` или `needs_landing` — BLOCKED. Живая группа без ручных ключей — BLOCKED, если это не утверждённая заглушка.
- Итоговое чтение не может получить PASS по счётчикам: проверять лишние живые группы, группы без ключей, все строки ключей и автотаргетинга с `AutotargetingCategories`, расписание, быстрые ссылки и уточнения, статусы.
- Если утверждено «одна группа = одна кампания», доказать ровно одну группу в каждой целевой кампании и отсутствие старой сводной кампании в рабочем контуре.

## Черновики Поиска: расписание, автотаргетинг, быстрые ссылки

Для поисковых черновиков обязательны `time-targeting-plan.tsv`, `search-autotargeting-category-map.tsv` (на каждую живую или планируемую группу), `sitelink-apply-readback.tsv` или подтверждённый `asset_gap` и итоговое чтение через API. Базовая запись скриптом сборки даёт только статус `partial_draft_written`; `draft_ready` — после подтверждённого расписания, фактически применённых быстрых ссылок и прочитанных категорий автотаргетинга. Молчаливый круглосуточный показ, категории автотаргетинга по умолчанию и чтение без поля `AutotargetingCategories` — дефект процесса.

После любого сохранения группы в интерфейсе Директа перечитать ключи группы через API: интерфейс сам делает кросс-минусовку и дописывает минус-слова в ключи. Отклонение вернуть через `Keywords.update` и повторить сверку. Радиус на карте в API не виден (`RegionIds` остаётся городом) — подтверждать повторным открытием группы.

## Отслеживание: UTM и адреса после отправки форм

При аудите или правке UTM в действующей поисковой кампании сначала разнести настройки уровня кампании и группы, адреса объявлений и быстрые ссылки; пустые или переопределяющие настройки группы считать возможным дефектом до чтения после записи. Перед правкой доказать, какие устаревшие параметры должны исчезнуть; после записи проверить объявления и ссылки и предупредить о риске повторной модерации.

Для посадочной на конструкторе страниц проверять не только адрес и UTM, но и адрес после отправки и переходы всех форм на живой странице: один устаревший междоменный адрес после отправки ломает атрибуцию. Если правки содержимого запрещены, менять только узкое техническое поле и доказать чтением каждую форму. Перед правилом атрибуции по UTM выяснить все рекламные потоки на сайт и сделать метку уникальной для направления. Новые цели называть «Направление: действие», без служебных слов.

## Семантика: покрытие, синонимы, операторы, минус-слова

- До пробного прогона сборки обязателен слой покрытия: `keyword-candidate-universe.tsv`, `keyword-inclusion-map.tsv`, `keyword-exclusion-map.tsv`, `segment-keyword-coverage.tsv`, `uncovered-target-query-report.md`. Короткий список из 20–50 фраз без карты покрытия = BLOCKED. Сырая таблица кандидатов — не пакет ключей.
- Каждая целевая фраза получает вердикт, сегмент, маршрут и посадочную или `needs_new_page`.
- Синонимы исчерпываются по [протоколу](synonym-exhaustion-protocol.md); построчный разбор — по [заданию проверяющему](semantic-review-agent-brief.md).
- Операторы (`"`, `!`, `[]`, `+`) ставятся только по построчному решению пользователя.
- Полная строка поискового запроса или Wordstat — только доказательство; в минус-слова идёт одно слово или короткая неразрывная маска.

## Клиентский пакет документов

Для договора, ТЗ, коммерческого предложения или акта по Директу не писать универсальный текст с нуля, если есть ранее принятый шаблон: найти его, сверить и вынести конкретику в ТЗ — кампании, посадочные, продукты и услуги, гео, источники семантики, цели, ограничения, результаты, критерии приёмки. Документ без матрицы «кампания → посадочная или услуга» неполон. Нельзя придумывать исключения, убирающие согласованные фиды, цели Метрики, настройку, запуск или ведение; первый месяц не сужать до аудита без явного решения «только аудит». Клиентский документ читается человеком: без внутренних статусов, кодов, служебных идентификаторов и описания внутренней процедуры.

## Конкурентный анализ — это извлечённое преимущество

Конкурентный анализ полезен, только если даёт извлечённое преимущество: `competitor-offer-matrix.tsv`, `competitor-ad-angle-matrix.tsv`, `advantage-gap-map.tsv`, `copy-opportunity-map.tsv`, и эти выводы использованы в текстах либо отклонены с причиной. Список доменов — не результат: анализируются конкретные страницы и объявления. Схемы колонок и порядок — в [основном порядке работы](main-workflow.md), раздел «Конкуренты по выдаче и страницам».

## Оплата за конверсию: не резать охват логикой оплаты за клик

При оплате за конверсию (`PAY_FOR_CONVERSION…`) клик бесплатен. Не ставить фразы на паузу «по кликам без оплат», не вводить правила «N кликов без оплаты — пауза», не сужать автотаргетинг до «целевых» и не оставлять собранные темы незапущенными. Исключать только явно чужое, запрещённое и то, что решил пользователь. Решения, принятые при оплате за клик, пересматривать, а не наследовать. Проверяющему не задавать рамку «главный риск — мусорные клики».

## Запись в кабинет: штатный скрипт, пробный прогон, свежее чтение

- До записи открыть [указатель скриптов](script-index.md) и взять штатный скрипт. Свой — только если штатного нет, с пометкой в журнале правок.
- Спецификацию пакета проверить до применения. Скрипты записи по умолчанию работают в пробном режиме, запись — только явным флагом. Правку кода сборщика проверять чтением файла, а не «проверочным» запуском записывающего слоя.
- Даже запись одного поля (метка, стратегия, ставка) идёт по этому навыку. Изменяемые поля перечитать из API непосредственно перед записью: кабинет мог поменять кто-то другой.
- После пачки записей сверить ранее работавшие кампании со снимком «до» и написать итог одной строкой.
- Когда объекты готовы к модерации — в том же отчёте спросить «отправить на модерацию?». После отправки прочитать `State`; если кампания не должна включаться — `suspend`.
- Живая остановка кампаний, групп и объявлений — только по отдельному разрешению, даже при сильном риске расхода.
- Порядок запуска при правках сайта: сайт → Метрика и цели после публикации страниц → кампании → модерация.

## Клиентская логика — в скрипте клиента

Логика под конкретного клиента живёт в собственном скрипте в папке проекта клиента (копия общего скрипта с правками). Общие скрипты навыков не содержат названий, товаров, текстов, доменов и значений по умолчанию конкретных клиентов. Перед запуском общего записывающего скрипта поиском (`rg -i`) проверить, нет ли в его коде названий клиентов; нашлись — сначала вынести эту логику в скрипт клиента. Второй заголовок и другие тексты объявлений берутся только из пакета, а не из значений по умолчанию в коде.
