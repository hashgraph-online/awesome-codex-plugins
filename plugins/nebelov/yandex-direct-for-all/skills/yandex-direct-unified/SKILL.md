# Яндекс.Директ: единый рабочий навык

Этот навык задаёт порядок работы. Узкие навыки yandex-wordstat, roistat-reports-api и amocrm-api-control уточняют свои программные интерфейсы, но не заменяют этот порядок.

## Перед началом

1. Пройти общий поиск навыков по теме задачи.
2. Всегда прочитать [основной порядок](references/main-workflow.md), [правила решений](references/decision-rules.md) и [правила работы](references/operating-rules.md). В правилах работы — таблица конкретных документов по операции: их прочитать до действия.
3. Для семантики — [сбор ключевых фраз](references/keyword-collection-runbook.md), [протокол исчерпания синонимов](references/synonym-exhaustion-protocol.md) и [задание смысловой проверки](references/semantic-review-agent-brief.md).
4. Для исследования спроса, конкурентов, медиаплана или прогноза — [приёмка исследования и прогноза](references/research-forecast-acceptance.md).
5. Для нового клиента, сборки по нескольким сайтам, комбинаторных объявлений и записи новых черновиков — [приёмка новой сборки](references/new-client-full-build-acceptance.md).
6. Для действующего кабинета, авторизации или любой записи — [надзорная проверка](references/workflow-supervisor.md) и [указатель скриптов](references/script-index.md); при сбое доступа — [восстановление доступа](references/access-recovery-runbook.md).
7. Для изменения самого навыка — [карта источников правил](references/source-map.md).

В первом статусе назвать прочитанные файлы.

Все ссылки относительны каталога навыка: установка не зависит от имени пользователя и расположения домашнего каталога.

## Неподвижные правила

- Roistat, amoCRM и XMLRiver необязательны. Отсутствие такого источника блокирует только выводы, которым он нужен (окупаемость, продажи, платный сбор выдачи), а не всю задачу. Подключение проверяйте по факту доступа, не предполагайте.

- Сначала определить клиента, кабинет и разрешённый объём; затем читать данные.
- Доступ подтверждается свежим запросом к нужной службе, а не наличием файла с токеном.
- В поставке есть общие приложения авторизации для Директа и Метрики. Пользователю не требуется создавать собственное приложение.
- Авторизация Директа и Метрики раздельна. Токен, код подтверждения и секрет приложения не передаются в аргументах процесса и не печатаются.
- Чтение и запись разделены. Любая запись, запуск, модерация, бюджет или остановка трафика требуют отдельного явного разрешения.
- Имена кампаний и групп показываются пользователю раньше служебных номеров.
- Сырые данные Wordstat и поисковых фраз не являются готовой семантикой.
- Автоматические сценарии не принимают смысловые решения за человека или проверяющего агента.
- Секреты и клиентские выгрузки хранятся только вне каталога навыка.
- Сначала API Директа; интерфейс — только при доказанном отсутствии метода. Метрика — только через API.
- В общем аккаунте читаются только кампании клиента. «0 кампаний» при заявленном кабинете — блокер доступа, а не факт о бизнесе.
- «Не знаю» — это ответ: повторно его не спрашивать, но и фактом не считать.
- Доказательства раскладываются по элементам (текст, посадочная, площадка, аудитория); одна продажа не засчитывается нескольким объявлениям.
- РСЯ — отдельный пакет текстов, у каждого объявления своё изображение без искажений. `DisplayUrlPath` — русский, до 20 символов, из ключа группы. Якоря в быстрых ссылках запрещены.
- Полный поисковый запрос — доказательство, а не минус-фраза: в минус-слова идёт одно слово или неразрывная пара.
- Бюджет и денежные параметры стратегии берутся только из решения заказчика; иначе `unknown`.
- Изменяемые поля перечитываются из API непосредственно перед записью; после записи ранее работавшие кампании сверяются со снимком «до».

## Результат

Каждый запуск оставляет проверяемые входы, исходные ответы, решения, план изменения и чтение после изменения. Если обязательного доказательства нет, статус — BLOCKED с конкретной причиной, а не предположение о готовности.
