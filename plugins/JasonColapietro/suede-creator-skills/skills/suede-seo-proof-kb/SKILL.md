# Suede SEO Proof Library Skills

## Compatibility

Use this playbook on any host that can read the user's source material. A durable ledger and impact index need an approved writable workspace; otherwise return structured tables without claiming persistence. The skill does not require a paid tool, external account, crawler or upload.

Read the [record and audience contract](references/record-contract.md) when setting up or repairing a library. Use the [worked correction and verification](references/claim-revision.md) for a changed claim, a missing source or a withdrawal. The fixtures in the second reference are synthetic, not publishable customer proof.

## 1. Take the smallest useful inventory

Start with the page or claim the requester named. Confirm the page's audience and purchase or implementation decision. List its material promises before looking for a number to fill a slot. A claim is material if a different answer might change a reader's next action: feature availability, implementation effort, price, eligibility, speed, outcome, or comparison.

Use an existing approved evidence store if one is present. Otherwise create a private claim ledger and a reverse index from claim IDs to pages and anchors. Keep source recordings, customer exports, raw logs and authentication details in their approved locations, not in the ledger. If the existing store is a public repo, do not save private pointers, names, excerpts, or hashes there just to make a record appear complete.

## 2. Give each claim a stable, narrow record

Record one independently changeable fact per ID. Include proposed public wording, evidence owner and source locator, observation date and coverage period, method or comparison, population, sample, exclusions, result, consent scope, next review, reviewer, and where it is used. Keep verification state separate from audience clearance. An accurate result can still be confidential; an approved quote can still need a correction.

Choose the evidence to fit the assertion:

- **Benchmarks:** preserve version, inputs, unit, environment, baseline, raw result reference, and material outliers. Compare like with like; label simulated workloads and cold versus warm runs.
- **Observed use:** for a demo, retain the build, relevant permissions, actual steps, outcome and an approved screenshot or timestamp. Do not use a mockup as evidence of current availability.
- **Customer evidence:** distinguish an exact, approved quote from the team's summary. Scope outcome claims to the cohort and period observed. Anonymize and disclose only if the agreement and audience clearance permit it.
- **Terms or capability:** link the exact authoritative page or configuration and retain plan, region, platform, and rollout restrictions. Do not treat a closed PR as a public capability.
- **Lessons learned:** record the conditions, observable failure and verified resolution. A successful retry alone does not prove the root cause.

If an essential element is absent, name the missing check, who can supply it, and what usable wording remains. Route new interviews to `suede-customer-research` or source recordings to `suede-media-transcript` rather than generating a quotation.

## 3. Match proof to the page's job

For each pivotal reader question, distinguish essential explanatory material from original evidence. Common definitions can orient a reader; a measured result, demonstrable limitation or verified workflow proves what this site can actually add. Use the smallest eligible observation that changes the reader's decision. Do not require a quota of evidence categories, repeat one test across unrelated sections, or promise a higher ranking.

When researching an AI-search gap, note the date, market, model, exact prompts that finished, existing owned URLs, and the IDs that could substantiate an answer. Report missing evidence separately from a missing page. Refresh a URL that already owns the intent rather than cloning it for a different phrase. Send the evidence packet and proposed page locations to `suede-copy`; keep review-only labels and private locators out of rendered copy.

## 4. Reverse the index on a correction or withdrawal

Find every indexed use, including localizations, pricing comparisons, FAQs, structured data, snippets and excerpts. Search the scoped source for the ID, old wording and retired value to catch unregistered usages; inspect candidate hits to avoid replacing coincidental numbers. For each confirmed use, return the approved replacement, removal, or owner review needed. Different audiences may need different language. Record the obsolete version and update the index so it is possible to explain what changed.

When separately authorized to implement, recheck the rendered surfaces rather than only a repository diff. Keep changes to account terms, structured data, marketing approvals and site publication within their existing workflows.

## Evidence boundaries

Return the ledger delta, public-safe evidence packets, affected URLs and anchors, and open questions with owners. Identify unchecked pages and explain why they were not inspected. Do not disclose private evidence, invent customer proof, publish content, run a new data collection job, or transfer sensitive content outside its approved store from this skill.
