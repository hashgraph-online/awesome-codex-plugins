# Suede SEO Sprint Skills

Use when a viable landing page has relevant search demand and one owner can improve it over a bounded window. A sprint concentrates learning; it does not guarantee a position.

1. Choose one canonical URL and one buyer task. Read the live page, comparable queries and search results in the intended market, and the conversion path. Check whether a different owned URL already serves that task better. If the canonical is wrong, access is blocked, or intent does not fit, solve that before starting the sprint.
2. Save the last complete 28 days and one comparison window with the same geography, device filters, dates, and URL/query scope. Record impressions, clicks, conversions and denominator, chosen rank signals, and recent site or SERP changes. Missing data is a baseline gap, not zero. Identify trend or seasonality that could move the result without the sprint.
3. Sequence changes instead of modifying everything every day. In week 1 capture target intent and fix access, headings and snippet mismatches. In week 2 add a real example, source, or comparison that improves the decision. In week 3 repair contextual internal routes and prepare relevant editorial pitches only if useful. In week 4 recheck indexing, traffic quality, and conversions; roll back regressions and record what to test next.
4. Log each action against its ship date, exact page, evidence, expected outcome and regressions. A title edit can improve CTR without moving position; impressions can rise without qualified demand. Keep those outcomes separate. Pause if another owned URL starts competing, search intent changes, or conversion performance worsens.

Return a baseline table, four weekly checkpoints with named owners, actual change history, and an outcome labeled improved, inconclusive, or regressed. Never represent a draft as live or send link outreach from this skill.

## Compatibility

A dated Search Console export, an owned URL, and a known primary conversion
event are enough to start. Actual page changes require authorized editing and
release access. If exports are missing, run this as a preparation sprint and
return the missing baseline evidence instead of asserting lift.

## Make the sprint reviewable

Name the one primary outcome, the audience that can produce it, and a
countermeasure for harm. Example: timely discovery for a transactional query
group is the outcome, lead quality is the guardrail, and branded impressions
are tracked as context not credited to the sprint. Name the owner of each
signal and set the smallest useful sample for the decision. If the selected
page has almost no query coverage or no verifiable customer route, pause and
address the premise before spending a month polishing the page.

A week is a review checkpoint, not an obligation to release something. Do not
combine a snippet test with an unrelated URL move just to fill the schedule.
If edits slip or indexing is delayed, measure relative to actual release and
verified live dates rather than the plan. Preserve a known-good version and
assign a person with authority to restore it. A clear next week can be "collect
more comparable data" instead of "repeat every action."

Use [the sprint evidence ledger](references/sprint-ledger.md) to keep
changes, actual live verification, and outcome attribution separate.

## Boundaries

- Do not promise rankings or a fixed indexing timeline.
- Validate the baseline and leave any external placement or publication for authorization.
