## What to Look For

### Premise & Approach
- **Problem framing**: Is the stated problem the real problem, or a symptom of something deeper?
- **Fundamental assumptions**: What assumptions does this plan rest on? Are they valid?
- **Alternative approaches**: Is there a simpler, more effective, or fundamentally different way to achieve the same goal? If you propose an alternative to a choice the plan explains, say why its stated reason doesn't hold or what it misses.
- **Scope appropriateness**: Is this plan solving the right problem at the right level? Is it too narrow or too broad?
- **Cost vs. benefit**: Is the proposed effort justified by the expected outcome, or is there a higher-leverage path?

### Completeness
- **Missing requirements**: Are all features fully specified?
- **Incomplete steps**: Where the plan describes work, does it have enough detail to implement?
- **Missing dependencies**: Are dependencies the plan states, or that the design implies between its parts, identified?
- **Missing edge cases**: Are error conditions and edge cases addressed?
- **Missing tests**: Is the testing strategy adequate? Would a test or acceptance criterion offered as evidence for a behaviour still pass with that behaviour missing or broken, or is any check unable to fail?

### Correctness
- **Technical feasibility**: Is the proposed approach technically sound?
- **Architecture issues**: Are there design flaws or anti-patterns?
- **Security concerns**: Are there potential vulnerabilities? Could data leak through logs, telemetry, caches, test output or committed files?
- **Performance issues**: Will the approach scale appropriately?
- **Integration issues**: Will the changes work with existing code?

### Clarity
- **Ambiguous requirements**: Are any requirements unclear or open to interpretation?
- **Vague steps**: Does each described piece of work clearly specify what needs to be done?
- **Missing context**: Is there sufficient background for implementers?
- **Conflicting statements**: Do parts of the plan contradict each other? Look especially for numbers or limits that differ between sections, and for one thing called by two names.
- **Dangling references**: Does the plan refer to a section, decision or ID of its own that it never defines? A reference to one defined in a document the plan names, such as another plan, a tasks file or a file in the repository, is not dangling.
- **Questions already answered**: Does the plan list as open a question it answers elsewhere?

### Implementation Quality
- **Over-engineering**: Is the solution more complex than necessary?
- **Under-engineering**: Is the solution too simplistic for the problem?
- **Code organization**: Is the proposed file structure sensible?

## Output Format
Return ONLY a valid JSON array with no additional text. Each element must have exactly these fields:
- "title": string (5-10 word summary of the issue)
- "desc": string (what is wrong and why it matters. Where it helps, add the evidence: the plan text it rests on, with its section and a short quote, or a repository location as path:line, only if you opened that file and checked what is there. If the plan or a file you opened shows which value or behaviour is intended, say which, for example which of two numbers that disagree is the right one. You don't need to propose a fix; whoever applies the finding decides it. But if the right fix is a design choice the plan does not settle, propose the one you would make, so that validation can weigh it.)
- "importance": "high" | "medium" | "low"
  - high = critical gaps, security issues, architectural flaws, blockers
  - medium = missing details, unclear requirements, potential issues
  - low = a real problem with a small impact (not a style or wording preference)
- "reference": string (which section of the plan this affects, e.g., "## Requirements" or "### Task 3")
- "type": "addition" | "modification" | "deletion" | "clarification"
  - addition = something is missing and should be added
  - modification = something exists but needs to be changed
  - deletion = something should be removed (unnecessary, harmful)
  - clarification = something is unclear and needs better explanation
