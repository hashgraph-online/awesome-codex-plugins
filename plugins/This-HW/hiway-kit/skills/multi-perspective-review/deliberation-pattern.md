# Deliberation Pattern: 3-Round 협의 프로세스

> 다관점 리뷰의 핵심 워크플로우

---

## 개요

Deliberation Pattern은 여러 전문가가 **독립적 의견 → 상호 검토 → 합의 도출** 순서로 협의하는 프로세스입니다.

**핵심 원칙:**

- Round 1: 독립성 (다른 의견에 영향받지 않음)
- Round 2: 상호작용 (다른 의견을 고려하여 재검토)
- Round 3: 합의 (충돌 해결 및 최종 의사결정)

**거짓 합의 방어 (모든 Round, 모든 실행 경로에 적용):**

- **근거 필수** — 이슈·주장은 근거(`파일:라인` + 인용 한 줄 · 명령과 출력 · URL 과 확인일)를 단다.
  근거 없는 주장은 **집계에서 제외**한다(개수·합의율에 넣지 않고, 리포트의 "집계 제외" 절에 한 줄로 남긴다).
- **명시적 반대** — Round 2 끝에 반대자가 합의 초안에 *근거를 들어 반대*한다. 합의는 반대가
  근거로 반박되거나, "근거 있는 반대를 못 찾음 + 시도한 검증"이 적힌 항목만 통과한다.

---

## Round 0: Facilitation (사전 준비)

**목적:** 필요한 관점 식별 및 초점 영역 정의

**수행자:** 메인 세션 (스킬 단계)

**프로세스:**

```
1. 문서 읽기 및 분석
   ├─ 문서 유형 (기획/설계/API)
   ├─ 복잡도 (Small/Medium/Large)
   ├─ 주요 도메인 (인증, 결제, 데이터 등)
   └─ 리스크 레벨

2. 관점 선택
   ├─ 필수: Requirements, Technical (항상 포함)
   ├─ 조건부: 문서 내용에 따라 선택
   └─ 생략: 관련 없는 관점 제외

3. 초점 영역 정의
   ├─ Requirements: P0 모호함, 엣지 케이스
   ├─ Security: 인증/권한, 민감 데이터
   └─ ... (관점별 구체적 포커스)

4. 공통 컨텍스트 수집
   └─ 대상 문서 + 프로젝트 에이전트 지침 파일(있는 것) — 모든 관점에 같은 것을 준다

5. Round 1 프롬프트 템플릿 생성
```

**출력:**

```json
{
  "perspectives": [
    {
      "name": "requirements",
      "agent": "clarify-requirements (선택 — 없으면 관점 프롬프트)",
      "focus_areas": ["P0 모호함", "엣지 케이스"],
      "priority": "critical"
    }
  ]
}
```

## Round 1: 초기 의견 수집 (병렬)

**목적:** 각 관점의 독립적 의견 도출

**실행 방식:** 병렬 (동시 실행)

**프로세스:**

```
# 경로 A: 관점마다 서브에이전트 (한 메시지에 병렬) — 에이전트가 없으면 범용 + 관점 프롬프트
# 경로 B: 서브에이전트 없음 — 메인 세션이 관점 블록을 하나씩 쓴다 (앞 블록 인용 금지, 쓴 블록 수정 금지)
for perspective in perspectives:
    review(
        by=perspective.agent or perspective.prompt,
        prompt=f"""
        다음 문서를 {perspective.name} 관점에서 리뷰:

        문서: {document}

        중점 영역:
        {perspective.focus_areas}

        형식:
        - Critical 이슈
        - Important 이슈
        - Nice-to-have 제안

        각 항목 끝에 근거를 붙여라: [근거: 파일:라인 "인용" | `명령` → 출력 일부 | URL (확인일)].
        문서를 읽고 판단한 것이면 해당 문서의 파일:라인과 인용 한 줄이면 된다.
        근거를 못 대면 항목 앞에 [추론] 을 붙여라 — 집계에서 제외된다.
        """
    )
```

**근거 규칙:** 근거의 종류는 주장이 무엇에 관한 것인지에 맞춘다 — 문서가 무엇을 말하는지(또는
말하지 않는지)는 문서 `파일:라인`, 코드·시스템의 현재 동작은 코드 `파일:라인` 또는 실행한 명령과
출력, 외부 사실(라이브러리 동작·표준·가격)은 URL 과 확인일. "~일 것이다"·"일반적으로"는 근거가 아니다.

**독립성 보장:**

- 다른 관점의 의견 미제공
- 순수하게 자신의 전문 영역만 검토
- 편향 방지

**수집 결과:**

```
Requirements: P0 모호함 3개 발견
Technical: 개발 3주 예상
Security: 감사 로그 필수
Business Logic: 적립률 5% 제안
Data/Schema: 2개 테이블 추가
```

## 종합 1: Round 1 종합 (메인 세션)

**목적:** 의견 통합, 충돌/중복 식별

**프로세스:**

```
0. 근거 검사 (집계 전에 먼저)
   ├─ 근거가 없거나 [추론] 인 항목 → "집계 제외" 목록으로 분리 (삭제하지 않는다)
   └─ 근거는 있는데 형식만 틀린 항목은 관점에 되돌리지 않고 메인 세션이 확인해 보정

1. 의견 수집 및 구조화
   ├─ Critical/Important/Nice-to-have 분류
   ├─ 주요 이슈 추출
   └─ 제안사항 정리

2. 중복 제거
   ├─ 동일 이슈 통합 (예: "트랜잭션 무결성")
   └─ 그룹화 (관련 이슈 묶기)

3. 충돌 식별
   ├─ 관점 간 상충 의견 (예: 기획자 1주 vs 개발자 3주)
   ├─ 충돌 유형 분류 (우선순위/기술vs보안/UXvs보안)
   └─ 충돌 목록 작성

4. 우선순위 분류
   ├─ Critical (즉시 해결)
   ├─ Important (권장)
   └─ Nice-to-have (선택)

5. 합의 초안 작성
   └─ 근거 있는 이슈별로 "이렇게 처리한다"는 한 줄 — Round 2 반대 단계의 공격 대상
```

**출력:**

```markdown
## Round 1 종합

### 집계 제외 (근거 없음) — N건
- (관점) 한 줄 요지 — 근거 없음/[추론]

### Critical (2개)

1. P0 모호함: "사용자" 정의 불명확
2. 보안: 포인트 조작 방지 없음

### Important (3개)

...

### 충돌 (2개)

1. 개발 기간: 기획자 1주 vs 개발자 3주
2. Rate Limiting: 보안 Phase 1 vs 개발자 Phase 2
```

## Round 2: 상호 검토 (순차)

**목적:** Round 1 의견을 고려하여 재검토

**실행 방식:** 순차 (이전 의견 컨텍스트 포함)

**프로세스:**

```
for perspective in perspectives:   # 순차 — 경로 A·B 동일
    review(
        by=perspective.agent or perspective.prompt,
        prompt=f"""
        Round 1 결과를 고려하여 재검토:

        문서: {document}

        Round 1 종합:
        {round1_summary}

        당신의 Round 1 의견:
        {your_round1_opinion}

        다른 관점 의견:
        {other_perspectives}

        재검토 항목:
        1. Round 1 의견 유지/변경?
        2. 다른 관점 의견에 추가할 점?
        3. 충돌 해결 제안?
        """
    )
```

**상호작용:**

- 다른 관점 의견을 읽고 반응 (반응도 근거를 단다 — "동의합니다"는 근거가 아니다)
- 자신의 관점에서 추가 이슈 식별
- 충돌 해결 제안

**예시:**

```
Technical (Round 2):
"보안 관점에서 감사 로그가 필수라고 했는데, 동의합니다.
다만 개발 기간이 2일 추가됩니다. 총 3주로 조정합니다."

Security (Round 2):
"개발자가 트랜잭션 설계를 SERIALIZABLE로 하겠다고 했는데,
이것만으로도 포인트 조작 1차 방어는 충분합니다.
Rate Limiting은 2차 방어이므로 Phase 2 연기 수용합니다."
```

### Round 2 마지막: 명시적 반대 (생략 불가)

**수행자:** 반대자 — 관점 중 Devil's Advocate 가 있으면 그것, 없으면 범용 서브에이전트(경로 B 는
메인 세션이 별도 블록으로). 관점 수에 세지 않는다. **관점별 재검토가 끝난 뒤** 합의 초안(종합 1 의
5)과 Round 2 의 변경 내용을 받아 아래를 수행한다.

```
prompt = f"""
당신의 역할은 합의에 *반대*하는 것이다. 아래 합의 초안의 각 항목에 대해, 그것이 틀렸거나
위험하거나 빠뜨린 것이 있다는 근거를 찾아라.

문서: {document}
합의 초안 + Round 2 변경: {draft_consensus}

항목마다 정확히 하나를 쓴다:
- 반대: <무엇이 틀렸나> [근거: 파일:라인 | 명령→출력 | URL (확인일)]
- 근거 있는 반대 없음: 시도한 검증 <어느 파일·명령·자료를 어떻게 봤는지>

금지: "동의한다"만 쓰기, 근거 없는 반대, 시도 기록 없는 "반대 없음".
"""
```

**판정 (메인 세션):** 항목별로

| 반대자 출력 | 처리 |
| --- | --- |
| 근거 있는 반대 → 다른 관점/메인이 **근거로 반박** (Round 2 재검토 또는 메인 확인) | 합의 통과, 반박 근거를 리포트에 적는다 |
| 근거 있는 반대 → **반박되지 않음** | 합의 아님 — Round 3 충돌 목록으로 (조건부 합의 또는 사용자 결정) |
| 근거 있는 반대 없음 + 시도한 검증이 구체적 | 합의 통과 ("반대 시도: …" 를 리포트에 남긴다) |
| 시도 기록이 없거나 "동의한다"뿐 | 무효 — 반대자를 한 번 다시 돌린다. 두 번째도 무효면 그 항목은 `검증되지 않은 합의`로 표시한다 |

합의율은 **근거 있는 항목 중 위 표로 "통과"한 비율**이다 — 집계 제외 항목은 분자·분모에 없다.

---

## Round 3: 합의 도출

**목적:** 충돌 해결 및 최종 의사결정

**수행자:** 메인 세션 (스킬 단계)

### 3-1. 충돌 분석

```
for conflict in conflicts:
    0. (충돌 = 종합 1 의 관점 간 충돌 + Round 2 반대 단계에서 반박되지 않은 근거 있는 반대)
    1. 충돌 근본 원인 파악
       ├─ 정보 부족?
       ├─ 목표 불일치?
       └─ 제약 충돌?

    2. 트레이드오프 분석
       ├─ 옵션 A: 장단점, 리스크
       ├─ 옵션 B: 장단점, 리스크
       └─ 옵션 C (중간 지점)

    3. 합의 전략
       ├─ Win-Win 찾기 (우선)
       ├─ 조건부 합의 (차선)
       └─ 사용자 결정 (최후)
```

**예시:**

```
충돌: 개발 기간 (기획자 1주 vs 개발자 3주)

트레이드오프:
A) 1주 출시: 빠르지만 버그 위험 높음
B) 3주 출시: 품질 보장하지만 시장 지연
C) Phase 분할: MVP 2주 + 고급 기능 1주

합의안: C) Phase 분할
- 기획자 우려 해소: 2주면 시장 선점 가능
- 개발자 우려 해소: 핵심 기능 품질 보장
- 리스크 완화: MVP로 빠른 검증 후 개선
```

### 3-2. 영향도 분석

코드베이스 영향이 크면 직접 영향 파일은 analyze-dependencies 로 확인한다(없으면 직접 검색).

```
1. 변경 범위 식별
   ├─ 직접 영향: 변경될 파일/모듈
   ├─ 간접 영향: 의존하는 시스템
   └─ 숨겨진 영향: 성능, 리소스, 운영

2. 리스크 분류
   ├─ High Risk: 데이터 손실, 보안 취약점
   ├─ Medium Risk: 성능 저하, 기존 기능 영향
   └─ Low Risk: 독립 기능, 롤백 쉬움

3. 비용 추정
   ├─ 개발 비용: 설계 + 구현 + 리뷰 + 버그 수정
   ├─ 테스트 비용: 단위 + 통합 + E2E + 성능
   ├─ 인프라 비용: 서버, DB, 외부 API
   └─ 운영 비용: 배포, 모니터링, 문서화

4. 권장사항
   └─ 승인 / 조건부 승인 / 재검토
```

### 3-3. 최종 리포트

`Round 1 + Round 2(재검토·반대) + 합의안 + 영향도 → 최종 문서`. 구조와 항목별 필수 필드:

```markdown
# 다관점 리뷰 최종 결과

## 📋 Executive Summary

- 문서: [문서명]
- 복잡도: [Small/Medium/Large]
- 참여 관점: [N]개 (+ 반대자)
- 실행 경로: [병렬(서브에이전트) / 순차(단일 컨텍스트)]
- 합의 상태: [X]% 합의 (근거 있는 항목 [N]건 기준 · 집계 제외 [M]건)

---

## 🔴 Critical (즉시 수정 필요)

### 1. [이슈명]

**제기 관점:** [관점 목록]
**내용:** [상세 설명]
**근거:** [파일:라인 "인용" | `명령`→출력 | URL (확인일)]
**영향:** [영향 범위]
**해결:** [구체적 해결책]
**반대 결과:** [반박됨(반박 근거) / 반대 시도했으나 없음(시도: …) / 미반박 → 충돌로 이동]
**합의:** ✅ 전원 합의 / ⚠️ 조건부 / ❓ 사용자 결정 필요 / 검증되지 않은 합의

---

## 🟡 Important (수정 권장)

...(같은 필드)

## 🟢 Nice-to-have (선택 사항)

...

## ⚪ 집계 제외 (근거 없음)

- [관점] 한 줄 요지 — 근거 없음/[추론] (지운 것이 아니라 집계에서 뺀 것이다)

---

## 💬 합의 과정

### 충돌 #1: [충돌 설명]

**Round 1:** [초기 의견]
**Round 2:** [재검토 의견 / 반대자 근거]
**합의안:** [최종 합의]
**결과:** ✅ 해결 / ❓ 사용자 결정 대기

---

## 📊 영향도 분석

**변경 범위:**

- 시스템: [영향받는 시스템 목록]
- 파일: [예상 변경 파일 수]

**개발 기간:** [예상 시간]
**리스크:** [리스크 레벨 및 완화 방안]

---

## 🎯 다음 단계

1. [ ] [액션 아이템 1]
2. [ ] [액션 아이템 2]
```

## 실행 시간

| Round       | 실행 방식 | 예상 시간   | 비고               |
| ----------- | --------- | ----------- | ------------------ |
| Round 0     | 단일      | 2-3분       | 메인 세션          |
| Round 1     | 병렬/순차 | 5-10분      | 경로 B 는 순차     |
| 종합 1      | 단일      | 2-3분       | 메인 세션          |
| Round 2     | 순차      | 10-15분     | 관점 수 × 2분 + 반대 단계 |

## 성공 요소

### 1. 독립성 (Round 1)

- 다른 의견에 영향받지 않음
- 순수한 전문가 시각
- 편향 방지

### 2. 상호작용 (Round 2)

- 다른 관점 이해
- 자신의 의견 재검토
- 충돌 인식

### 3. 합의 (Round 3)

- 트레이드오프 명확화
- Win-Win 탐색
- 합리적 결정

## 실패 케이스 및 대응

### 케이스 1: 관점 간 소통 부족

**증상:** Round 2에서도 충돌 지속

**원인:** Round 1 의견이 불명확

**대응:** 종합 1 에서 각 의견을 주장·근거·요구로 나눠 명확히 정리

### 케이스 1-2: 전원 동의 (반대 0건)

**증상:** 관점 전원이 동의하고 반대자도 "반대 없음"만 썼다

**원인:** 합의가 맞거나, 반대가 형식적이다 — 둘은 겉으로 구별되지 않는다

**대응:** 반대자의 **시도한 검증**이 구체적인지(어느 파일·명령을 봤는가)로 가른다. 구체적이지
않으면 무효 처리하고 한 번 다시 돌린다. 그래도 같으면 `검증되지 않은 합의`로 표시한다

### 케이스 2: 무한 논쟁

**증상:** Round 3에서도 합의 실패

**원인:** Hard Constraint 충돌

**대응:** 호스트의 질문 수단으로 사용자 결정을 받는다

### 케이스 3: 시간 초과

**증상:** 30분 이상 소요

**원인:** 너무 많은 관점 또는 복잡한 문서

**대응:** 문서를 섹션별로 나누어 반복 리뷰
