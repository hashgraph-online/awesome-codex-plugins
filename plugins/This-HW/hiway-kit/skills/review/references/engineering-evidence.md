# 구현 근거와 품질을 함께 본다

새 기능·비단순 수정의 완료 검토에서 읽는다. 기존 테스트·린트·프로젝트 언어 규약이 우선한다.

- 입력 경계에서 파싱/검증하고 내부에는 검증된 값을 전달한다. 실패/부재/빈 결과를 구분한다.
- 타입/린트 경고를 숨기는 캐스팅·ignore·광범위 예외 처리 대신 원래 계약을 고친다.
- 새 라이브러리/런타임을 기본값으로 강제하지 않는다. 프로젝트에 설치된 도구와 관례를 쓴다.
- 복잡도·줄수는 검토 신호다. 공통 코드를 만들 때 실제 중복 책임과 변경 이유가 같은지 확인한다.
- 주석은 이유·프로토콜·제약을 설명할 때 남긴다. 모든 주석을 오류로 취급하거나 주석만으로 작업을 막지 않는다.
- 디버그 흔적, 불필요한 래퍼, 사용하지 않는 옵션, 과도한 예외 처리는 동작 증거와 함께 줄인다.
  정리 작업을 기능 변경과 섞어 범위를 넓히지 않는다.

각 완료 주장에 대응하는 관측을 남긴다:

| 주장 | 검증면 | 필요한 증거 |
| --- | --- | --- |
| 함수/API 동작 | 호출 결과 | 정상/오류/경계 입력, 테스트 명령과 rc |
| CLI 동작 | 실제 프로세스 | argv, stdout/stderr, 종료코드 |
| 사용자 흐름 | 실제 UI/브라우저 | 입력→화면/상태 변화, 관련 캡처 |
| 자동화/플러그인 동작 | 새 소비자 런타임 | 설치 위치·실제 발화/조회, 설정만 존재하는 상태와 구분 |

가짜 서비스가 반환하는 값만 검사하거나 구현 문자열을 그대로 검사하는 테스트는 동작 증거가 아니다.
되돌리면 실패하는 대조군을 사용한다. 느리거나 불안정한 통합 검사를 단순 스냅샷으로 대체하지 않는다.

검증 기록에는 소스 지문(커밋 또는 미커밋 diff/대상 파일 해시), 명령, rc, 결과 경로를 함께 둔다.
기록 이후 관련 코드가 바뀌면 해당 증거를 재사용하지 않는다. 미실행·타임아웃·도구 부재는 통과가 아니다.
관련 부분이 바뀌지 않았고 실패/불확실성이 없으면 검증을 반복해서 비용을 늘리지 않는다.
