# Anti-loop Policy

In Evidence mode, apply receipt-integrity guards without creating or approving a contract. In Guarded mode, apply contract authority after the staged id is approved and passed. In Off mode, ordinary work remains fail-open unless Click is explicitly invoked. Read-only review never needs a build contract.

## Observable guards and advisory guidance

1. **Prefer reuse without blocking fresh observations (advisory).** Tracked read-only argv requests execute with `shell=False`. Compatible simple Bash reads are converted to the same request. The runner atomically claims revision, digest, one-use token, replay state, and freshness, and stores request digest, mutation revision, result metadata, and status—not output. A fresh identical read may run with reuse guidance; consumed-token replay and an active same-digest reservation remain hard violations.
2. **Prefer repair or narrowing after repeated failures (advisory).** A failed command or output larger than 48,000 bytes may be retried under fresh authorization. After the second unchanged failure or incomplete result, Click advises changing, narrowing, or repairing the request but does not impose a fixed hard stop. The same rule applies to ordinary failing argv verification sources. Verification that changed protected repository content is not an ordinary failure and remains blocked until an approved mutation repairs or reconciles the workspace.
3. **Keep planning non-authoritative (advisory).** `update_plan` and equivalent host plan tools remain available in armed, staged, approved/passed, and review turns. A plan update cannot stage, approve, replace, or widen the active contract; it cannot change the contract digest, mutation authority, or evidence state. Avoid unnecessary parallel planning and implement directly from the compact contract when practical. Same-turn second staging, same-turn pass, and mid-run contract replacement remain hard lifecycle denials. If the approved outcome or boundary must change, stop and ask the user.
4. **Prefer narrow follow-up after broad context (advisory).** In approved implementation and review, a broad repository inventory may establish context. A later distinct-digest broad request remains available with non-blocking narrowing guidance even while another broad inventory is running or after one succeeds. A completed exact-digest request is also available under fresh authorization with repeat guidance; only an active exact-digest reservation remains blocked by the runner-state interlock. Path-scoped inventory and concrete content searches remain available. Inventory count and advisory output cannot change contract, mutation, or evidence authority.
5. **Make write intent explicit.** An ambiguous implementation command must use `click-gate mutate`; ordinary edit tools remain deterministic mutations. Direct active Bash is not guessed writable.
6. **Bind exact verification; leave sufficiency to strategy.** Final checks use protocol-v2 `click-gate verify` entries with `evidence_id`. Guarded ids resolve to the approved registry; Evidence ids register dynamically on first use. The first accepted group reserves its exact digest. The model chooses checks; legacy units neither deny nor advise.
7. **Do not mutate through verification.** Python `-c` and direct Python scripts are rejected as checks. In Git worktrees, a final batch that changes tracked or pre-existing non-ignored untracked content fails stale. New non-ignored paths are reported, and obvious new source, application, library, configuration, or migration paths also fail stale; ignored paths remain outside this snapshot.
8. **Bind Browser receipts; keep workflow tuning advisory.** The canonical Browser MCP tool is denied during an approved contract unless `verification.evidence` contains one referenced source with `kind: "browser"`. Calls remain serial, require a stable `tool_use_id`, and map the matching `PostToolUse` result to that assigned source and current mutation revision. Fresh normalized repeats after success or repeated failure remain available with reuse or repair guidance. Tool timeouts over 30 seconds and explicit waits over five seconds also remain available with timing guidance rather than a permission failure. Unassigned shadow sessions and replay after explicit evidence finalization remain blocked. There is no normal call-count or elapsed-session cap; after 256 normalized inputs, Click compacts the oldest per-input guidance record while preserving the source receipt. Once observed, a later failure does not demote the source. A later mutation resets the Browser ledger.
9. **Own server lifecycles.** Recognizable long-running development servers are rejected by `mutate` and must use `click-gate service` start/stop. A Click-owned supervisor retains the exact isolated child, responds to explicit stop and `SessionEnd`, and enforces a two-hour lifetime ceiling.

## Evidence economy

In Guarded mode, assign each approved `done_when` condition one cheapest sufficient source through `primary_evidence`. In Evidence mode, register only checks actually chosen for the work. Do not duplicate proof by default. Collect after the last relevant mutation, reuse only current receipts, and stop when evidence is sufficient. Same-revision reuse requires exact intent/contract, check, tree, environment, executable, and coverage bindings. Cross-revision Evidence reuse requires a committed mapping; Guarded may also use approval-bound dependencies. Missing or incomplete receipts rerun. Stop managed services before completion.

The Skill and semantic grader still decide whether a source is sufficient and whether two different sources duplicate the same semantic condition. The Hook independently runs bound argv checks, meters the canonical Browser MCP path, and records per-id completion. Hosted, manual, and existing completion are explicit attestations; unmatched connectors remain outside the independently observed boundary. Do not exploit an unmatched path to create a shadow verification suite.

## Read-only code review

For code review without changes, run `click-gate review`. Do not create or approve a build contract. Use structured inspection or compatible reads, prefer focused follow-up after broad context, and keep mutations rejected while review is active. Plan, inventory, and repeat guidance remains non-authoritative.

Questions, explanations, and simple read-only lookups do not enter review mode and are not recorded in the observation ledger.

A source mutation clears the successful observation ledger and makes completion evidence stale because earlier results may describe different code. An argv source with approval-bound deterministic dependencies, a matching committed repository mapping, or both may promote its prior success only after the host records the approved mutation's matching pre/post snapshot and the relevant resolved files, exact check, environment, and executable remain unchanged. Missing post receipts or later workspace drift run the check. Git-ignored content, external dependencies, and external system state are outside the protected tree receipt. A read/search or final verification already running blocks a concurrent mutation so the recorded result cannot silently describe different code.

## What the Hook cannot observe

The Hook cannot inspect hidden reasoning, detect a plan written only in prose, cover reads performed through an unmatched connector or hosted tool, prove that a natural-language boundary was obeyed semantically, or stop a custom wrapper from concealing work. These guards reduce visible tool loops; they are not a reasoning-token cap, semantic proof, or security/resource sandbox.

When a guard blocks an action, use existing evidence, narrow the command, make the necessary in-scope correction, or report a real boundary blocker. Do not rename or wrap the same work merely to bypass the guard.
