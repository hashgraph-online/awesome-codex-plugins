# Custom domains

Use a hostname the user controls when they request it. The publication must be an eligible, live HTML-format page or site with no password. Domain management requires an authorized BrewPage account or separate REST owner proof that already has the required account reach. Resolve the owner and operation before publishing material with a requested domain.

- On compatible MCP, include `domain` on `publish` when creating an eligible publication. For an existing item, use `domains` with `action: "attach"`, its exact target and the requested hostname. Use the installed schema.
- On runner REST create, append `--domain '{hostname}'` for eligible HTML or sites with an existing saved or privately supplied account owner token that permits this operation. The runner checks that selected token's profile reach and available domain capability through `GET /api/limits` before creating. Missing or unresolved applicable proof leaves the write pending. Remaining server eligibility, DNS records and notices come from the actual result. This runner does not establish an OAuth connection or change DNS.
- For an existing item, the REST attachment operation is `PUT /api/publications/{type}/{ns}/{id}/domain` with `{"hostname":"www.example.com"}` and eligible `X-Owner-Token` proof. The route takes `html` or `site` as `type`. Use the exact publication identity and a host capability authorized for this request. When that capability or account proof is unavailable, offer the first-party connected workflow. If creation succeeded and attachment failed, return the existing BrewPage link and actual domain outcome. Never republish to retry attachment.
- Use the actual `records`, `status`, `nextStep` and `nextCheckAt` in the response. Give the owner the exact required DNS records. A provider UI that appends the zone commonly uses `host` instead of the full returned `name`. The user or their authorized DNS integration applies the records.
- After the owner applies records, use the supported `check` once, then read status on the returned schedule. `pending_dns` or `verifying` means the original BrewPage link remains the working address. Report the custom `url` as live only on confirmed `active` and `serving: true`. If the publication moved to a required subdomain, also relay its returned effective BrewPage link.

Keep owner tokens, management keys and OAuth out of requests to custom hosts and DNS providers. The first-party [custom domains guide](https://brewpage.app/llms-full.txt#custom-domains) describes eligibility, record formats and service status.
