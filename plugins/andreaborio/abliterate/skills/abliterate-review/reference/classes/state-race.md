# State, races and workflow integrity (CWE-362, CWE-367, CWE-841)

## Sources
- Concurrent or repeated requests from one actor: double-click, retries, parallel tabs, scripted bursts; duplicate webhook deliveries.
- Time gaps: a job queued now and run later, a cache entry created by one user and read by another, a token issued before permissions changed.
- Out-of-order calls: hitting step 3 of a workflow without step 2, replaying a callback, changing a status field directly.

## Sinks
| Pattern | Smell | Safe shape |
| --- | --- | --- |
| Check then act (367) | `if (balance >= amt) { balance -= amt; save }` read in app memory; `exists()` then `create()`; `access()`/`stat` then `open` | atomic conditional update: `UPDATE ... SET balance = balance - $1 WHERE id=$2 AND balance >= $1` and check affected rows; unique constraint; `open` with flags then `fstat` |
| Lost update | read-modify-write on a row without lock or version | `SELECT ... FOR UPDATE`, optimistic version column, `F()` expressions (Django), `increment` ops |
| Double spend / replay | coupon, invite, gift-card, refund, one-time token redeemed twice | single-use enforced by unique constraint or atomic state transition `WHERE status='pending'` |
| Idempotency | payment/webhook handler without idempotency key or dedupe table | store `event_id`/`Idempotency-Key` with a unique index, return the saved result |
| Revoked permission | job payload carries `userId` and runs with stored privileges, long-lived websocket, cached authorization | re-authorize at execution time against current state; short-lived grants |
| Cache key scope | key `report:${id}` or per-URL cache without tenant/user/role/locale; CDN caching responses that vary by `Authorization`/cookie | include tenant and actor in key; `Cache-Control: private`/`Vary` |
| Workflow skipping (841) | status or step taken from request body; no server-side state machine; price/amount from client | server holds state and allowed transitions; recompute amounts server-side |
| Filesystem | temp file with predictable name in shared dir, symlink swap between check and open | `mkstemp`/`O_EXCL`, private dir |

## Guards that work / Look-alike guards
Work:
- Database-enforced invariants: unique indexes, check constraints, conditional updates, transactions at an isolation level that actually prevents the anomaly (read committed does not prevent a read-then-write lost update).
- `SELECT ... FOR UPDATE` on the row actually being checked, inside the same transaction as the write.
- Explicit transition table (`from -> to`) validated server-side.
- Authorization evaluated again where the effect happens.
- Cache keys that contain every dimension the response varies on.

Look-alike:
- In-process mutex or JS "single thread" argument with multiple instances/workers/serverless invocations.
- Client-side disabled button, debounce, or a front-end "already submitted" flag.
- An `if` check followed by an `await`/network call before the write (the gap is the vulnerability).
- Transaction without a lock or constraint (two transactions both pass the check).
- Idempotency key generated by the server per request (does nothing for retries).
- Rate limit as a substitute for atomicity.
- Cache invalidation on update only, while permission/tenant changes do not invalidate.

## Falsify before reporting
1. Is there a real window: do two requests (or request plus job) interleave between the check and the effect on shared state? Identify both statements and what separates them.
2. Does the datastore enforce the invariant (unique index, conditional update, constraint) regardless of the application check? Read the schema/migration.
3. Is the operation actually concurrent in this deployment (multiple workers/instances, async handlers), or serialized by a queue with concurrency 1 per key?
4. What does the attacker gain: repeated redemption, negative balance, access after revocation, another tenant's cached data? If there is no value, it is a bug, not a vulnerability.
5. Cache: does the response depend on identity or tenant, and is that in the key or in `Vary`?
6. Confirm: a deterministic test runs two operations against the same fixture (two parallel calls via `Promise.all`/threads, or interleaved steps with a controlled hook) and asserts a single effect.

## Severity cues
- Raises: money, credits, inventory, one-time grants; cross-tenant cache leak; privilege retained after revocation; unauthenticated trigger; cheap to repeat at scale.
- Lowers: narrow window plus a DB constraint that fails the second write loudly; self-affecting only; requires admin; effect is a duplicate harmless record.

## Regression test
- Fails before: fire N=2..5 concurrent redemptions of a one-use code (or withdrawals exceeding balance) via `Promise.all`/threads against a test DB; assert exactly one succeeds and the balance never goes negative; before the fix more than one passes.
- Replay: deliver the same webhook `event_id` twice; assert one side effect and the same response.
- Revocation: queue a job, revoke the actor's permission, run the job; assert it is refused with no effect.
- Cache: user in tenant A populates the cache, tenant B requests the same URL; assert B does not receive A's data.
- Workflow: call the final step without prerequisites; assert rejection. Allowed case: the normal ordered flow and a legitimate retry (same idempotency key) still succeed.
